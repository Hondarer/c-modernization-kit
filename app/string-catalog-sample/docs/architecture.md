# string-catalog-sample のアーキテクチャー

## この文書の位置付け

この文書は、文字列カタログの責務分離、書式の仕様、生成物の境界を示します。  
公開 API の契約は公開ヘッダーの Doxygen コメントを正本とし、この文書には複製しません。

利用側から見た要件と外部から観測できる振る舞いは [機能仕様](functional-spec/README.md) を正本とします。  
この文書は、機能仕様が定める要件を、どの構成で実現するかを示します。

## 解決する課題

文字列を多言語で出力する場合、翻訳のたびに語順が変わります。  
`printf` の書式を翻訳者へ渡すと、語順の変更に伴って引数の順序も変わり、型の不一致による未定義動作を招きます。

C の可変長引数は順番にしか安全に取り出せません。  
`va_arg` で指定した型が実引数の型 (既定引数拡張後) と適合しない場合、動作は未定義です。  
このため、書式だけを差し替える方式では、翻訳の誤りがそのまま実行時の破壊につながります。

本サンプルは、次の 5 点でこの課題を扱います。

- 引数の型と文字列表現は文字列 ID 側の引数スキーマが決めます。
- 言語別リソースは語順だけを決めます。書式指定は書けません。
- 可変長引数は最初に一度だけ値の配列へ写し、そのあとで書式を展開します。
- 出力する言語はプロセスで 1 つとし、文字列を組み立てるたびには指定しません。
- カタログはライブラリが抱え込まず、利用者が注入します。

## 責務の 3 段構成

処理は次の 3 段で進みます。

```text
                  文字列 ID
                       |
          +------------+------------+
          |                         |
     引数スキーマ              言語別リソース
          |                         |
     { STRING,               日本語: "...{1}...{0}"
       ERROR_CODE }          英語:   "...{0}...{1}"
          |                         |
          +------------+------------+
                       |
                       v
              可変長引数の取り出し
                       |
                       v
              値の配列 (最大 10 個)
                       |
                       v
              位置指定書式の展開
                       |
                       v
                UTF-8 の文字列
```

| 段 | 実装 | 責務 |
|---|---|---|
| 入口 | `prod/libsrc/string_catalog/string_catalog_format.c` | 引数検査、カタログの取得、言語別リソースの選択、下位 2 段の呼び出し |
| 保持 | `prod/libsrc/string_catalog/string_catalog_catalog.c` | 注入されたカタログの保持と、文字列 ID による検索 |
| 取り出し | `prod/libsrc/string_catalog/string_catalog_argument.c` | 引数スキーマに従って `va_arg` の型を選び、値の配列へ写す |
| 展開 | `prod/libsrc/string_catalog/string_catalog_render.c` | 位置指定を値の文字列表現へ置き換える |

`va_arg` の型指定は取り出しの段だけに現れます。  
ほかの段は値の配列だけを扱うため、可変長引数の制約から独立します。

値の配列を経由することで、次を実現します。

- 位置指定の並べ替え (`{1}` を `{0}` より前に置く)
- 同じ位置指定の繰り返し参照 (`{0}` を 2 回書く)
- 可変長引数を持たない入力源への将来の転用

## 言語の扱い

出力する言語はプロセスで 1 つです。  
`string_catalog_set_language()` で設定し、文字列を組み立てる API には言語を渡しません。  
状態は `prod/libsrc/string_catalog/string_catalog_language.c` が保持します。

言語設定は同期を持たないプロセス グローバルな状態です。  
プロセスの初期化時に設定し、文字列を組み立てている間は変更しない前提です。  
設定を変更しない限り、文字列の組み立ては複数のスレッドから同時に行えます。

言語の 0 番はニュートラル言語です。  
`string_catalog_set_language()` を呼び出していないプロセスの既定値であり、言語別リソースが欠けている場合の読み替え先でもあります。

ニュートラル言語以外の要素が NULL の場合は、ニュートラル言語の要素を使用します。  
翻訳が追い付いていない言語でも、文字列を出力できます。  
ニュートラル言語の要素は NULL にできません。

現在のカタログでは、ニュートラル言語の書式を暫定的に英語と同じ表現とし、英語の要素を NULL としています。  
英語をニュートラル言語と分ける必要が生じた時点で、英語の要素を追加します。

## 書式の仕様

書式が解釈するのは、位置指定とエスケープだけです。

| 記法 | 意味 |
|---|---|
| `{0}` から `{9}` | 対応する位置の引数を、引数種別が定める表現で展開します。 |
| `{{` | `{` を 1 文字出力します。 |
| `}}` | `}` を 1 文字出力します。 |

添字は 1 桁だけを受け付けます。  
引数の上限が 10 個であるのは、1 桁の添字で表せる範囲がここまでであるためです。  
`{01}` のような 2 桁、`{abc}` のような数字以外、引数個数を超える添字、対を成さない `{` と `}` は、いずれも定義エラーです。

書式指定を書けないのは、言語ごとに値の表現が変わることを防ぐためです。  
`{0:X8}` のような記法を認めると、日本語では 16 進数、英語では 10 進数といった食い違いが発生し、ログの解析が言語に依存します。

## 引数種別

引数種別は、可変長引数から取り出す型と文字列表現を 1 つにまとめた列挙です。  
型と表示形式を別々の列挙に分けると、`STRING` と 16 進表示のような意味を持たない組み合わせを表現できてしまいます。

既定引数拡張によって `char` と 8 bit、16 bit の整数は `int` へ、`float` は `double` へ昇格します。  
そのため 8 bit と 16 bit の種別は `int` として取り出し、種別が表す幅へ変換してから格納します。  
昇格後の型と一致しない `va_arg` の指定は行いません。

単精度浮動小数点数の種別は設けていません。`double` へ昇格した値を倍精度として扱えば足りるためです。

`SSIZE` 種別が受け取る型は `int64_t` です。  
POSIX の `ssize_t` は Windows に無く、幅も処理系で異なるため、公開契約へ露出させません。  
これは [コーディング規範](../../general/docs/coding-guideline.md) の「クロスプラットフォーム API の I/O 結果には `int64_t`」に従う判断です。

種別ごとの対応表は、公開ヘッダー `prod/include/string_catalog/string_catalog_argument.h` を正本とします。

## メタデータ

カタログは、書式のほかに次の 3 つを保持します。

| 項目 | 参照 API | 内容 |
|---|---|---|
| 文字列 ID の固定文字列 | `string_catalog_id_text()` | `STRING_CATALOG_ID_0001` のような、言語に依らない参照名です。ログの検索キーや障害報告で使用します。 |
| 分類値 | `string_catalog_category()` | ライブラリが解釈しない `int` の補足情報です。言語に依らず、文字列 ID ごとに固定です。 |
| 備考 | `string_catalog_note()` | 引数の単位や出力条件など、書式には含めない補足です。言語別に持ち、書式と同じ読み替えを行います。 |

固定文字列と分類値は言語に依らず、備考は現在の言語のものを返します。  
カタログに存在しない文字列 ID では、固定文字列と備考は NULL、分類値は 0 を返します。

### 分類値

分類値は、ライブラリが意味を持たない `int` です。  
重大度、用途、出力先など、値の意味と有効な範囲は利用者が決めます。  
ライブラリは値を検査せず、保持して返すだけです。

0 は分類なしを表します。  
利用者が 0 を意味のある分類値として登録することもできますが、その場合はカタログに存在しない文字列 ID と区別できません。  
区別が必要な場合は、先に `string_catalog_id_text()` で存在を確認します。

この app では、分類値をトレース レベルとして使います。  
列挙 `string_catalog_trace_level` は、カタログ定義と同じ `prod/src/cmd/string-catalog-sample/string_catalog_definition.h` にあります。  
値は cplat の `cplat_trace_level` と同一です。  
この app は標準 C だけで完結するサンプルであり cplat に依存しないため、同じ値をここで再実装しています。  
cplat を利用する app へ移植する場合は、値が同じであるため変換表なしで置き換えられます。

範囲外の値は、コマンドの `trace_level_of()` が `STRING_CATALOG_TRACE_LEVEL_NONE` へ切り詰めます。  
意味付けを行う階層で切り詰めるため、ライブラリとそのテストは分類値の範囲を確認しません。

本 app はトレースの出力機構を持ちません。  
レベルは、利用側が出力先や絞り込みを決めるための情報として保持します。

## カタログの注入

カタログはライブラリが抱え込みません。  
利用者が定義し、`string_catalog_set_catalog()` でプロセスへ注入します。

利用者が用意するのは次の 2 つだけです。

| 利用者が用意するもの | 内容 |
|---|---|
| 文字列 ID の列挙 | 文字列を識別する定数です。名前と値は利用者が決めます。 |
| カタログの配列 | 引数スキーマ、分類値、メタデータ、言語別の書式と備考です。 |

ライブラリが定めるのは、言語、引数種別、書式の構文、結果コードです。  
これらは利用者から変更できません。

文字列 ID の型を列挙にせず `int` としているのは、列挙を利用者側で定義できるようにするためです。  
ライブラリは `string_catalog_id` という名前を定義しません。  
利用者は任意の名前の列挙を定義し、その定数をそのまま渡せます。

本サンプルでは、この 2 つをコマンド側の `prod/src/cmd/string-catalog-sample/` へ置いています。

| ファイル | 内容 |
|---|---|
| `string_catalog_definition.h` | 文字列 ID の列挙と、カタログを取得する宣言 |
| `string_catalog_definition.c` | カタログの配列と添字表 |

この 2 ファイルは、カタログ定義 (Excel など) からの 1 組の生成物です。  
列挙と表は常に同時に生成します。  
現時点では、生成器そのものは含みません。

言語別の書式と備考は、言語をキーとした指示付き初期化子で記載します。

```c
{[STRING_CATALOG_LANGUAGE_NEUTRAL] = "Failed to open file {0}. Error code={1}",
 [STRING_CATALOG_LANGUAGE_JAPANESE] = "ファイル {0} を開けませんでした。エラー コード={1}"},
```

位置ではなく言語で対応が決まるため、言語の追加や並べ替えの影響を受けません。  
記載しなかった言語の要素は暗黙にヌル ポインターとなり、ニュートラル言語への読み替えがそのまま働きます。  
リソースを持たない言語は、行ごと省略できます。

配列はコピーせず、ポインターだけを保持します。  
プロセスの生存期間にわたって有効な領域を渡す必要があるため、静的記憶域期間を持つ配列を想定しています。

注入していないプロセスは、カタログが空であるものとして扱います。  
この状態で文字列を組み立てると `STRING_CATALOG_ERR_NOT_FOUND` を返します。

書式を展開する実装は、注入されたカタログを直接参照しません。  
`prod/include_internal/string_catalog/catalog.h` が宣言する 3 つの関数だけを経由します。  
保持と検索は `prod/libsrc/string_catalog/string_catalog_catalog.c` が担います。

### 添字表による探索

文字列 ID からカタログを引く探索は、既定では線形探索です。  
利用者は、文字列 ID を添字としてカタログの添字を引く表を添えられます。

```text
string_catalog_set_catalog(entries, entry_count, id_index, id_index_count)

  id_index[string_id] -> entries の添字 (未登録は負の値)
```

添字表を渡すと、線形探索を添字引きへ置き換えます。  
文字列 ID が小さい非負整数である場合に使用できます。  
文字列 ID が添字表の範囲を超える場合は、線形探索へフォールバックします。

添字表の内容は利用者が用意するため、参照する前に値の範囲を確認します。  
`string_catalog_verify()` は、各文字列が添字表を通して自分自身へ到達することも確認します。  
これにより、表と配列が食い違った状態や、文字列 ID の重複を検出できます。

## カタログの点検

`string_catalog_verify()` は、カタログ全体の書式が引数スキーマと矛盾しないことを確認します。  
確認するのは、書式の構文、位置指定の添字が引数個数に収まること、引数個数が上限に収まること、添字表から各文字列へ到達できること、ニュートラル言語の書式と備考が揃っていることです。  
分類値はライブラリが解釈しないため、範囲を確認しません。

ニュートラル言語以外のリソースは、欠けていればニュートラル言語へ読み替えるため、欠けていること自体は不正ではありません。

カタログは注入した時点で内容が確定するため、点検は起動時に一度実行すれば十分です。  
文字列を組み立てるたびに実行する必要はありません。

サンプル コマンドは、カタログを注入した直後にこの関数を呼び出します。

## 依存関係

この app は標準 C だけで完結し、`appdeps.mk` を持ちません。  
結果コードは `STRING_CATALOG_OK` と `STRING_CATALOG_ERR_*` の独自体系であり、ほかの app の結果コードとは別系統です。

エラー コードの引数種別は、Linux の `errno` と Windows のエラー コードのどちらも `int` として受け取ります。  
プラットフォーム固有のエラー変換は行いません。

## テストの構成

| テスト | 対象 |
|---|---|
| `stringCatalogRenderTest` | 位置指定書式の展開と構文確認 |
| `stringCatalogArgumentTest` | 引数種別ごとの可変長引数の取り出し |
| `stringCatalogLanguageTest` | プロセスの言語設定 |
| `stringCatalogCatalogTest` | カタログの注入と、文字列 ID による検索 |
| `stringCatalogFormatTest` | 公開 API。カタログはテスト ディレクトリの偽物を注入する |
| `stringCatalogDefinitionTest` | コマンドが用意するカタログと添字表 |
| `catalogIntegrationTest` | コマンドのカタログと展開処理を結合した確認 |

`stringCatalogFormatTest` がカタログを偽物へ差し替えるのは、コマンドのカタログが正しい内容だけを持ち、定義が壊れた場合の経路へ到達できないためです。  
偽物はテスト ディレクトリの `fake_catalog.c` にあり、テストから文字列 ID、分類値、引数個数、引数種別、言語別の書式と備考を書き換えられます。  
偽物は添字表を渡さずに注入するため、線形探索の経路も同時に確認できます。

`stringCatalogDefinitionTest` は `test/src/cmd/` に置きます。  
対象がライブラリではなく、コマンドが用意するソースであるためです。

`stringCatalogLanguageTest` は、既定値を確認するテストを先頭に置きます。  
言語設定はプロセス グローバルな状態であり、後続のテストが値を変更するためです。
