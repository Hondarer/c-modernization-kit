# 文字列カタログの条件式フィルターの調査結果と cplat 移行方針

共有配布は、第 3 段階で一時ディレクトリのメモリ マップしたファイルとファイル ロックに置き換えました。

### カタログへの関連付けを維持する

確認済みの状態として、フィルター本体は特定のジョブ名やワーカー番号を参照しません。  
引数名と型をカタログから取得するため、アプリ固有の `sequence_number` も通常の引数として照合できます。

推奨方針は、次の構造を維持することです。

- カタログを参照せず、条件式をポインターを含まないイメージへコンパイルします。
- スロット作成時にカタログと結び付け、イメージの適用時に名前解決と事前計算を行います。
- 項目ごとの判定を「常に一致」「常に不一致」「引数値に依存」の 3 状態に分けます。
- 未使用の面へ適用結果を構築し、読み書きロックの下で参照する面を切り替えます。
- ハッシュ値とバイト列が一致する行は、前回の事前計算結果を再利用します。

公開名は `cplat_string_catalog_filter_*` を基本とし、スロットは不透明型を維持します。  
公開宣言は `prod/include/cplat/string_catalog/`、実装と私有宣言は既存の `prod/libsrc/cplat/string_catalog/` 内へ配置する方針を推奨します。  
同じモジュール内で引数収集と書式展開の私有関数を共有できるため、内部の値配列や命令形式を公開する必要がありません。

## 条件一致による強制出力を維持する

通常時の詳細度は出力先のしきい値で決め、条件に一致したトレースだけを `CPLAT_TRACE_LEVEL_TO_FORCE` で強制出力へ変更します。  
条件に一致しないトレースも書式展開を行い、元のレベルで出力先へ渡します。  
条件式リストが空の場合は強制出力へ変更するトレースがなく、通常のトレース出力を継続します。

### 判定と出力方針の責務

| 層 | 担う処理 |
|---|---|
| cplat のフィルター本体 | 条件の一致結果と、組み立てた文字列を返します |
| トレース種別の生成物 | 分類値をトレース レベルとして扱い、一致時に強制出力へ変更します |
| 利用側 | 出力先、条件の更新時期、配布方法を決定します |

Table: 判定とトレース出力を結び付ける各層の責務

公開 API は、PoC の `sample_filter_slot_format` / `vformat` と同じく、常に文字列を組み立てて一致結果を返す `cplat_string_catalog_filter_slot_format` / `vformat` とします。  
移動と改名の段階で、この名前で公開済みです。  
公開関数の最終名、引数順序、出力引数と失敗時の状態は、cplat の規範と照合して確定しました。  
照合で見直したのは 2 点です。  
コンパイルの書き込み先の引数は、ほかの書き出す関数と同じく `image_out` としました。  
行を無効にした原因の列挙型は、関数の結果コードと取り違えないよう `cplat_string_catalog_filter_line_error` としました。

### 引数収集を既存の書式展開と共有する

試作の `slot_vformat()` は、判定用に複製した `va_list` から引数を収集し、書式展開時には `cplat_string_catalog_vformat()` が再び引数を収集していました。  
移行後は `cplat_internal_string_catalog_prepare_format()` で 1 回だけ収集し、判定と書式展開で同じ値を使用します。  
判定は、共有の値を比較の区分ごとに正規化して評価します。

事前計算で一致が確定する場合も、文字列の組み立てに必要な引数収集は残ります。  
この共通化の効果は、収集の重複解消です。

## 生成器との接続で型検査と定義の一元管理を回復する

確認済みの状態として、PoC の `sample_filter_output` マクロは生成物の型付きラッパーを経由しません。  
このため、ラッパーによる引数の型検査が働かず、コンテキスト引数の取得式を設定ファイルと出力マクロで二重管理しています。  
キーの名前解決表も手動定義です。

生成器へ次の機能を追加する方針を推奨します。

- カタログのキー定義から名前解決表を生成します。
- カタログ単位でフィルターを接続し、未接続時は既存の出力動作を維持します。
- 型付きラッパーの `_with_source` 経由で、呼び出し位置とコンテキスト引数を付与します。
- 別のカタログ用スロットの誤接続を防ぐ構造を設けます。
- ライブラリがカタログを公開する場合も、利用者へカタログ構造体を露出させずに設定できる入口を用意します。

`sequence_number` の取得式と意味は、引き続きアプリ側が所有します。  
移行後は生成物が設定ファイルから取得式を展開するため、出力マクロ側での二重管理を解消できます。

接続 API の形式、接続先の所有権、解除と破棄の順序、出力中の設定変更の可否は、既存のトレーサー設定にそろえる方針とし、「第 2 段階: 生成器とサンプルの接続」で具体化します。

## 公開 API 化に必要な契約と検査を補強する

| 論点 | 確認済みの状態 | 推奨方針 |
|---|---|---|
| 分類名の変更 | 名前解決結果を再利用するため、最初の適用より前に設定する契約です | 作成時に設定を固定する設計を優先します |
| 分類値の範囲 | 名前配列のインデックスが値となり、名前指定時は `0` から `count - 1` に限定されます | 負値や非連続の値を扱う必要があれば、値と名前の対応表へ変更します |
| カタログの入力検査 | 作成時の検査は限定的で、後続処理は引数定義を直接参照します | 引数の個数、配列、種別、名前解決表の整合を入口で確認します |
| メモリ量 | 行数とカタログ項目数に応じた事前計算領域を 2 面確保します | サイズ演算の前提をコンパイル時に固定し、使用量を測定しました (「事前計算の領域のメモリ量を測定した」を参照) |
| エラー通知 | 判定用ロックの取得失敗が、不一致として書式展開へ進む経路があります | 公開 API では判定失敗を結果コードで区別します |
| イメージの互換性 | 形式版とバイト順を検査しますが、異なる形式への変換はありません | 対応形式と非対応時の拒否を契約に明記します |

### 分類名の解決と表示を整理する

現行の分類名設定には、識別子の解決、値の制限、自然文の表示が結び付いています。  
説明用の名前を設定すると受理する条件の範囲も変わるため、汎用 API では設定ごとの意味を明示する必要があります。  
分類名の表現と値の制限を分離するか、作成時の一体の設定として扱うかは、実装前に決定します。

決定事項は次のとおりです。

- 分類値の名前はスロットの作成時に渡して固定し、作成後の設定関数は廃止しました。
- 名前による指定、値の範囲の制限、説明文での表示は、1 つの設定のまま扱い、その効果を契約と機能仕様へ記載しました。
- 名前を付けられる値は 0 から始まる連続した値に限る現状を維持し、負の値や連続しない値への対応は適用範囲外としました。

分類値をトレース レベルとして解釈する規則は、フィルター本体へ持ち込みません。  
設定がない場合は匿名の整数として扱い、有効な範囲は利用側が決める境界を維持します。

### 説明文の文型を共通機能として扱う

自然文の説明には、項目の `brief` と `id`、引数の名前と説明を利用できます。  
PoC では、行が 1 項目に限定される場合はその項目の引数説明を使用し、複数項目が対象でも説明が共通の場合は説明を添えます。  
cplat へ移したあとも、この振る舞いを維持しています。

cplat は日本語とニュートラル言語の説明文型を保持します。  
これに伴い、ライブラリが文言を保持しないという責務境界を、その文型の範囲に限って更新し、string_catalog モジュールの README へ例外として記載しました。  
アプリのメッセージ内容とメタ情報は利用側の資産として維持します。  
メタ情報は言語別ではないため、説明文型を切り替えてもメタ情報自体は翻訳されません。

### 事前計算の領域のメモリ量を測定した

スロットは、作成時に 2 面分の事前計算の領域を確保します。  
1 面の大きさは、フィルター オブジェクトの大きさに加え、行数を L、カタログの項目数を E とすると、測定の時点ではおおよそ `9 × L × E + 9 × E + 132 × L` バイトでした。  
その後、正規表現の保持 (1 行あたり 32 バイト) と、行数の上限を 1024 へ広げるための行の集合の配列化を加えたため、現在の計算式は cplat の設計資料の「判定の事前計算」を参照してください。  
大半を占めるのは行と項目の組ごとの判定結果と引数の対応表で、2 面合わせて `18 × L × E` バイトになります。

作成の前後でヒープの使用量を測定した結果を次に示します (Linux、glibc の `mallinfo` による測定)。

| 項目数 | 行数 | 行幅 | 実測 | 計算式による値 |
|---|---|---|---|---|
| 7 (サンプルのカタログ) | 32 | 256 | 283,616 バイト | 275,924 バイト |
| 1,000 | 64 | 1024 | 3,301,056 バイト | 3,286,246 バイト |
| 10,000 | 64 | 1024 | 13,825,056 バイト | 13,816,246 バイト |
| 100,000 | 64 | 1024 | 119,129,120 バイト | 119,116,246 バイト |

Table: スロット 1 個の作成で増えるヒープ使用量

実測と計算式の差は、スロット本体、同期オブジェクト、メモリ確保の管理領域の分です。  
行数を 64 とすると項目 1 件あたり約 1.1 KiB となり、項目数が 10 万件を超えるカタログでは 100 MiB を超えます。  
行数の上限は 1024 へ広げましたが、メモリは固定長で確保する原則を保つため、行数に比例して増えます。  
大きなカタログで使用する場合は、行数の上限を必要な分だけに抑えるか、対象の項目を分けた別のカタログで判定することを検討します。

## 共有配布は実プロセス間の契約を定めてから統合する

確認済みの状態として、共有領域は `calloc()`、排他は `cplat_local_lock` による模擬です。  
同じパスの領域を同一プロセス内で共有できますが、別プロセスへの配布は実現していません。

世代管理、公開前検証、変更時だけの取り込み、取り込み結果の取得は共通化できます。  
領域の管理には既存の `cplat_mmap` と `cplat_interprocess_lock` を利用する方向を推奨します。  
ただし、模擬実装の置き換えだけでは運用上の契約は確定しません。

| 未決事項 | 実プロセス間配布の設計で決定する内容 | 第 2 段階のソース領域による扱い |
|---|---|---|
| 領域の作成と初期化 | 同時起動、既存領域のサイズ不一致、作成者と削除者の責務 | 未決。0 で埋まった領域を未公開として扱う点だけが決まります |
| 排他 | プロセス内のスレッド排他とプロセス間排他の組み合わせ、取得順序 | 書き込み側の排他を読み取り側にも渡し、変化を検知したときだけ二重確認で取ります。プロセス間で共有する排他の選定が残ります |
| 公開途中の異常終了 | 不完全な公開内容の検知、以前の条件の維持、復旧手順 | 公開時刻が奇数のまま残り、以前の条件を維持します。次の公開で回復します |
| 領域の再作成 | 世代番号の再利用と新しい領域の識別 | 単調増加クロックの値を使うため、再利用は起きません |
| 取り込み失敗 | 再試行する条件、成功した世代と試行した世代の区別 | 試行した公開時刻を記録し、同じ公開内容は再試行しません。結果は状態取得で確認します |
| 適用中のロック | 領域の複製とスロットへの適用を分けるか、ロック保持時間の許容範囲 | 複製と適用を分け、どちらも書き込み側を待たせません |

Table: 実プロセス間配布へ移行する前に決定する事項

試作の実装は、適用失敗時にも取り込み済み世代を更新して、同じ世代の再試行を止めます。  
また、スロットへの適用が終わるまで配布用ロックを保持します。  
第 2 段階のソース領域は、再試行を止める方針を引き継ぎ、ロックの保持をなくします (「条件の取り込みを公開時刻の比較で検知する」を参照)。

フィルター本体は共有メモリを参照せず、先頭アドレスとバイト数でイメージを受け取る境界を維持します。  
これにより、配布機構の整備を待たずに本体の統合を進められます。

## 本体、生成器、共有配布の順に移行する

### 第 1 段階: 本体の統合

コンパイル、行編集、検証、判定、差し替え、説明文を cplat へ移し、公開入力の検査とエラー処理を補強します。  
引数収集を既存実装と共有し、サンプルは cplat の API を利用する構成へ切り替えます。  
この段階では、サンプルの出力接続と模擬配布を新しい API に接続して利用します。

完了条件は、共通機能のテストを cplat 側で実行でき、サンプルの条件編集、一覧表示、通常出力と強制出力が維持されることです。

変更を小さく保つため、第 1 段階は変更の種類ごとに分けて進めます。

| 回 | 内容 | 状態 |
|---|---|---|
| 1 | コンパイル、フィルター オブジェクト、スロット、説明文を `cplat/string_catalog/filter.h` と `string_catalog/filter/` へ移動し、`cplat_string_catalog_filter_*` へ改名する。サンプルは cplat の API を利用し、PoC 側の実装は削除する | 完了。動作と契約は変更せず、サンプルの単体テスト 81 件とエクスポート テストが成功 |
| 2 | 公開入口の結果コードを補強する。判定用ロックの取得失敗は文字列を組み立てずに結果コードで返し、ロックの作成失敗は作成関数の結果コードを返す | 完了。失敗経路を cplat 側の `stringCatalogFilterSlotTest` で確認 |

#### 条件の取り込みを公開時刻の比較で検知する

試作の出力層は、出力のたびに共有配布から条件を取り込んでいました。  
この「出力のたびに変化を確かめる」動作を、アプリ固有の呼び出しではなく cplat の機能として提供します。  
条件の受け渡しに使うメモリ領域を「ソース領域」と呼び、スロットへ結び付けます。  
ソース領域は先頭アドレスとバイト数で受け取り、共有メモリ、ファイルのマップ、プロセス内の静的領域のどれでも構いません。

ソース領域は、64 バイトのヘッダーと、それに続くフィルター オブジェクトで構成します。  
ヘッダーには、署名、形式版、行数の上限、行幅、フィルター オブジェクトのバイト数と並べて、公開時刻を置きます。  
公開時刻は単調増加クロックのナノ秒値で、アトミックに読み書きする 64 ビットの整数です。  
表示用に、公開した実時刻とプロセス ID も記録します。

| 公開時刻の値 | 意味 |
|---|---|
| 0 | 未公開です。0 で埋まった新しい領域はこの状態です |
| 奇数 | 書き込み中です。読み取り側は取り込みません |
| 0 以外の偶数 | 公開済みです。値が変わったことを、公開内容が変わったことと見なします |

Table: ソース領域の公開時刻が表す状態

単調増加クロックの値を使う理由は、次の 3 点です。

- 書き込み側が前回の値を知らなくても、新しい値が前回より大きくなります。複数の書き込み側が順に公開しても、値が重複しません。
- 領域を作り直しても、前の領域で読み取った値より新しい値になります。世代番号の再利用を考える必要がありません。
- OS の再起動で単調増加クロックが小さな値へ戻っても、ファイル上に残った領域では、前回の値に 2 を加えた値が採られるため、公開時刻は増え続けます。
- Linux の `CLOCK_MONOTONIC` と Windows の `GetTickCount64()` は、どちらもプロセス間で共通の時間軸です。

Windows の単調増加クロックはミリ秒単位のため、同じ時刻に 2 回公開することがあり得ます。  
書き込み側は、前回の値に 2 を加えた値と現在の値のうち大きいほうを新しい値とし、常に増加させます。

前回の値に 2 を加えると 64 ビットを超える場合は、2 と現在の値のうち大きいほうへ戻します。  
読み取り側は大小ではなく不一致で変化を判定するため、戻った値でも取り込みます。  
戻った値が読み取り側の取り込み済みの値と一致するのは、その読み取り側が上限までの公開をすべて取り込み損ねた場合に限られ、現実には起こりません。  
ナノ秒の単調増加クロックで上限に届くには約 584 年かかるため、上限に達するのは壊れた値や意図的に大きくした値に限られます。

memory mapped file のように領域が OS の再起動を越えて残る場合は、異なる版のライブラリや異なる行数の上限と行幅で書かれた内容が残っていることがあります。  
読み取り側は、ヘッダーの署名、形式版、行数の上限、行幅を確かめ、一致しない公開内容はフィルター オブジェクトを読まずに取り込みの失敗として記録します。  
書き込み側は、署名または形式版が異なる領域への公開を拒否し、その領域を上書きしません。

公開と取り込みの手順は、seqlock と同じ形です。

1. 書き込み側は、公開時刻を奇数にしてから、ヘッダーとフィルター オブジェクトを書き込み、最後に新しい偶数の値を書き込みます。
2. 読み取り側は、出力のたびに公開時刻を 1 回だけアトミックに読みます。奇数の場合と、適用済みの値と同じ場合は、そのまま判定へ進みます。
3. 値が変わっていた場合は、スロット内の作業領域へフィルター オブジェクトを複製し、公開時刻を読み直します。
4. 読み直した値が最初の値と異なる場合は、複製を捨てて、次の出力で改めて取り込みます。
5. 一致した場合は、複製を検証してスロットへ適用し、その値を適用済みとして記録します。

適用に失敗した場合も、その値を適用済みとして記録し、同じ公開内容の取り込みを繰り返しません。  
結果コードと無効にした行の数は、状態取得の関数で確認できます。

複製中に書き込みが重なった場合は、公開時刻の読み直しで検出します。  
読み直しをすり抜けた破損も、フィルター オブジェクトのハッシュ値の検証で拒否されます。

公開時刻の確認では、読み取り側はロックを取りません。  
ただし、ロックを取らない複製は書き込み中の領域を読み得ます。一貫しない内容は公開時刻とハッシュ値で捨てますが、C11 の規則ではデータ競合になります。  
そこで、試作の二重チェック (緩いチェック、書き込み側と同じロック、最終チェック、複製) を、結び付けの任意の引数として残しました。  
書き込み側の排他を渡した場合、スロットは変化を検知したときだけその排他を取り、公開時刻を読み直してから複製し、複製を終えた時点で解放します。  
検証と適用は排他の外で行うため、書き込み側を待たせるのは複製の間だけです。  
排他を取得できない場合は取り込まず、結果コードを記録して次の判定で改めて試みます。  
サンプルは、書き込み側どうしを直列化している `sample_filter_share` の排他を、読み取り側にも渡します。  
書き込み中に書き込み側が異常終了した場合、公開時刻は奇数のまま残り、読み取り側は適用済みの条件を使い続けます。  
次に公開した時点で回復します。  
書き込み側どうしの排他は、引き続き利用側が行います。

取り込みは、スロットの判定付き組み立て (`cplat_string_catalog_filter_slot_vformat()` と `_format()`) の中で行います。  
複数のスレッドが同時に変化を検知した場合は、1 つのスレッドだけが取り込み、ほかのスレッドは適用済みの条件で判定を続けます。  
取り込みを待たせないためです。  
生成物の `<module>_write()` はこの関数を使うため、生成物にアプリ固有の取り込み処理を呼び出す仕組みは要りません。

### 第 3 段階: 実プロセス間の配布

共有配布の未決事項を確定してから、模擬領域を実際の共有領域と排他へ置き換えます。  
複数の発行元と受信先、異常終了、再起動を検証します。

#### 領域と排他の実装を cplat の外へ委譲する

ソース領域のメモリと排他の実装は、cplat 以外のライブラリやアプリが主体的に受け持てるようにします。  
cplat は、先頭アドレスとバイト数、および排他を取得、解放する関数の組だけを受け取ります。

| 操作 | cplat が受け取るもの | 排他の扱い |
|---|---|---|
| 公開 (`cplat_string_catalog_filter_source_publish`) | 先頭アドレス、バイト数、排他の関数の組 (任意) | 関数の組を受け取った場合は、cplat が書き込みの間だけ取得します。受け取らない場合は、呼び出し側が直列化します |
| 取り込み (`cplat_string_catalog_filter_slot_attach_source`) | 先頭アドレス、バイト数、排他の関数の組 (任意) | 関数の組を受け取った場合は、変化を検知したときだけ取得する二重確認で複製します |
| 情報取得 (`cplat_string_catalog_filter_source_get_info`) | 先頭アドレス、バイト数 | 排他を取らず、書き込み中は `CPLAT_ERR_BUSY` を返します |

Table: ソース領域の操作と cplat が受け取るもの

このサンプルでは、領域と排他の実装をコマンド内のモジュール (`sample_filter_share_region.c`) に置きます。  
`sample_filter_share` は、そのモジュールの領域と排他を、関数の組として cplat の公開と取り込みへ渡します。

| 項目 | 決定 |
|---|---|
| インターフェイスと実装 | `sample_filter_share_region.h` は cplat に依存せず、結果を独自の列挙型で返します。実装は `cplat_mmap` と `cplat_interprocess_lock` を使います |
| 置き場所 | 一時ディレクトリの `string-catalog-filter-sample.share` に固定します |
| 作成と初期化 | 開いた時点でファイルがなければ作成し、0 で埋めます。複数のプロセスが同時に作成しないよう、排他の下で開きます |
| 既存のファイルの大きさ | 必要な大きさに満たない場合は、作り直さずに開くことを拒否します。大きい場合は受け付け、先頭の必要な大きさだけを使います |
| 削除 | どのプロセスも削除しません。再起動後も最後の公開内容を引き継ぎます |
| 排他の実体 | 共有メモリのパスに `.lock` を付けたファイルのファイル ロック。同じプロセスのスレッドは、先にプロセス内のロックで直列化します |
| 排他を待つ時間 | 開くときと公開は取得できるまで待ちます。取り込みは 100 ミリ秒までとし、取得できなければ次の出力で再試行します |

## 検証は既存テストを移植し、公開境界を追加する

共通機能のテストはサンプルのワーカー定義への依存を外し、cplat 内のテスト用カタログへ移します。  
アプリ固有の巡回連番、対話操作、生成物との接続確認は、利用側のテストとして残します。

| 検証対象 | 主な確認内容 |
|---|---|
| コンパイルと編集 | 構文、上限値、診断位置、失敗した編集による既存内容の維持 |
| イメージ検証 | 署名、形式版、長さ、ハッシュ、命令、ジャンプ先、定数参照の破損 |
| デコンパイル | 復元後の再コンパイルによる一致、括弧、出力領域不足 |
| 名前解決と判定 | 不明な名前、異なる型の同名引数、未使用引数、数値境界、NULL、分類名 |
| 差し替え | 複数スレッドの適用と判定、失敗時の旧条件維持、入力イメージの寿命 |
| 公開 API | 不正なカタログ、名前解決表、サイズ計算、割り当て失敗、結果コード |
| 説明文 | 日本語とニュートラル言語、項目の限定、共通する引数説明、無効行 |
| 生成器と出力 | 型付きラッパー、呼び出し位置、コンテキスト、通常出力と強制出力、公開範囲 |
| 共有配布 | 同時公開、複数受信先、異常終了、再作成、取り込み失敗と復旧 |
| 性能と資源 | カタログ項目数と行数に対するメモリ量、判定コスト、適用時の待機時間 |

Table: 移行時の検証対象と確認内容

破損イメージのテストでは、単なるハッシュ不一致だけでなく、構造検査まで到達する入力も用意します。  
命令列や参照先の検査が実際に機能することを確認するためです。

これに沿って、壊れたイメージのテストではハッシュ値を計算し直し、ハッシュ値の確認では拒否されない状態で構造の検査に届かせています。  
計算し直しが正しいことは、書き換えずに計算し直したイメージが検証に成功することで確かめています。  
追加後のカバレッジは、`filter_image.c` の行が 85%、分岐が 69% です (追加前は 82% と 63%)。

Linux/GCC と Windows/MSVC の双方で局所ビルドと関連テストを行い、内容がある `.warn` を確認します。  
生成器変更時は `app/cplat/bin_test/` で `python3 -m unittest test_string_catalog_gen` を実行します。  
framework または複数 app にまたがる全体テストは、コストを説明してユーザーに確認してから実施します。
