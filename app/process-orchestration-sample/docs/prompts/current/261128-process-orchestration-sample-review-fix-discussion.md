**Question**

BL-018 で、cplat に存在しない `GetFileAttributesU`、`DeleteFileU`、`CreateDirectoryU` を、どの方法で置き換えますか。

**Context**

- **経緯と背景**: この 3 つの関数は `cplat/win32/win32.h` に定義されておらず、Windows のリンクで失敗します。使用箇所は、ディレクトリの作成 (`ipc_endpoint.c` の `create_single_dir`)、ソケット ファイルの存在確認と削除 (`ipc_transport_unix_windows.c`) です。
- **根拠資料**: cplat には、両 OS で使える UTF-8 のファイル操作がすでにあります。
    - `cplat_stat` (`cplat/crt/sys/stat.h`): Windows では `_wstat64` を使います。
    - `cplat_mkdir` (`cplat/crt/sys/stat.h`): Linux では権限 `0755` (umask 適用) で作成し、Windows では権限を指定しません。
    - `cplat_remove` (`cplat/crt/stdio.h`): ファイルを削除します。
- **Linux の権限の注意**: `cplat_mkdir` は Linux で `0755` を使うため、ソケットの親ディレクトリに必要な `0700` を満たしません。Linux では現在の `mkdir(path, 0700)` を残す必要があります。

```c
/* 案 A: cplat の既存の関数を使う (Windows の分岐) */
rc = cplat_mkdir(path, detail_out);
/* 失敗した場合は cplat_stat で既存のディレクトリかどうかを確認する */
```

```c
/* 案 B: cplat/win32/win32.h に UTF-8 版を追加する */
CPLAT_EXPORT DWORD CPLAT_API GetFileAttributesU(const char *lpFileName);
CPLAT_EXPORT BOOL CPLAT_API DeleteFileU(const char *lpFileName);
CPLAT_EXPORT BOOL CPLAT_API CreateDirectoryU(const char *lpPathName, LPSECURITY_ATTRIBUTES lpSecurityAttributes);
```

```c
/* 案 C: この app で UTF-8 から wchar_t へ変換して W 版を呼ぶ */
wchar_t wpath[MAX_PATH];
/* MultiByteToWideChar(CP_UTF8, ...) で変換 */
DeleteFileW(wpath);
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) cplat の既存の `cplat_stat`、`cplat_mkdir`、`cplat_remove` を使う。Linux のディレクトリ作成は `mkdir(path, 0700)` のまま残す。
- [ ] B: cplat の `win32.h` に 3 つの UTF-8 版の関数を追加し、`mock_cplat` とテストも追加する。
- [ ] C: この app で UTF-8 から `wchar_t` へ変換し、`GetFileAttributesW`、`DeleteFileW`、`CreateDirectoryW` を直接呼ぶ。

**Answer**

- [ ] B: A に加え、`reserved` を要求番号として使い、要求と応答を 1 対 1 で照合する。プロトコルの版を 2 に上げる。
- [ ] C: 照合は追加しない ([Q-003](#q-003-持続接続で送受信に失敗した後の扱い) の対策だけとする)。

```c
rc = pos_ipc_client_call(client, ...);   /* 接続し直してから送信する (前の要求は再送しない) */
```

**Status**

**Question**

**Context**

- **経緯と背景**: [Q-005](#q-005-要求と応答の照合方法) で、互換性ではなくプロトコルの正確性を重視して再検討するよう指示を受けました。版を上げることを前提にします。
- **現状 (版 1、24 バイト)**: `magic` (4)、`version` (2)、`flags` (2)、`method_id` (4)、`status_code` (4)、`payload_size` (4)、`reserved` (4、0 固定)。応答の `method_id` を照合しておらず、要求番号はありません (`ipc_protocol.h`)。
- **照合の考え方**: クライアントは接続ごとに 1 から増える要求番号を要求に付け、サーバーは同じ値を応答に写します。クライアントは、応答の要求番号と `method_id` が送った要求と一致することを確かめます。
- **案 A (32 バイト)**: `magic` と `version` は、将来の版でも先頭の同じ位置に置きます。受信側は、版が異なることを常に判別できます。

```text
案 A: オフセット  0 magic (u32)  4 version (u16 = 2)  6 flags (u16)
                  8 request_id (u64)
                 16 method_id (u32)  20 status_code (i32)  24 payload_size (u32)  28 reserved (u32 = 0)
```

```text
案 B: 版 1 と同じ 24 バイトで、reserved (u32) を request_id として使う。version = 2。
```

```text
案 C: 案 A に header_size (u16) とヘッダーとペイロードの CRC32 (u32) を加え、36 バイト以上にする。
```

- **要求番号の幅**: 案 B の 32 ビットは、1 つの持続接続で約 43 億回の呼び出しで一巡します。一巡しても、照合は直前の要求との比較のため誤りにはなりませんが、要求番号を「接続内で一意」と定義できなくなります。
- **CRC の要否**: ローカルのストリーム (`AF_UNIX`、名前付きパイプ) では、カーネルがデータの欠落や破損を起こしません。CRC が検出できるのは実装の不具合だけで、その種類の不具合 (応答の取り違え、境界のずれ) は要求番号と長さの照合で検出できます。
- **header_size の要否**: ヘッダーの長さは版から一意に決まります。版が異なる場合は [Q-022](#q-022-不正なフレームを受信した場合の扱い) の手順で接続を閉じるため、長さの欄で読み飛ばす必要はありません。

**Answer**

- [ ] B: 24 バイトのまま、`reserved` を 32 ビットの要求番号として使い、版を 2 に上げる。
- [ ] C: 案 A に、ヘッダー長の欄とヘッダーとペイロードの CRC32 を加える。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: プロトコルの正確性と単純さを優先しました。変更量は基準にしていません。  
理由: 64 ビットの要求番号は接続内で一意と定義でき、照合の意味が明確になります。`magic` と `version` を固定の位置に置くことで、将来の版との不一致を常に検出できます。CRC とヘッダー長の欄は、ローカルのストリームでは検出できる誤りを増やさず、検証する欄だけが増えます。

### Q-022 不正なフレームを受信した場合の扱い

**Status**

未回答

**Question**

不正なフレームを受信した場合に、サーバーとクライアントはどう扱いますか。

**Context**

- **経緯と背景**: [Q-005](#q-005-要求と応答の照合方法) の再検討の一部です。現在のサーバーは、ヘッダーの検証に失敗すると応答せずに接続を閉じます。クライアントは `CPLAT_ERR_CORRUPT_DATA` または `CPLAT_ERR_VERSION_MISMATCH` を返しますが、接続を閉じないため、以後の受信がずれます (BL-003)。
- **検証する項目 (案によらず共通)**: `magic`、`version`、`flags` (要求は要求の、応答は応答のフラグだけ)、`reserved` が 0、`payload_size` が上限以内、要求の `status_code` が 0。クライアントは、応答の要求番号と `method_id` が送った要求と一致することも確かめます ([Q-021](#q-021-プロトコルの版-2-のヘッダー構成))。
- **境界の考え方**: ヘッダーの検証に失敗した時点で、以後のバイト列のどこがフレームの境界かは分かりません。そのため、いずれの案でも、検証に失敗した接続はそれ以上読まずに閉じます。応答のペイロードが呼び出し側のバッファーより大きいだけの場合は、フレームとして正しいため、読み捨てて `CPLAT_ERR_BUFFER_TOO_SMALL` を返し、接続は使い続けます。
- **案 A の版の不一致の扱い**: サーバーは、`magic` が正しく `version` だけが異なる要求に、自身の版で `CPLAT_ERR_VERSION_MISMATCH` の応答 (要求番号 0、ペイロードなし) を 1 つ返してから閉じます。クライアントは、`magic` が正しく版が異なる応答を受けたら `CPLAT_ERR_VERSION_MISMATCH` を返します。
- **案 B の扱い**: サーバーはどの不正でも応答せずに閉じます。クライアントには `CPLAT_ERR_EOF` として見えます。

```text
案 A: 版 1 のクライアント → 版 2 のサーバー: CPLAT_ERR_VERSION_MISMATCH (原因が分かる)
案 B: 版 1 のクライアント → 版 2 のサーバー: CPLAT_ERR_EOF (切断と区別できない)
```

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 検証に失敗した接続は、受信側がそれ以上読まずに閉じる。版だけが異なる場合は、サーバーが自身の版で `CPLAT_ERR_VERSION_MISMATCH` の応答を 1 つ返してから閉じる。クライアントは、版の不一致は `CPLAT_ERR_VERSION_MISMATCH`、それ以外の不正は `CPLAT_ERR_CORRUPT_DATA` を返して接続を閉じる。
- [ ] B: 検証に失敗した接続は、受信側がそれ以上読まずに閉じる。サーバーはどの不正でも応答しない。クライアントは不正の種類に応じた結果コードを返して接続を閉じる。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: プロトコルの正確性と、異常の原因を利用者が判別できることを優先しました。  
理由: 検証に失敗した接続を閉じることで、境界のずれが以後の呼び出しへ波及しなくなります。版の不一致は、将来 cplat へ統合して版が混在した場合に最も起きやすい不正で、`CPLAT_ERR_EOF` と区別できると原因をすぐに特定できます。`magic` と `version` を固定の位置に置く ([Q-021](#q-021-プロトコルの版-2-のヘッダー構成)) ことで、この応答は将来の版でも解釈できます。

**Status**

**Question**

`pos_ipc_call` と `pos_ipc_client_call` で、IPC 層の結果 (送受信の成否) と、サーバーの処理側の関数が返した結果を、区別して返しますか。

**Context**

```c
/* 案 A */
rc = pos_ipc_call(&ep, method, req, req_len, resp, cap, &len, &status, 1000, NULL);
if (rc != CPLAT_OK) { /* IPC の失敗 (接続、期限、不正なフレーム、未登録のメソッド) */ }
else if (status != CPLAT_OK) { /* 処理側が返した結果 */ }
```

```c
/* 案 B: 現在の形のまま、処理側が返してはならない結果コードを公開ヘッダーに明記する */
rc = pos_ipc_call(&ep, method, req, req_len, resp, cap, &len, 1000, NULL);
```

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 戻り値は IPC 層の結果だけとし、処理側の結果は新しい引数 `status_out` に格納する。サーバーの IPC 層の判定は、応答の `flags` の専用のビットで区別する。
- [ ] B: 現在の形のまま 1 つの戻り値で返し、処理側が返してはならない結果コード (`CPLAT_ERR_TIMEOUT`、`CPLAT_ERR_EOF`、`CPLAT_ERR_BUFFER_TOO_SMALL` など) を公開ヘッダーに明記する。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

**Recommendation**

**Question**

**Context**

- **経緯と背景**: [Q-010](#q-010-同じ宛先のサーバーの二重起動を防ぐ方式) で、できれば両 OS でファイルを生成したくないとの補足を受け、ファイルを作らない排他の方式を精査しました。
- **現状**: ソケットは `$XDG_RUNTIME_DIR/<ns>/<inst>/<target>.sock`、または `/tmp/pos-u<uid>/<ns>/<inst>/<target>.sock` に作ります。ディレクトリの作成、残ったソケットの確認と削除、`bind` 後の `chmod`、閉じる際の `unlink` があり、BL-008 (代替配置先の所有者)、BL-010 (確認と削除の競合) の原因になっています。閉じる際の `unlink` は、別のサーバーが置き換えた後のソケットを消すおそれもあります。
- **抽象名前空間**: `sun_path[0]` を NUL にしたアドレスは、ファイル システムと関係しません。最後の参照を閉じると名前は自動で消えます。同じ名前の `bind` は `EADDRINUSE` で失敗します。ソケットの権限は意味を持ちません ([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html))。scratchpad の試験プログラムで、WSL2 のカーネル 6.6 で次を確認しました。

```text
1 つ目の bind: 成功 / 2 つ目の bind: EADDRINUSE / 閉じた後の bind: 成功
サーバーが SO_PEERCRED で見たクライアントの uid: 1000 / クライアントが見たサーバーの uid: 1000
```

- **案 A の形**: 名前は `pos-u<euid>-<ns>-<inst>-<target>` (USER スコープ) とします。CUSTOM スコープは、Windows の名前付きパイプと同じく `custom_dir` のハッシュを使い、`pos-c-<FNV-1a 64 ビット>-<ns>-<target>` とします。ファイルの権限が効かないため、サーバーは受け付けた接続の `SO_PEERCRED` の uid が自身の実効 uid と一致しない場合に閉じます。クライアントも接続先の uid を確かめ、一致しない場合は `CPLAT_ERR_PERMISSION_DENIED` を返します。
- **案 A で起きなくなること**: ディレクトリの作成と検証 (BL-008、[Q-011](#q-011-代替配置先の検証に失敗した場合の扱い))、残ったソケットの確認と削除 (BL-010)、`chmod` までの間の権限、閉じる際の `unlink` の競合。排他は `bind` の 1 回の操作で決まります。
- **案 A の制約**:
    - 抽象名前空間は、ネットワーク名前空間ごとに分かれます。ネットワーク名前空間が異なるコンテナーとは通信できません (ファイルのソケットは、ディレクトリを共有すれば通信できます)。
    - 他のユーザーが先に同じ名前を `bind` すると、サーバーは `CPLAT_ERR_BUSY` で起動できません。`SO_PEERCRED` の確認により、要求の内容が他のユーザーに渡ることはありません。`$XDG_RUNTIME_DIR` のファイルのソケットでは、この妨害は起きません。
    - `SYSTEM` スコープ (BL-001) の権限は、ファイルの権限ではなく `SO_PEERCRED` の uid と gid で判定することになります。Windows の名前付きパイプの DACL と同じく、OS の識別子で接続を判定する形です。
- **案 B の形**: 現在のファイルのソケットのまま、ロック ファイル (`flock`) で排他し ([Q-010](#q-010-同じ宛先のサーバーの二重起動を防ぐ方式) の回答)、代替配置先を検証します ([Q-011](#q-011-代替配置先の検証に失敗した場合の扱い) の回答)。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 抽象名前空間のアドレスにする。サーバーとクライアントは `SO_PEERCRED` で相手の uid が自身の実効 uid と一致することを確かめる。ディレクトリとファイルは作らない。
- [ ] B: ファイルのソケットのまま、ロック ファイルで排他し、代替配置先のディレクトリを検証する ([Q-010](#q-010-同じ宛先のサーバーの二重起動を防ぐ方式) と [Q-011](#q-011-代替配置先の検証に失敗した場合の扱い) の回答のまま)。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 不具合が構造的に起きない設計と、ファイルを作らないこと (ユーザーの補足) を優先しました。  
理由: 案 A では、BL-008 と Linux の BL-010 の原因になっている処理自体がなくなります。排他は `bind` の原子的な結果で決まり、異常終了の後に残る物もありません。接続の判定は `SO_PEERCRED` で行い、Windows の名前付きパイプ ([Q-026](#q-026-windows-の既定のバックエンド)) と同じく、名前空間の名前と OS の識別子による判定という等価な形になります。ネットワーク名前空間の制約と名前の先取りによる起動の妨害は残るため、許容できるかの判断をお願いします。

```c
GetFileInformationByHandleEx(h, FileAttributeTagInfo, &tag, sizeof(tag));   /* ReparseTag を確認する */
```

- **案 C の形**: cplat に、ソケットのファイルの確認と削除を行う両 OS 共通の関数を追加します。[Q-025](#q-025-linux-の-af_unix-のアドレス方式) で抽象名前空間を選ぶと、Linux 側の用途がなくなります。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) cplat の既存の `cplat_makedirs` と `CreateFileU` を使い、ソケットの確認と削除は同じハンドルで行う。cplat は変更しない。
- [ ] B: cplat の `win32.h` に `GetFileAttributesU`、`DeleteFileU`、`CreateDirectoryU` を追加し、`mock_cplat` とテストも追加する。
- [ ] C: cplat に、ソケットのファイルの確認と削除を行う両 OS 共通の関数を追加し、`mock_cplat` とテストも追加する。

### Q-030 名前付きパイプのクライアントがサーバーの作成ユーザーを確かめるか

**Status**

未回答

**Question**

名前付きパイプのクライアントが、接続先のサーバーのプロセスが自身と同じユーザーであることを確かめますか。

**Context**

- **経緯と背景**: [Q-012](#q-012-名前付きパイプに接続を許可するアカウント) で、サーバー側の DACL を作成ユーザーと LocalSystem に限定することに決まりました。これはクライアントの接続を制限するもので、サーバーの正しさは確かめません。
- **残る問題**: パイプ名は規則から推測できます。他のユーザーが先に同じ名前のパイプを作ると、正しいサーバーは `FILE_FLAG_FIRST_PIPE_INSTANCE` で起動に失敗し、クライアントは他のユーザーのサーバーへ接続します。偽装レベルの制限 (`SECURITY_IDENTIFICATION`) により、クライアントの権限は使われませんが、要求の内容は渡り、偽の応答を受け取ります。
- **Linux との対応**: [Q-025](#q-025-linux-の-af_unix-のアドレス方式) の案 A では、クライアントが `SO_PEERCRED` で接続先の uid を確かめます。
- **案 A の形**: 接続後に `GetNamedPipeServerProcessId` でサーバーのプロセス ID を取得し、そのプロセスのトークンのユーザーの SID が自身と一致しない場合は、接続を閉じて `CPLAT_ERR_PERMISSION_DENIED` を返します。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 確かめる。接続後にサーバーのプロセスのユーザーの SID を照合し、一致しなければ `CPLAT_ERR_PERMISSION_DENIED` を返す。
- [ ] B: 確かめない (サーバー側の DACL と偽装レベルの制限だけとする)。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 両 OS で等価な保護と、公開ヘッダーの「作成ユーザーのみ」の意図を、接続の両方向で満たすことを優先しました。  
理由: サーバーの DACL だけでは、名前を先に取得した他のユーザーのサーバーへ要求が渡ることを防げません。案 A は Linux の `SO_PEERCRED` による確認と同じ保護を Windows に与えます。照合の処理はクライアントの接続時の 1 回だけで、通常の呼び出しの性能には影響しません。
