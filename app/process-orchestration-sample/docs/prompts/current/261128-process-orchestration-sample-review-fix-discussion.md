### Q-002 Windows のファイル操作の置き換え方法

**Status**

未回答

**Question**

BL-018 で、cplat に存在しない `GetFileAttributesU`、`DeleteFileU`、`CreateDirectoryU` を、どの方法で置き換えますか。

**Context**

- **経緯と背景**: この 3 つの関数は `cplat/win32/win32.h` に定義されておらず、Windows のリンクで失敗します。使用箇所は、ディレクトリの作成 (`ipc_endpoint.c` の `create_single_dir`)、ソケット ファイルの存在確認と削除 (`ipc_transport_unix_windows.c`) です。
- **根拠資料**: cplat には、両 OS で使える UTF-8 のファイル操作がすでにあります。
    - `cplat_stat` (`cplat/crt/sys/stat.h`): Windows では `_wstat64` を使います。
    - `cplat_mkdir` (`cplat/crt/sys/stat.h`): Linux では権限 `0755` (umask 適用) で作成し、Windows では権限を指定しません。
    - `cplat_remove` (`cplat/crt/stdio.h`): ファイルを削除します。
- **Linux の権限の注意**: `cplat_mkdir` は Linux で `0755` を使うため、ソケットの親ディレクトリに必要な `0700` を満たしません。Linux では現在の `mkdir(path, 0700)` を残す必要があります。

```c
/* 案 A: cplat の既存の関数を使う (Windows の分岐) */
rc = cplat_mkdir(path, detail_out);
/* 失敗した場合は cplat_stat で既存のディレクトリかどうかを確認する */
```

```c
/* 案 B: cplat/win32/win32.h に UTF-8 版を追加する */
CPLAT_EXPORT DWORD CPLAT_API GetFileAttributesU(const char *lpFileName);
CPLAT_EXPORT BOOL CPLAT_API DeleteFileU(const char *lpFileName);
CPLAT_EXPORT BOOL CPLAT_API CreateDirectoryU(const char *lpPathName, LPSECURITY_ATTRIBUTES lpSecurityAttributes);
```

```c
/* 案 C: この app で UTF-8 から wchar_t へ変換して W 版を呼ぶ */
wchar_t wpath[MAX_PATH];
/* MultiByteToWideChar(CP_UTF8, ...) で変換 */
DeleteFileW(wpath);
```

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) cplat の既存の `cplat_stat`、`cplat_mkdir`、`cplat_remove` を使う。Linux のディレクトリ作成は `mkdir(path, 0700)` のまま残す。
- [ ] B: cplat の `win32.h` に 3 つの UTF-8 版の関数を追加し、`mock_cplat` とテストも追加する。
- [ ] C: この app で UTF-8 から `wchar_t` へ変換し、`GetFileAttributesW`、`DeleteFileW`、`CreateDirectoryW` を直接呼ぶ。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 既存の共通処理の再利用と、影響するサブモジュールの最小化を優先しました。  
理由: A は cplat を変更せず、両 OS で共通の関数を使えます。B は cplat に API を追加するため、`mock_cplat`、テスト、機能仕様の更新が必要になり、cplat のサブモジュールへの変更も生じます。C は UTF-8 の変換処理を app 内に重複して持つことになり、cplat への統合時に置き換えが必要です。

### Q-003 持続接続で送受信に失敗した後の扱い

**Status**

未回答

**Question**

BL-003 で、持続接続 (`pos_ipc_client`) の送受信が途中で失敗した後、その接続をどう扱いますか。

**Context**

- **経緯と背景**: 現在は、タイムアウトなどで失敗しても接続をそのまま使い続けるため、次の呼び出しが前の要求の応答を受け取ります。
- **根拠資料**: 公開ヘッダー `ipc.h` の `pos_ipc_client_call` の説明は、相手側の切断を検出した場合に「暗黙の再接続を行わず、`CPLAT_ERR_EOF` 等のエラーを返します」としています。

```c
/* 案 A: 破損状態にして以後はエラーを返す */
rc = pos_ipc_client_call(client, ...);   /* CPLAT_ERR_TIMEOUT */
rc = pos_ipc_client_call(client, ...);   /* 送信せずにエラー。呼び出し側が close して open し直す */
```

```c
/* 案 B: 次の呼び出しで自動的に接続し直す */
rc = pos_ipc_client_call(client, ...);   /* CPLAT_ERR_TIMEOUT */
rc = pos_ipc_client_call(client, ...);   /* 内部で接続し直してから送信する */
```

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 失敗した接続を破損状態にし、以後の呼び出しは送信せずにエラーを返す。接続し直すのは呼び出し側とする。
- [ ] B: 失敗した接続を閉じ、次の呼び出しで自動的に接続し直す。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 公開ヘッダーの既存の契約 (暗黙の再接続を行わない) との一貫性を優先しました。  
理由: B は、要求が相手に届いて処理されたかどうかが分からないまま再送する余地を作ります。停止要求のように副作用のある要求では、二重に実行される危険があります。A は現在の契約と同じ考え方で、呼び出し側が状況に応じて判断できます。

- [ ] B: `CPLAT_ERR_CORRUPT_DATA` を返す。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 呼び出し側の処理の単純さと、既存の説明との一貫性を優先しました。  
理由: 相手側の切断ですでに `CPLAT_ERR_EOF` を返すため、呼び出し側は「`CPLAT_ERR_EOF` なら開き直す」という 1 つの規則で扱えます。`CPLAT_ERR_CORRUPT_DATA` は、受信したデータの形式の誤りにも使っており、区別しにくくなります。

### Q-005 要求と応答の照合方法

**Status**

未回答

**Question**

BL-003 で、受信した応答が送った要求に対応することを、どの方法で確認しますか。

**Context**

- **経緯と背景**: 現在のクライアントは、応答ヘッダーの `method_id` を確認していません。[Q-003](#q-003-持続接続で送受信に失敗した後の扱い) で失敗後の接続を使わない方針にすれば、要求と応答のずれは通常は起きません。照合は、サーバーの不具合などに備えた二重の確認になります。
- **根拠資料**: フレーム ヘッダー (`ipc_protocol.h`) には 4 バイトの `reserved` 領域があり、現在は 0 固定です。サーバーは応答に `reserved = 0` を書きます。
- **案 B の影響**: `reserved` を要求番号に使うと、サーバーは要求の `reserved` を応答へ写す必要があります。古い版のサーバーは 0 を返すため、新旧を混在させると照合に失敗します。プロトコルの版 (`POS_IPC_FRAME_VERSION`) を上げるかどうかも合わせて決める必要があります。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 応答ヘッダーの `method_id` が要求と一致することを確認する。一致しない場合は接続を破損状態にする。プロトコルは変更しない。
- [ ] B: A に加え、`reserved` を要求番号として使い、要求と応答を 1 対 1 で照合する。プロトコルの版を 2 に上げる。
- [ ] C: 照合は追加しない ([Q-003](#q-003-持続接続で送受信に失敗した後の扱い) の対策だけとする)。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: プロトコルの互換性の維持と、変更量の抑制を優先しました。  
理由: 失敗後の接続を使わなければ、要求と応答のずれは起きません。A は数行の追加で、サーバーの不具合による取り違えも検出できます。B は同じ持続接続で複数の要求を同時に送る (パイプライン化) 場合に必要になりますが、現在の設計は 1 接続 1 要求を直列化しているため不要です。

- [ ] B: `timeout_ms` 引数を削除し、期限なしで待つことを契約にする。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
優先した基準: 公開ヘッダーの既存の契約の維持を優先しました。  
理由: 公開ヘッダーはすでに `timeout_ms` を「停止待機タイムアウト」と説明しており、A は説明に実装を合わせる修正です。cplat に期限付きの join があるため、実装も局所的です。

### Q-008 起動中または停止中の子への操作の扱い

**Question**

**Context**

- **経緯と背景**: 現在の `child-start` は、`STARTING` と `STOPPING` の子に対して `CPLAT_ERR_BUSY` を返します。`child-stop` は、`STARTING` の子を `STOPPED` に書き換えて成功を返すため、停止したはずの子が動き続けます。
- **案 B の振る舞い**: 状態の変化を条件変数で待ちます。起動の完了まで最大 5 秒 (`POS_PARENT_CHILD_START_TIMEOUT_MS`) かかるため、その間 IPC のワーカー スレッドを 1 本占有します。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) `child-start` と同じく、`child-stop` も `STARTING` と `STOPPING` の子に対して `CPLAT_ERR_BUSY` を返す。呼び出し側が再試行する。
- [ ] B: 起動または停止の完了を待ってから、要求された操作を行う。

選択方式: 単一選択

- [ ] B: 作成ユーザーだけに許可する。
- [ ] C: 作成ユーザー、LocalSystem、Administrators グループに許可する。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

**Recommendation**

理由: LocalSystem は OS 自体の権限で、許可から外しても保護にはなりません。Administrators を許可すると、同じ端末の別の管理者ユーザーからも接続できるため、「作成ユーザーのみ」の説明から外れます。
