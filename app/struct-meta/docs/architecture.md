# struct-meta のアーキテクチャー

## 目的

`struct-meta` は、構造体レイアウトの表現と、その表現を使う操作を分離します。  
将来 `cplat` へ移しやすいように、再利用可能な機能を 1 個の共有ライブラリ `libstruct_meta` にまとめ、サンプルと生成コマンドを分離します。

## メタデータの取得経路

記述子を得る経路は 2 系統あります。どちらも同じカタログ ハンドル (`struct_meta_catalog`) になるため、利用側のコードは経路を意識しません。

| 経路 | 記述子の作り方 | レイアウトを決めるもの | コンパイラ |
|---|---|---|---|
| 事前組み込み型 | `struct-meta-gen` が生成した C ソースを実行体へ組み込む | 生成コードの `offsetof` と `sizeof` を解くコンパイラ | ビルド時に必要 |
| 事後解析型 | 実行時に C ヘッダーを構文解析して組み立てる | `layout` の ABI 規則 | 不要 |

構文解析はもともとコンパイラに依存していません。事前組み込み型でコンパイラが要るのは、レイアウトの決定を委ねているからです。  
`layout` がレイアウトを求められるようになったことで、実行時にヘッダーを読んで記述子を組み立てられます。

両者がずれないよう、`layout` を唯一の計算主体とし、生成コードへ `_Static_assert` を出力してコンパイラの実レイアウトと照合します。  
詳細は [レイアウトの計算と照合](#レイアウトの計算と照合) を参照してください。

事後解析型は、実行中のプログラムが静的に知らない構造体を扱うための経路です。  
外部仕様のバイナリ レコードのように、型がビルド時に確定しない対象へ使用します。  
静的に既知の型へ適用する場合は、利用側で `descriptor->size` と `sizeof` の一致を確認してください。

## 依存方向

```text
layout (ABI 規則)      parse (構文解析 + AST)
        ↘                    ↙
          catalog (記述子の構築 + 索引 + 寿命)
                      ↓
              meta (記述子 + 索引)
                      ↓
                   access
                 ↙   ↓   ↘
              json patch print
                ↓
            json/file

struct-meta-gen    --> catalog (事後解析型と同じ入口) --生成--> C ソース
struct-meta-sample --> catalog (両経路) + json/file + patch + print
```

`layout` と `parse` は他のカテゴリへ依存しません。`catalog` が両者と `meta` を使って記述子を組み立てます。  
`meta` が他カテゴリへ依存しないという規則は変わりません。`catalog` が上位から `meta` を使います。

`meta` は記述子、フィールド種別、汎用属性、再帰検査、記述子の索引を提供します。  
索引を独立したカテゴリにせず `meta` へ含めるのは、記述子の検査そのものが索引を参照するためです。  
索引を別カテゴリにすると `meta` が他カテゴリへ依存し、依存方向の規則に反します。  
`access` はフィールド検索、属性検索、配列要素、パスの解決を提供し、構造体へのポインター演算を集約します。  
パスは `scores`、`scores[1]`、`addresses[0].city` の形式を扱い、空文字列や途中で配列インデックスを省略した曖昧なパスを拒否します。  
`json`、`patch`、`print` はアクセス機能を利用し、メタデータのレイアウトを独自に解釈しません。

`patch` は、ルートからメニューを辿る編集と、`access` が解決したパスから始める編集を提供します。  
パスが配列全体で終わる場合は要素選択へ、構造体で終わる場合はその構造体のフィールド選択へ進みます。  
どちらの編集方法でも、メニューは現在位置と選択候補の完全な C フィールド パスを表示します。

## フィールドの型モデル

フィールドの種別 (`struct_meta_field_kind`) は、整数について符号の有無だけを表します。  
幅は `struct_meta_field` の `element_size` が表します。  
`int`、`long long`、`int32_t` のように C の型名ごとに種別を増やすと、対応する型が増えるたびに列挙が伸びるためです。

整数の `element_size` は 1、2、4、8 のいずれかです。  
それ以外の幅は記述子の検査で拒否します。

幅ごとの読み書きは `struct_meta_internal_integer_*` に集約します。  
JSON 変換、表示、対話編集はいずれもこの関数を経由し、各所で幅の分岐を繰り返しません。  
書き込みでは対象の幅に収まらない値を `CPLAT_ERR_OUT_OF_RANGE` として拒否し、黙って切り詰めません。

## 記述子と属性

公開 API の入口は、利用前に `struct_meta_descriptor_validate()` で記述子全体を再帰検査します。  
検査対象には、フィールド範囲、型ごとの制約、ネスト記述子との要素サイズ一致、属性キーの妥当性と重複、記述子の循環が含まれます。

属性は構造体またはフィールドに付与できる key/value の配列です。  
JSON 変換は `json.name`、`json.ignore`、`json.required` を解釈します。  
`meta` はフィールドの共通解釈に使用する `meta.kind` と `meta.format` を解釈します。  
属性モデル自体は個別機能に依存しないため、別カテゴリが独自の名前空間を追加できます。

### 文字列とバイト配列

`char[N]` は既定で NUL 終端文字列として扱います。  
`signed char[N]`、`unsigned char[N]`、`int8_t[N]`、`uint8_t[N]` はバイト配列として扱います。  
`char[N]` に `@struct_meta{meta.kind=bytes}` を付けた場合は、符号付きバイト配列として扱います。

配列でない `char`、`signed char`、`int8_t` は符号付き 1 バイト整数です。  
配列でない `unsigned char`、`uint8_t` は符号なし 1 バイト整数です。  
生成コードは、対象環境の plain `char` が 8 ビットの符号付き整数であり、`int8_t` と同じ範囲であることをコンパイル時に検査します。

バイト配列の既定表現は、宣言型の符号に従う整数配列です。  
`@struct_meta{meta.format=hex}` を付けると、JSON、テキスト表示、対話編集で空白区切りの 16 進文字列を使用します。  
出力は小文字 2 桁を半角空白 1 個で区切る `00 a5 ff` 形式です。  
入力は大文字と小文字、および要素間の 1 個以上の半角空白を許容します。  
先頭と末尾の空白、`0x` 接頭辞、2 桁でない要素、記述子の要素数と一致しない入力は拒否します。  
対話編集で配列全体を指定した場合は 16 進文字列を使用し、インデックス付きパスを指定した場合は宣言型に従う 10 進整数を使用します。

`meta.kind` の値は `bytes`、`meta.format` の値は `hex` だけを定義します。  
未知の値、スカラーへの `meta.kind=bytes`、バイト配列以外への `meta.format=hex` は不正な記述子として拒否します。

### Doxygen 属性の書式

Doxygen コメントには、値を持たない `@struct_meta{key}` または値を持つ `@struct_meta{key=value}` を記載します。  
属性名には英数字、`.`、`_`、`-` を使用できます。  
属性値は `=` の後ろから `}` までの 1 行の文字列であり、前後の空白は除去します。  
空の属性名、空の属性値、改行または波括弧を含む属性値、閉じ波括弧が無い記述は生成エラーです。  
同一の構造体またはフィールドに同じ属性名を複数回記載した場合も、生成エラーです。

```c
/**
 * @brief 利用者情報です。
 * @struct_meta{schema.version=1}
 */
typedef struct person
{
    int id;     /**< 識別子です。 @struct_meta{json.name=person_id} @struct_meta{json.required} */
    int serial; /**< 内部連番です。 @struct_meta{json.ignore} */
} person;
```

## 解析器の境界

`parse` は flex/bison を使う限定的な C ヘッダー解析器です。  
`typedef struct { ... } name;`、対応済みプリミティブ型、同じヘッダー内のネスト構造体、固定長配列を扱います。  
プリプロセッサ展開、任意の宣言子、ビット フィールド、ポインター、可変長配列を含む完全な C 文法は対象外です。

解析器はライブラリの一部であり、事前組み込み型と事後解析型の両方が同じ実装を使います。  
ライブラリとして同一プロセスで繰り返し呼べるよう、flex の `reentrant` と bison の `api.pure` を用い、状態をグローバル変数へ置きません。  
異常時にプロセスを終了させず、`struct_meta_diagnostic` へ原因と行番号を書いて結果コードを返します。  
記録するのは最初の 1 件だけです。後続の診断は最初の診断の波及であることが多いためです。

### 対応する型

| 記述 | 扱い |
|---|---|
| `int`、`unsigned int` | 受理します。 |
| `float`、`double` | 受理します。 |
| `char` | スカラーでは符号付き 1 バイト整数、配列では NUL 終端文字列として受理します。`meta.kind=bytes` を付けた配列は符号付きバイト配列です。 |
| `signed char`、`unsigned char` | スカラーでは 1 バイト整数、配列ではバイト配列として受理します。 |
| `short`、`unsigned short` | 受理します。LP64 と LLP64 のどちらでも 2 バイトです。`short int` などの綴りも受理します。 |
| `long long`、`unsigned long long` | 受理します。x86_64 の LP64 と LLP64 のどちらでも 8 バイトです。 |
| `int8_t` から `uint64_t` の固定幅型 | 受理します。コーディング規範が幅に意味のある値へ推奨する型です。 |
| 同じヘッダー内の `typedef struct` 名 | ネスト構造体として受理します。 |
| `long`、`unsigned long` | 拒否します。LP64 で 8 バイト、LLP64 で 4 バイトとなり、後述の互換性の契約を壊します。 |
| ポインター メンバー | 拒否します。 |

型名と種別・大きさ・アラインメントの対応は `struct_meta_internal_layout_find_type()` の表を正本とします。  
対応する型を増やすときは、LP64 と LLP64 で幅が一致することを必ず確認してください。

`size_t` は長さ明示型ではないため対象外です。  
`_Bool` は未対応です。字句解析器のキーワードに無いため、構造体型名と解釈されて後段で失敗します。

Doxygen の汎用属性の構文解析は `parse` の責務です。  
`catalog` はフィールド種別を決めるため、`meta.kind` と `meta.format` の妥当性だけを解釈します。  
`meta` は手作業で構築した記述子を含め、同じ属性契約を検査します。  
その他の属性名の意味は `parse` と `catalog` と `meta` では解釈しません。  
JSON 実装だけが `json.name`、`json.ignore`、`json.required` を解釈します。

## レイアウトの計算と照合

`layout` は、対応する型の大きさとアラインメント、および構造体の配置規則を持ちます。  
規則は x86_64 の System V AMD64 ABI と Windows x64 で一致するものだけです。

- メンバーは、現在のオフセットをそのメンバーのアラインメントへ切り上げた位置に置きます。
- 配列のアラインメントは要素のアラインメントと同じ、大きさは要素の大きさ × 要素数です。
- 構造体のアラインメントは最大メンバー アラインメント、大きさは末尾をそのアラインメントへ切り上げた値です。
- 表に載せた型では、アラインメントが大きさと一致します。`double` を 4 バイト境界へ置く 32 ビット x86 Linux は契約の対象外です。

事後解析型は、この計算値をそのまま記述子へ入れます。  
事前組み込み型は、記述子の初期化子に `offsetof` と `sizeof` を出力し、レイアウトの決定を実際のコンパイラへ委ねます。  
あわせて、計算値と一致することを検査する `_Static_assert` を出力します。

```c
static const struct_meta_descriptor g_address_desc = { "address", sizeof(address), g_address_fields, 2, ... };

/* レイアウト エンジンの計算値と、コンパイラが決めた配置との照合。 */
_Static_assert(sizeof(address) == 36, "address: レイアウト エンジンの計算値と一致しません");
_Static_assert(offsetof(address, city) == 0, "address.city: レイアウト エンジンの計算値と一致しません");
_Static_assert(offsetof(address, zip) == 32, "address.zip: レイアウト エンジンの計算値と一致しません");
```

これにより、事後解析型の正しさが、事前組み込み型のビルドのたびに検証されます。  
`layout` の表や規則を変えて実際のコンパイラとずれた場合、生成コードのコンパイル時に落ちます。

生成器が型のスペリングを扱わないのは、この構成の副産物です。  
要素 1 個の大きさも `sizeof(((person *)0)->scores[0])` の形でフィールドから求めるため、生成器の入力は記述子だけで足ります。  
型名と種別の対応表は `layout` の 1 箇所だけが持ちます。

## 記述子の寿命

事後解析型で組み立てた記述子、フィールド配列、属性配列、文字列は互いを指し合い、寿命が完全に一致します。  
個別に解放すると解放漏れと二重解放の余地が生まれるため、1 個のアリーナから確保し、`struct_meta_catalog_destroy()` でまとめて返します。

事前組み込み型のカタログは静的領域を指すため、破棄しても記述子は解放しません。  
どちらの場合も、破棄時に登録済みの記述子を索引から登録解除します。

## 検索の索引

名前による検索は、既定では線形走査です。  
型数やフィールド数が増えたときに備え、`cplat` のハッシュ テーブルを使った索引を用意しています。

索引は明示登録制です。  
`struct_meta_index_register()` で登録した記述子だけが対象になります。  
記述子ポインターを鍵にするため、暗黙に控えると、自動変数として組み立てた記述子でアドレスが再利用されたときに別の記述子へ誤って一致します。

登録した記述子では次の 2 点が変わります。

- `struct_meta_descriptor_validate()` が、登録時に求めた検査結果を返します。公開入口が呼ばれるたびに記述子全体を再帰走査し直す費用がなくなります。
- `struct_meta_descriptor_find_field()` とパス解決のフィールド名検索が、表引きになります。

未登録の記述子は従来どおり線形走査で扱います。  
これは失敗時の縮退ではなく、索引を使わない正規の経路です。  
一方、登録処理そのものが失敗した場合はエラー コードを返し、索引の無い状態を黙って作りません。

登録できるのは、寿命が登録期間より長く、内容が変化しない記述子だけです。  
自動変数として組み立てた記述子は、スコープを抜ける前に `struct_meta_index_unregister()` してください。

### スレッド安全性の契約

`cplat` のハッシュ テーブルは内部にロックを持ちません。  
読み取り同士は同一テーブルでも安全ですが、書き込みとの同時実行はできません。  
そこで同じ契約を採ります。

> 登録と登録解除は利用側で直列化し、検索と同時に実行しないでください。
> 通常は初期化時に登録を済ませてください。

### 規模による損得

ハッシュ テーブルの 1 件あたりの費用は数百ナノ秒の水準です。  
フィールド数や型数が少ない間は、線形走査の方が速くなります。  
件数によるしきい値での出し分けは導入していません。  
必要になった時点で、この節の判断を見直してください。

## 生成カタログの索引

生成カタログの型名テーブルは、レコード数もキーの最大長も生成時に確定し、成果物は読み取り専用です。  
そこで実行時に構築せず、`struct-meta-gen` が構築したテーブルの永続化イメージを生成コードへ埋め込み、実行時は `cplat_hashtable_attach()` で接続するだけにします。  
挿入の繰り返しが排除され、残る費用は 1 回の接続とハンドル 1 個の確保だけになります。

この方式が成り立つ根拠は次のとおりです。

- `cplat_hashtable_attach()` は領域へ書き込みません。ヘッダーを参照して検査し、ハンドルを確保して、渡されたアドレスを保持するだけです。したがってイメージを読み取り専用領域に配置できます。
- `gen/` は毎ビルド再生成され、Git 管理しません。イメージを作った `libcplat` と、それを読む実行体がリンクする `libcplat` は必ず同一です。配置の版番号に不整合が生じることはありません。

イメージは 8 バイト境界を要求されるため、`uint64_t` の配列として出力します。  
接続に失敗した場合は線形走査へ縮退させず、その場で異常終了します。  
同一ビルドで生成したイメージを読み込めないという不変条件の破綻であり、通知なく別の経路へ遷移すると原因を特定できなくなるためです。  
生成カタログには線形走査の経路自体がありません。

接続直後の `cplat_hashtable_validate()` は行いません。  
イメージは同一ビルド内の同一ライブラリが生成した固定バイト列であり、件数に比例する再検査は埋め込みの利点を損なうためです。

接続と索引への登録は `struct_meta_catalog_attach_static()` が行い、生成コードは呼び出すだけです。  
これにより、実行時に解析して作成したカタログとまったく同じハンドルになります。  
生成カタログは各記述子を `struct_meta_index_register()` へも登録します。  
このため生成コードのリンクには `libstruct_meta` が必要です。  
生成カタログの利用者は必ず `libstruct_meta` を使用するため、実際の制約にはなりません。

実行時に解析して作るカタログでは、件数もキーの最大長も解析を終えた時点で確定します。  
そこで自動拡張版ではなく、必要量を求めてから `cplat_hashtable_create()` を 1 回だけ呼び出します。

## プラットフォーム間互換性の契約

生成物は、x86_64 の Linux と Windows の間でバイト互換であることを契約とします。  
現時点で生成物をプラットフォーム間で流用してはいませんが、将来の流用に備えて契約として定め、契約を破る入力を解析器が拒否します。

x86_64 では LP64 と LLP64 の差は `long` だけです。  
`size_t` も `time_t` も 8 バイト、列挙型も 4 バイトで、どちらもリトル エンディアンであり、整列規則も同じです。  
`cplat` の永続化レイアウトは `uint32_t`、`uint64_t`、`size_t`、列挙型、`unsigned char`、`cplat_timespec` だけで構成され、`long` を使いません。

契約が成り立たなくなるのは次の場合です。

- 32 ビット対象、ビッグ エンディアン、整列規則の異なる ABI。
- MSVC で `_USE_32BIT_TIME_T` を定義した場合。`time_t` が 4 バイトになり `cplat_timespec` が崩れます。
- 解析対象ヘッダーが `long` または `unsigned long` のメンバーを含む場合。

守りは 3 層です。

1. 解析器が `long` と `unsigned long` を診断付きで拒否します。
2. 生成コードが `size_t`、`time_t`、`cplat_hashtable_config` の大きさを `_Static_assert` で検査します。生成器が動作した環境での実測値を埋め込むため、生成側と利用側で配置がずれればコンパイル時に落ちます。
3. 接続に失敗した場合は実行時に異常終了します。

## ビルド

`libstruct_meta` のソースは、責務ごとのサブディレクトリ (`layout`、`parse`、`catalog`、`meta`、`access`、`json`、`patch`、`print`) に置きます。  
各サブディレクトリは makefw のテンプレート `makefile` を持ち、コンパイルだけを行います。  
リンクはライブラリ ルートの `prod/libsrc/struct_meta/` で行い、`makechild.mk` の `NO_LINK = 1` が子階層のリンクを止めます。  
ルート直下にソースを置かないため、`makelocal.mk` で `MAKEFW_BUILD := 1` を明示します。

`SUBDIRS` は宣言しません。  
makefw が `makefile` を持つサブディレクトリを自動検出し、オブジェクトを再帰的に収集します。  
責務を増やすときは、サブディレクトリを作ってテンプレート `makefile` とソースを置くだけで済みます。  
`makepart.mk` の `ADD_SRCS` へ相対パスを列挙してはいけません。ライブラリ ルート直下へシンボリック リンクが作られ、Doxygen の重複読み込みとモジュール私有ヘッダーの探索失敗を招きます。

`.l` と `.y` は `prod/libsrc/struct_meta/parse/` に置きます。  
flex/bison の生成物はそのディレクトリの `gen/` に出るため、リンクを行うライブラリ ルートまでオブジェクトが届くよう、makefw の `bin/filter_existing_source_objs.sh` が `<サブディレクトリ>/gen/<ステム>.c` も生成元の根拠として認めます。  
あわせて `_flex_bison_compile.mk` が生成物を `.SECONDARY` に指定し、中間ファイルとして削除されないようにします。  
see: `framework/makefw/docs/subfolder-compilation.md`

解析対象ヘッダーは `struct-meta-sample/makepart.mk` の `STRUCT_META_GEN_HEADERS` で静的に宣言します。  
`struct-meta-gen` を先にビルドする必要があるため、`prod/src/cmd/makelocal.mk` が再帰 make の順序を明示します。  
flex/bison と `gen/*.c` の汎用コンパイル規則は makefw を利用し、ヘッダーからメタデータを作る規則はこの app 内に保持します。

Windows で WinFlexBison を使う場合は、`BISON=win_bison` と `FLEX=win_flex` を指定します。  
makefw は Windows で `FLEXFLAGS` の既定値を `--wincompat` とし、MSVC で利用できるコードを生成します。  
`.l` と `.y` の変換対象は `PLATFORM_*` で出し分けず、flex/bison をクロスプラットフォームな外部コマンドとして扱います。

生成ツール `struct-meta-gen` の実行ファイル名は、Linux の `struct-meta-gen` と Windows の `struct-meta-gen.exe` を `PLATFORM_*` で明示的に切り替えます。  
これにより、生成規則の前提条件と実際の Windows ビルド成果物を一致させます。

`struct-meta-gen` は `src` のビルド中に実行するため、`prod/makelocal.mk` は `default` と `build` のとき、`src` より先に `c-platform` と cJSON の実行時ライブラリを `prod/cbin` へ配置します。  
`struct-meta-gen` は解析とレイアウト計算を `libstruct_meta` へ委ねるため、自 app の実行時ライブラリも同じディレクトリへ配置します。  
これは `libsrc` の完了後に行います。  
`clean` ではコピーせず、配置済みの実行時ライブラリだけを削除します。  
Linux では共有ライブラリを、Windows では DLL を同じ bundle 定義から選択します。  
Linux で生成器を実行するレシピは、このディレクトリを一時的な `LD_LIBRARY_PATH` の先頭へ追加します。  
設定済みの `LD_LIBRARY_PATH` は後続要素として維持します。

## JSON デコードの更新単位

JSON デコードは従来どおり、検証済みのフィールドから順に出力先を更新します。  
後続フィールドでエラーが発生しても、先に更新したフィールドは元へ戻しません。  
呼び出し側が原子的な更新を必要とする場合は、一時領域へデコードして成功後に置き換えます。

## JSON で扱える整数の範囲

cJSON の整数拡張 API を使用し、`int64_t` と `uint64_t` の全域を正確な十進表記で扱います。  
エンコードでは整数を `double` へ変換せず、符号に対応する 64 ビット整数生成関数へ渡します。  
デコードでは、cJSON が保持する正確な整数表記を符号に対応する 64 ビット整数取得関数で読み出します。

JSON の数値に C の整数幅は含まれないため、取得した値をフィールドへ格納するときに `element_size` の範囲を検査します。  
小数、符号の不一致、または対象フィールドの幅に収まらない値は `CPLAT_ERR_OUT_OF_RANGE` として拒否します。
