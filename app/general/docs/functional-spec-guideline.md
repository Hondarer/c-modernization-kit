# 機能仕様の記載規範

## 概要

本書は、app の機能仕様に記載する内容、章立て、記載粒度、要件 ID と UUID の運用を定めます。  
対象は、各 app の `docs/functional-spec/` 配下の機能仕様です。

機能仕様は、app に割り当てられた要件を、API 設計、実装設計、実装、テストへ渡すための入力です。  
機能仕様より下流の成果物を根拠として、機能仕様を記載してはなりません。

要件 ID の接頭辞、参照コメントのタグ、カテゴリごとの主語は、app ごとに異なります。  
これらは、各 app の `docs/functional-spec-guideline.md` が定めます。本書では、この文書を app 固有規範と呼びます。

本文の構成と表現は、[日本語技術文書の文章規範](../../../framework/docsfw/docs/japanese-technical-writing-guideline.md) に従います。

## 機能仕様の役割

機能仕様は、利用側または上位設計から見た app の責務を定めます。  
app が提供する能力、外部から観測できる振る舞い、利用条件、保証範囲、適用範囲外を記載します。

機能仕様は、関数の一覧や実装の解説ではありません。  
関数の構成と契約、実装方式、検証方法は、機能仕様から導出する下流成果物が定めます。

## 記載する内容

機能仕様には、次の内容を記載します。

- app が解決する、利用側の課題
- app 自身が満たす機能、品質、互換性、方式の要件
- 入力の種類、処理の結果、状態の変化など、利用側から観測できる振る舞い
- Linux と Windows で利用側から観測できる結果が異なる場合の差異
- データ形式、文字モデル、通信形式など、相互運用性または安全性のために固定する条件
- 利用側が満たす前提と、app が保証する範囲の限界
- app が扱わない範囲と、app 内に代替機能がある場合の選択方法

外部標準または OS の仕様は、要件の条件や互換性を定義するために必要な場合だけ参照できます。  
参照する場合は、app が満たす内容を本文で明示し、外部文書だけに要件を委ねてはなりません。

## 記載しない内容

機能仕様には、次の内容を記載しません。

- app を利用するアプリケーションの業務要件、運用、配備、監視、教育
- 関数名、型名、定数名、関数の引数と戻り値
- 公開ヘッダー、ソース ファイル、実装ディレクトリの構成
- 使用する外部ライブラリ、依存する他の app、内部データ構造、内部アルゴリズム
- コーディング規則、API の命名規則、実装手順
- テスト ケース、テスト用の観測経路、検証コマンド
- API の移行表、使用例、チュートリアル

特定の方式を採用すること自体が相互運用性または安全性の要件である場合は、その方式を「制約」として記載できます。  
この場合も、方式を実現するライブラリや内部処理は記載しません。

未解決の実装不具合を、仕様として許容される振る舞いにしてはなりません。  
既知の事象によって保証できない範囲がある場合は、原因や実装状況ではなく、保証しない条件と利用側が選択できる代替機能を記載します。

## 文書の参照方向

機能仕様は、上位の要求、外部標準、同じ階層の機能仕様を参照できます。  
API 文書、実装文書、ソース、テストなど、機能仕様より下流の成果物は参照しません。

他の app の機能仕様は、責務の境界を説明する必要がある場合に参照できます。  
この場合も、参照先の要件を自身の app の要件として記載してはなりません。

下流成果物は、設計判断または検証対象の根拠を示す必要がある場合に、機能仕様の要件 ID と UUID を参照できます。  
参照は、API のまとまり、設計判断、代表的な検証項目など、要件との対応を説明する意味がある単位に限定します。  
すべての関数、ソース行、テストの確認文へ機械的に要件との対応を付与してはなりません。

下流成果物から参照する場合は、要件 ID と UUID を一組で記載します。  
媒体ごとの記法は、「下流成果物での参照記法」に従います。

機能仕様から下流成果物への逆参照は追加しません。

## 要件 ID と UUID

要件 ID は、次の形式とします。

```text
<PREFIX>-<CATEGORY>-<TYPE>-NNN
```

`<PREFIX>` は、app 固有規範が定める要件 ID の接頭辞です。  
`<CATEGORY>` は、機能仕様のファイル名に対応する大文字のカテゴリ名です。  
複数語からなるカテゴリは、ファイル名と同じく下線で語を区切ります (例: `STRING_CATALOG`)。  
区切りに `-` を使用すると、要件 ID の区切りと区別できなくなるため使用しません。  
`<TYPE>` は、要件の種別に対応する種別コードです。  
`NNN` はカテゴリと種別の組み合わせごとに `001` から始まる 3 桁以上の連番です。

例を次に示します。

```text
SAMPLE-EXAMPLE-FUNC-001
SAMPLE-EXAMPLE-QUAL-001
```

要件 ID は、人が要件のカテゴリ、種別、系列内の識別番号を読み取るために使用します。  
要件のカテゴリや種別の見直しによって、設計または製作中に変更される可能性があります。

各要件には、要件 ID とは別に UUID を 1 つ付与します。  
UUID は、小文字の 16 進数とハイフンによる UUIDv4 の標準表記とします。

```text
123e4567-e89b-42d3-a456-426614174000
```

UUID は、要件 ID が変更された場合も同じ論理要件を追跡するための永続識別子です。  
同じ論理要件である限り、要件文、種別、カテゴリ、連番を変更しても UUID を変更してはなりません。

要件 ID と UUID の対応の正本は、各機能仕様の「機能要件」に記載します。  
別の対応表は作成しません。

## 要件の種別

要件の種別と種別コードは、次の 4 種類です。

| 種別コード | 種別 | 対象 |
|---|---|---|
| `FUNC` | 機能 | app が提供する処理と、外部から観測できる結果 |
| `QUAL` | 品質 | 安全性、信頼性、性能、再現性など、処理の性質に対する保証 |
| `COMP` | 互換性 | プラットフォーム、保存形式、通信形式、ABI などの間で維持する性質 |
| `CONS` | 制約 | 下流設計が守る必要のある方式または選択範囲 |

利用側が守る条件は、app 自身が満たす要件ではありません。  
利用側の条件には要件 ID を付与せず、「前提と制約」に記載します。

## 要件の記述形式

要件は、次の表へ記載します。  
表の 2 列目の見出しは、app 固有規範が定めます。

| 要件 ID | sample の要件 |
|---|---|
| `SAMPLE-EXAMPLE-FUNC-001` <!-- sample-req: uuid=123e4567-e89b-42d3-a456-426614174000 --> | sample の例示機能は、指定された入力を処理し、結果を利用側へ返します。 |

UUID は、要件 ID の直後に 1 つの HTML コメントとして記載します。  
HTML コメントのタグは app 固有規範が定めます。  
HTML コメントは Markdown の表示には反映されませんが、要件 ID と UUID の対応を機械的に読み取れます。

1 行には、1 つの要件だけを記載します。  
複数の条件または結果が互いに独立して変更できる場合は、要件を分割します。

要件文では、要件 ID のカテゴリに対応する機能を主語とし、条件、処理、観測できる結果を明確にします。  
要件文を単独で引用した場合も責務の主体を特定できるように、主語は省略しません。  
`本 app は` や `本機能は` など、機能カテゴリを特定できない主語は使用しません。

カテゴリごとの主語は、app 固有規範の主語表に従います。

主語と同じ機能名を後続の文で繰り返さず、対象となる操作または状態を具体的に記載します。  
`対象`、`それ`、`同じ` などの指示語は、要件文の中だけで参照先を特定できる場合に限って使用します。

条件がある場合は、「〜の場合」の形で条件を先に示します。

「適切に」「安全に」「必要に応じて」など、要件を満たしているかを判断できない表現は使用しません。  
数量が契約に必要な場合は値を明示します。  
上位条件によって値が決定される場合は、具体値を実装から逆算せず、app が保証する範囲を記載します。

背景、理由、例外、利用側への注意は要件文へ含めず、対応する機能別の節で説明します。

## 下流成果物での参照記法

以降の例では、app 固有規範が定める参照コメントのタグを `<TAG>`、要件 ID の接頭辞を `<PREFIX>` と表記します。

Markdown では、表示する要件 ID の直後に、正本と同じ UUID を HTML コメントで記載します。

```markdown
要件: `<PREFIX>-EXAMPLE-FUNC-001` <!-- <TAG>: uuid=123e4567-e89b-42d3-a456-426614174000 -->
```

C の製品コードでは、通常のブロック コメントへ要件 ID と UUID を記載します。

```c
/* <TAG>: id=<PREFIX>-EXAMPLE-FUNC-001; uuid=123e4567-e89b-42d3-a456-426614174000 */
```

C++ の製品コードでは、行コメントへ要件 ID と UUID を記載できます。

```cpp
// <TAG>: id=<PREFIX>-EXAMPLE-FUNC-001; uuid=123e4567-e89b-42d3-a456-426614174000
```

公開宣言と対応付ける場合は、生成する API 文書へ要件情報を混入させないため、要件コメントを Doxygen コメントより前に配置します。  
複数の要件と対応する場合は、要件ごとにコメントを分離します。

テストでは、テスト項目の説明に続く `//` コメントへ要件 ID と UUID を記載します。  
説明コメント、要件コメント、テスト マクロの間に空行を挿入してはなりません。

```cpp
// 指定された入力に対して所定の結果を返すことを確認する。
// <TAG>: id=<PREFIX>-EXAMPLE-FUNC-001; uuid=123e4567-e89b-42d3-a456-426614174000
TEST(exampleTest, example_returns_expected_result)
{
    // Arrange
```

`TEST`、`TEST_F`、`TEST_P`、`TYPED_TEST` のすべてで同じ配置規則を使用します。  
要件コメントはテスト エビデンスの概要へ出力します。

要件コメントだけをテスト項目の説明にしてはなりません。  
テストの目的を示す説明を先に記載します。

1 つのテストが複数の要件と対応する場合は、説明の後続に要件コメントを要件ごとに記載します。  
個々の確認やアサーションへ同じ要件情報を重複して記載しません。

## 要件 ID と UUID の変更

新しい要件 ID は、カテゴリと種別の組み合わせにおいて、Git 履歴を含めて過去に使用した最大番号より大きい番号とします。  
廃止した要件 ID は再利用しません。

要件の種別またはカテゴリを変更する場合は、移動先の系列で新しい要件 ID を付与し、UUID を維持します。  
意味を保った表現修正、節の移動、要件の具体化でも UUID を維持します。

1 つの要件を複数に分割する場合、複数の要件を統合する場合、別の論理要件に置き換える場合は、既存の ID と UUID を廃止します。  
分割または統合後の各要件には、新しい ID と UUID を付与します。

## 各文書の構成

各機能仕様は、次の見出しで構成します。

1. 概要
2. 解決する課題
3. 機能要件
4. 機能別の振る舞い
5. 適用範囲外
6. 前提と制約
7. 選択の指針
8. 関連する機能仕様と外部仕様

「概要」「解決する課題」「機能要件」「適用範囲外」「前提と制約」は必須です。  
記載する内容が存在しない場合も見出しを残し、「該当する項目はありません」と記載します。

「機能別の振る舞い」は、機能のまとまりごとに具体的な見出しへ置き換えます。  
正常な振る舞い、代替結果、失敗時の振る舞い、状態変化、プラットフォーム差、保証範囲から、その機能の理解に必要な内容を記載します。

「選択の指針」と「関連する機能仕様と外部仕様」は、該当する内容がある場合だけ設けます。

## 文書の分割単位

1 つの文書は、利用側から見て 1 つの目的を持つ機能カテゴリを扱います。  
実装ディレクトリまたは公開ヘッダーの分割を、機能仕様の分割根拠にしてはなりません。

1 つのカテゴリに複数の操作がある場合でも、同じ課題と前提を共有する場合は 1 つの文書にまとめます。  
課題、利用条件、変更理由を独立して説明する必要がある場合は、別の機能カテゴリとして分割します。

## app 固有規範

app 固有規範は、各 app の `docs/functional-spec-guideline.md` に配置します。  
app 固有規範は本書を参照し、次の 2 つの表を所定の書式で定義します。  
この 2 つの表は、検査スクリプトが読み取る機械可読な契約です。

要件 ID の構成は、「要件 ID の構成」の見出しの直下に、次の書式で記載します。

```markdown
| 項目 | 値 |
|---|---|
| 要件 ID 接頭辞 | `SAMPLE` |
| 参照コメント タグ | `sample-req` |
| 機能要件表の見出し | `sample の要件` |
```

カテゴリごとの主語は、「カテゴリごとの主語」の見出しの直下に、次の書式で記載します。  
カテゴリは、`docs/functional-spec/` に配置する機能仕様のファイル名と一対一で対応させます。

```markdown
| カテゴリ | 主語 |
|---|---|
| `EXAMPLE` | sample の例示機能 |
```

app 固有規範には、この 2 つの表に加えて、機能仕様の変更後に実行する検査コマンドを記載します。  
app 固有の用語や、その app だけに適用する追加の記載規則がある場合も、app 固有規範に記載します。

`docs/functional-spec-guideline.md` と `docs/functional-spec/` の両方が配置されている app が、検査の対象になります。

## 変更時の扱い

機能の追加、削除、外部から観測できる振る舞いの変更は、対応する機能仕様に先に反映します。  
その後、下流成果物を機能仕様に適合させます。

機能仕様を変更するときは、同じカテゴリの要件間と、関連する機能仕様との間に矛盾がないことを確認します。  
要件 ID と UUID の追加、維持、廃止は、本書の「要件 ID と UUID」に従います。

## 確認

機能仕様の変更後は、次の項目を確認します。

- すべての要件 ID と UUID が所定の形式であり、文書群全体で重複していないこと
- 要件 ID の接頭辞、カテゴリ、種別が、app 固有規範、文書名、要件の内容と一致すること
- 各要件文が、要件 ID のカテゴリに対応する主語で始まること
- Markdown、製品コード、テストの要件参照が媒体ごとの記法に従うこと
- 下流成果物が参照する UUID が正本に存在し、要件 ID がその UUID の現在の ID と一致すること
- 各要件が app 自身の責務であり、利用側や上位アプリケーションの責務を含まないこと
- 各要件文が一つの要求だけを持ち、条件と観測可能な結果を判定できること
- API 名、実装方式、ソース、テストへの参照が存在しないこと
- 前提、保証範囲、適用範囲外が要件と矛盾しないこと
- 関連する機能仕様との用語と役割分担が一致すること

Markdown の表記と文章は、[日本語技術文書の文章規範](../../../framework/docsfw/docs/japanese-technical-writing-guideline.md) と [text_style_jp](../../../framework/docsfw/bin/text_style_jp.md) に従って確認します。

要件 ID と UUID の形式および参照関係は、ワークスペース ルートで次のコマンドを実行して確認します。  
検査は、`docs/functional-spec-guideline.md` が配置されているすべての app を対象とします。

```shell
python3 bin/check_functional_spec.py
```
