## LADR-001 トップ ダウン記載スタイルへの統一方針

決定者: Tetsuo Honda  
最終更新日: 2026-11-25

### 背景と課題

`app/` 配下の第一者管理ソース ファイルでは、プロトタイプ宣言を省略して下位関数から順に定義を重ね、`main` や主たる関数が末尾に来るボトム アップ記載が多数を占めています。ソースの全体像を上から下へ把握しやすくするため、記載スタイルをトップ ダウンへ統一する方針を明確にする必要があります。

### 得られた事実

- 2026-11-25 時点の対象 244 ファイル (各リポジトリで追跡され、ignore 対象でもシンボリック リンクでもない `app/*/prod/` 配下の `.c`) のうち 154 ファイルが規則に違反している。前方プロトタイプ宣言のない `static` 関数は 1,341 個である (一時ディレクトリの走査スクリプトによる実測)。
- コマンド ソースでも `main()` がファイル末尾付近に配置されているファイルが多数存在する (`compress-cli.c`、`pinned-prompt.c`、`trace-cli.c`、`porter-test.c` 等)。
- リポジトリ自体も OSS であるため、対象と対象外の区分は「第一者管理 / 第三者管理」と表現する。

### 決定

`app/` 配下の第一者管理対象ソース ファイルにおいて、宣言を省略して定義を重ねるボトム アップ スタイルを禁止し、宣言を先に記載して主たる関数から順に関係性の強さ順に記載するトップ ダウン スタイルへ統一する。コマンド ソースでは、`main` を宣言セクションの直後 (最初の関数定義) に配置する。

## LADR-002 関数記載順の非決定論的指針と宣言・定義の順序一致

決定者: Tetsuo Honda  
最終更新日: 2026-11-25

### 背景と課題

トップ ダウン記載を採用しても、複数の下位関数をどのような順序で並べるかの目安がないと、ファイルごとのばらつきや宣言と定義の対応の追いづらさが生じます。可読性を確保するための記載順の粒度、具体的な並び順の指針、および宣言・定義間の順序関係を定める必要があります。

### 得られた事実

- 現在の `app/general/docs/coding-guideline.md` には、翻訳単位内の関数記載順および `static` 関数の前方宣言に関する規定が存在しない。
- `static` 関数のアドレスでファイル スコープの変数を初期化するファイルが 5 件ある (`cplat` の `prompt_linux.c`、`prompt_windows.c`、`sym_loader_resolve.c`、`trace-cli.c` の `s_commands[]`、`service-sample` の `service-sample-impl.c`)。これらは、前方宣言が変数より後にあるとコンパイルできない。
- `app/general/docs/coding-guideline.md` の命名規則は、シンボルのスコープを公開 (`prod/include/`)、ライブラリ内共有 (`prod/include_internal/`)、モジュール内共有 (モジュール私有ヘッダー)、ファイル内 (`static`) の順に判定する。

### 決定

ファイル全体の構成を「`#include` → 定数・マクロ・型の定義 → `static` 関数の前方プロトタイプ宣言 → ファイル内共有変数と定数表 → 主たる関数の定義 → `static` 関数の定義」とする。前方宣言を変数より前に置き、`static` 関数のアドレスで初期化する変数をコンパイルできるようにする。

主たる関数は、当該 `.c` で定義する `static` でない関数で、ヘッダー (`prod/include/`、`prod/include_internal/`、モジュール私有ヘッダー) で宣言されたものと、入口関数 (`main`、`wmain`) とする。入口関数は最初の関数定義とし、ライブラリとモジュールでは公開関数、ライブラリ内共有関数、モジュール内共有関数の順に置く。

`static` 関数同士の記載順は一意の順序までは要求せず、「機能のまとまりと処理の流れの順 (深さ優先のステップ ダウン)」「共通補助の後置」「対になる操作の隣接」「宣言と定義の順序一致」の 4 原則を指針として規範化する。原則間の優先、呼び出し先が呼び出し元より前に来る配置、主たる関数同士の順序は、規則違反として扱わない事項として規範に明記する。

## LADR-003 適用対象の範囲と既存コードの一括改修

決定者: Tetsuo Honda  
最終更新日: 2026-11-25

### 背景と課題

`app/` 配下には第一者管理・第三者管理、製品コード (`prod/`)・テスト コード (`test/`)、C・C++、自動生成物とシンボリック リンクが混在しており、さらに既存の第一者管理 `.c` には 154 ファイルの違反ソースが存在するため、適用範囲と本案件での改修境界を確定する必要があります。

### 得られた事実

- 2026-11-25 時点で、`app/*/prod/` 配下のディスク上の `.c` は 306 ファイルである。このうち各リポジトリの `git ls-files` で追跡されるものは 244 ファイルである。追跡されない 62 ファイルは、`packages/` から展開した第三者のソース (lua、sqlite、zlib、cJSON 本体)、`gen/` 配下の生成物 9 件 (`struct_meta_parse.lex.c`、`struct_meta_parse.tab.c`、`sample_types_meta.c`、string-catalog の生成物 6 件)、シンボリック リンク 1 件 (`cplat` の `bench-hashtable/bench_timer.c`) である。
- 追跡される 244 ファイルには、cJSON の第一者管理の拡張 (`integer/cJSON_Integer.c`、`jsonc/cJSON_JSONC.c`) とサンプル (`cjson_sample.c`、`zlib_sample.c`) が含まれる。
- 違反ファイルは 154 ファイル (`cplat`: 81、`porter`: 42、`struct-meta`: 17、`string-catalog-sample`: 7、`service-sample`: 5、`cjson`: 2) である。
- `app/general/docs/coding-guideline.md` の「inline 関数」節は、`.c` ファイルでは `inline` を指定しないと定めている。
- `app/general/AGENTS.md` は、個別 app 固有の設定、パス、例外を正本として記載しないと定めている。

### 決定

適用対象はファイル単位で決め、`app/<name>/prod/` 配下の `.c` のうち、そのファイルを含む Git リポジトリで追跡され、ignore 対象でもシンボリック リンクでもないものとする。app 名の列挙では決めない。これにより、`packages/` から展開した第三者のソースと自動生成物 (`gen/` 配下など) とシンボリック リンクは対象外になり、cJSON の第一者管理の拡張 (`integer/cJSON_Integer.c`、`jsonc/cJSON_JSONC.c`) とサンプル コマンドは対象に含まれる。`test/` 配下、C++ ソース、ヘッダーは対象外とする。

`.c` には `inline` を書かない既存の規範に従い、`.c` の `static inline` を対象とする記述は設けない。チェッカーは `inline` の有無にかかわらず `static` の関数定義を検出する。

既存の違反ファイル (2026-11-25 時点で 154 ファイル) は、本案件の中でトップ ダウン記載へ書き換える。段階分けは [LADR-007](#ladr-007-段階分けと並行案件との順序) による。

## LADR-004 機械的チェックの方式・厳格度・実行タイミング

決定者: Tetsuo Honda  
最終更新日: 2026-11-27

### 背景と課題

GCC および MSVC の標準コンパイラ警告では `static` 関数の前方プロトタイプ宣言漏れやボトム アップ配置を検出できないため、Linux / Windows 双方で機能する機械的チェックの実現方式、エラーおよび警告の判定範囲、ならびに実行タイミングを定める必要があります。

### 得られた事実

- `app/makepart.mk` にはすでに `-Wmissing-prototypes`、`-Wstrict-prototypes`、`-Wmissing-declarations` が設定されているが、GCC 8.5.0 実機検証の結果、これらは外部リンケージ関数のみ対象であり `static` 関数の未宣言定義やボトム アップ配置には警告を出さない。
- GCC・MSVC ともに `static` 関数の事前宣言や定義順を強制するコンパイラ警告オプションは存在しない。
- `app/general/bin/` には既存の規範チェッカー (`check_c_blank_lines.py` 等) が独立 Python スクリプトとして配置されている。
- 実装後の実測 (2026-11-27、作業 WBS 4.3) で、全対象 246 ファイルに対する `check_c_topdown.py` の実行時間は約 1.67 [s] だった。
- 実装・書き換えの過程で、`reorder_c_topdown.py` に条件付きコンパイルの分岐内の `#include`、マクロ、型定義、静的変数を `static` 関数定義ごと主たる関数の後ろへ移してしまう欠陥が判明した (`backlog.md` の BL-006)。また、複数の分岐にそれぞれ完全な実装を持つ 2 ファイル (`cplat` の `console.c` と `etw-viewer.c`) は、チェッカーの仕様により `non-topdown-order` 7 件が残存した (`backlog.md` の BL-004)。
- 書き換えた 153 ファイルのうち、自動並べ替え不可と判定された 2 ファイル (`porter` の `tcpServer.c`、`cplat` の `prompt_windows.c`) と、BL-006 により崩れた 3 ファイル (`cplat` の `elevated_process.c`、`process.c`、`eventlog-register.c`) の計 5 ファイルを手作業で修正し、全 153 ファイルが `--verify` に合格した。

### 決定

`app/makepart.mk` は変更せず、`app/general/bin/` に OS 共通の Python チェッカー (`check_c_topdown.py`) を新設する。チェッカーは `makefw` (`make`) や CI には組み込まないが、対象ソース コードの新規作成または編集を行った際には変更対象ファイルに対して実施することを規範のルールとして明文化する。あわせて任意のタイミングでの全件チェック用途にも使用し、実装後に実測した実行時間をもとに最終評価を行う。違反 (終了コード 1) とするのは次の 2 項目だけとする。

- `missing-prototype`: 各 `static` 関数の定義について、同名の `static` 関数のプロトタイプ宣言が、ファイル内の最初の関数定義より前に存在すること。
- `non-topdown-order`: 主たる関数の定義がすべて最初の `static` 関数の定義より前にあり、入口関数 (`main`、`wmain`) がある場合はそれがほかのすべての関数定義より前にあること。

宣言と定義の順序不一致 (`order-mismatch`) は `warning:` として出力し、終了コードは 0 のままとする。呼び出し方向の逆転は検査しない。前処理の条件は評価せず、条件付きコンパイルの複数の分岐に現れる同名の関数は 1 つの関数として扱い、宣言と定義はそれぞれ最初に現れた位置で判定する (`non-topdown-order` は各定義の位置で判定)。既定の走査は [LADR-003](#ladr-003-適用対象の範囲と既存コードの一括改修) のファイル単位の条件で対象を選ぶ。

既存ファイルの書き換えには、再実行できる並べ替えの補助ツール `app/general/bin/reorder_c_topdown.py` (単体テストは `app/general/bin_test/test_reorder_c_topdown.py`) を作成して使う。改修前後で、ファイル スコープの各要素のトークン列の集合と前処理の条件とコメントが一致し、差分が追加した前方プロトタイプ宣言だけであることを検証する機能を持たせ、書き換えた全ファイルで合格させる。

編集時の実施は、規範の文言 (対象の `.c` を新規作成または編集した場合は、そのファイルに対して実行してエラーと警告を 0 件にする) のとおりに記載する。移行前のファイルを部分的に編集する場合の扱い、並行案件への適用、エージェントへの発火の手段は、この案件では定めず残課題一覧へ送る。

## LADR-008 Git の書き込み操作と CI の確認

決定者: Tetsuo Honda  
最終更新日: 2026-11-25

### 背景と課題

ルートの `AGENTS.md` は、ユーザーの個別の指示があるまでステージングとコミットを行わないことを定めています。書き換えは複数のリポジトリ (親リポジトリ、cjson、porter、cplat) にまたがり、Windows/MSVC の確認を CI で行うため、コミットと push の許可の範囲と手順を定める必要があります。

- CI は親リポジトリの `.github/workflows/ci.yml` だけにあり、サブモジュール (cjson、cplat、porter) には CI のワークフローがない。

### 決定

この案件の成果物を main へコミットして `origin` へ早送りで push することを許可済みとして扱う。Git の書き込み操作は主エージェントだけが行う。コミットは作業の単位 (app ごと。サブモジュールの app はそのリポジトリのコミットと親リポジトリの参照の更新) とし、push はサブモジュール、親リポジトリの順に行う。強制 push、rebase、stash、`git rm`、`git add -N`、ほかのブランチへのコミット、タグの作成は行わない。push のたびに親リポジトリの CI を `gh run list` と `gh run watch` で確認し、エラーや警告があればその都度直して再確認する。
