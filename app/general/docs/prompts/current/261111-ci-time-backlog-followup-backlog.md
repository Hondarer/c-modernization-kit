## BL-001 並列度の引き上げの効果の評価

`ci.yml` で `MAKEFW_CPU_BUDGET` を 8 に指定し、Linux と Windows の Build と Run tests が `make -j4` で動くようにしました。  
実行 43102328935 では全ジョブが成功し、警告のアーティファクトもありませんでしたが、短縮の効果は実行ごとの差と区別できませんでした。

実行全体は 297[分] で、前回の実行 42930377100 の 221[分] より長くなりました。  
cplat の Build は、OL8 が 102[分] (前回 98[分])、OL10 が 49[分] (前回 64[分])、Windows が 71[分] (前回 58[分]) です。並列度を 2 倍にしても Build が半分にならない理由は、特定できていません。

評価の際は、並列度を上げた後の実行を複数回集め、上の表の中央値と最小値に比べます。効果がない、または悪化していると判断した場合の対処は、次のとおりです。

- `ci.yml` の `MAKEFW_CPU_BUDGET` の指定を外すと、`make -j2` に戻ります。
- Run tests ステップに `MAKEFW_TEST_RUN_JOBS: "2"` を追加すると、コンパイルの並列度を 4 にしたまま、テストを同時に実行する数だけを 2 に戻せます。

> [!NOTE]
> 最終仕様の判定基準 (Build ステップが過去 5 回の中央値より短い) は、効果がなくても満たす場合がある基準でした。評価では、1 回の値ではなく、複数回の分布を比べる必要があります。

実行 43102328935 の Windows の Run tests ステップは 132[分] で、過去 5 回 (69 ～ 103[分]) のどれよりも長くなりました。  
内訳は、cplat が 84[分] (前回 50[分])、porter が 35[分] (前回 19[分])、calc が 25[分] (前回 5[分])、struct-meta が 21[分] (前回 7[分]) です。Build ステップでも、`framework/testfw` が 32[分] (前回 22[分]) でした。

テストを同時に実行する数を 2 から 4 に変えた影響か、ランナーの差かは、1 回の実走では区別できません。テストの失敗とタイムアウトはありません。  
BL-001 の評価で Windows だけが長い傾向が続く場合は、`MAKEFW_TEST_RUN_JOBS: "2"` の追加、または Windows だけ `MAKEFW_CPU_BUDGET` を外す対処の対象になります。

## BL-003 app の中の時間の内訳を読み取れない点

CI のログは app ごとにまとめて出力されるため、app の中で、コンパイル、リンク、テストのビルド、テストの実行にそれぞれ何分かかったかを読み取れません。  
BL-001 と BL-002 の原因を特定するには、段階ごとの時刻をログへ出す仕組みが必要です。makefw の変更を伴うため、今回の案件の対象外としました。

## BL-004 コンパイル結果のキャッシュとジョブの分割

並列度の引き上げ以外の対策として、次の 2 つを検討の候補に残します。どちらも、BL-001 の評価の後に判断します。

- コンパイル結果のキャッシュ (ccache): Linux では、コンテナー イメージへの追加と、makefw のコンパイラ呼び出しの変更が必要です。Windows の MSVC は、一括コンパイル (`/MP`) と PCH を使っているため、対応が難しいと見込みます。
- ジョブの分割: cplat のテストを複数のジョブへ分けます。`prod` のビルド結果の受け渡しと、テスト結果とカバレッジをまとめる処理が必要です。

時間の大半は app/cplat のテストのビルドと実行であり、ほかの app は cplat の完了を待ってから動きます。
