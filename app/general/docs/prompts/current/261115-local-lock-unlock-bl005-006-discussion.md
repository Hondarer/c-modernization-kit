### 調査で確認した事実

1. **`sync.h` の契約**: `cplat_local_lock_unlock()` の `@return` は「呼び出しスレッドが保持しているミューテックスに対しては `CPLAT_OK` を返します」と定め、続けて「OS のロック解除が失敗した場合は `CPLAT_ERR_UNKNOWN`」と記載しています。この 1 文目は第 2 バッチで追加した契約です。
2. **Linux 実装**: `pthread_mutex_init(&native, NULL)` で既定型のミューテックスを作り、`pthread_mutex_unlock()` の結果を返します。POSIX は既定型のミューテックスを所有スレッドが解放する場合のエラーを定義していません (`sync_linux.c` に `see:` 付きで記載済み)。
3. **Windows 実装**: `ReleaseSRWLockExclusive()` は戻り値を持たず、関数は常に `CPLAT_OK` を返します。
4. **既存の書き方**: 第 2 バッチは、取得の成功後に解放する 22 箇所 (`filter_slot.c` 13、`argparser.c` 2、`sample_filter_share_region.c` 2 など) を `(void)` と「取得に成功したロックの解放は失敗しない」の理由コメントで統一しました。BL-006 が指摘する 2 箇所は、この 22 箇所に含まれます。
5. **第 3 バッチでの変化**: 第 3 バッチは、`pinned_prompt.c`、`pinned-prompt.c`、`string-catalog-filter-sample.c` の 13 組でローカル ロック解放の結果も確認し、失敗時に結果コードを返すか `CPLAT_ABORT` を呼ぶ形にしました。また `sample_filter_share_lock_release()` は、第 2 バッチの理由コメントを削除し、ローカル ロックの解放結果も確認する形になりました。この結果、同じ状況に対して 2 つの書き方が混在しています。
6. **BL-005 の対象**: `sink_registry_unlock()` の呼び出し元は `cplat_trace_file_sink_create()` の 5 箇所と `cplat_trace_file_sink_dispose()` の 1 箇所です。いずれも `sink_registry_lock()` の成功を確認した後にだけ呼びます。`cplat_internal_trace_file_sink_write_text()` の再オープン失敗経路も、`cplat_local_lock_lock()` の成功後に解放します。
7. **BL-006 の前提**: BL-006 は「`sync.h` は OS のロック解除失敗時に `CPLAT_ERR_UNKNOWN` を返すと記載している」ことを根拠に、理由コメントが契約と矛盾するとしています。事実 1〜3 から、保持中のミューテックスでは `CPLAT_ERR_UNKNOWN` の経路に到達しないため、理由コメントは `sync.h` の 1 文目の契約と一致します。

## 現行の合意内容

合意版は版 11 です。ユーザーの依頼は「BL-005、BL-006 の問題点解消を進める」こと、第 2 ゲートでの「BL-002 も本件で対策したい」こと、および [Q-007](#q-007-bl-002-の対策方式) の補足「API 名は破壊的に変更を許容するので、歪のない最適な API 体系にすること」です。

- **BL-005、BL-006**: 取得に成功したローカル ロックの解放は失敗しないものとして扱います ([Q-001](#q-001-保持中のローカル-ロック解放の失敗をどう扱うか))。`cplat_local_lock_unlock()` を `void` にし、解放結果による分岐、`(void)`、理由コメント、解放失敗の注入テストを削除します ([Q-002](#q-002-第-3-バッチで解放結果を確認するようにした箇所をそろえるか)、[Q-004](#q-004-cplat_local_lock_unlock-の戻り値を-void-にするか))。
- **BL-002**: 無期限待機の取得を戻り値のない関数に分け、無期限待機の呼び出しをすべて移行します ([Q-007](#q-007-bl-002-の対策方式)、[Q-008](#q-008-無期限待機と期限付きの取得関数の名前))。
- **適用範囲**: `sync.h` の同期プリミティブ全体と、プロセスとソケットの待機関数に同じ原則を適用します ([Q-012](#q-012-api-体系をそろえる範囲))。
- **命名**: 待機を伴う操作は、無期限の `X()`、待たない `try_X()` (既存のロックだけ)、期限付きの `timed_X(..., timeout_ms)` に分けます ([Q-013](#q-013-同期-api-の命名と戻り値の体系)、[Q-017](#q-017-プロセスとソケットの待機関数の名前と引数))。
- **戻り値**: 契約の範囲内で失敗しない操作は `void`、失敗しうる操作は結果コードを返します。`void` の操作は、`NULL` を渡すと何もせず、OS が失敗を報告すると `CPLAT_ABORT` で終了します ([Q-005](#q-005-void-化した-cplat_local_lock_unlock-が-os-の失敗報告を受けた場合の扱い)、[Q-009](#q-009-無期限待機の取得が-os-の失敗報告を受けた場合の扱い)、[Q-013](#q-013-同期-api-の命名と戻り値の体系)、[Q-014](#q-014-ローカル読み書きロックの解放の戻り値)、[Q-015](#q-015-ローカル読み書きロックの無期限待機で条件変数の待機が失敗した場合の扱い))。
    - `void`: ローカル ロックの無期限取得と解放、条件変数の無期限待機・`signal`・`broadcast`、ローカル読み書きロックの無期限取得と解放、スレッドの無期限 join。
    - `int`: 期限付きの関数、`try_X()`、プロセス間ロックとプロセス間読み書きロック、プロセスとソケットの待機関数。
- **待ち時間の定数**: 共通の `CPLAT_WAIT_FOREVER` (`INT_MAX`) と `CPLAT_NO_WAIT` (0) に統一し、モジュールごとの 3 組を削除します。期限付きの関数も両方を受け付けます ([Q-013](#q-013-同期-api-の命名と戻り値の体系)、[Q-018](#q-018-待ち時間を表す定数の統一))。
- **ソケット**: 単一ソケットの待機は、無期限と期限付きのどちらも `ready_out` を持たず、期限付きの時間切れは `CPLAT_ERR_TIMEOUT` で返します。複数ソケットの待機は `ready_out` を残し、時間切れは `CPLAT_ERR_TIMEOUT`、無期限待機で有効なソケットがなければ `CPLAT_ERR_INVALID_ARGUMENT` を返します ([Q-017](#q-017-プロセスとソケットの待機関数の名前と引数)、[Q-020](#q-020-ソケットの期限付き待機での時間切れの知らせ方))。
- **プロセス**: `cplat_process_run_sync()` を無期限にし、`cplat_process_timed_run_sync()` を設けます。期限が切れたら子プロセスを強制終了し、公開定数の上限 3000 ms まで終了を待ってから `CPLAT_ERR_TIMEOUT` を返します。上限内に終わらなくても `CPLAT_ERR_TIMEOUT` を返し、強制終了が失敗した場合はその結果コードを返します。`cplat_process_terminate()` は Linux で `SIGKILL` を送ります ([Q-019](#q-019-プロセスの同期実行に期限付きの関数を設けるか)、[Q-022](#q-022-linux-のプロセスの強制終了で送るシグナル)〜[Q-026](#q-026-強制終了の後に上限内で終わらなかった場合の結果))。
- **BL-003**: Linux のプロセス終了待機は、無期限と期限付きの両方で `pidfd_open()` と `poll()` を使い、未対応のカーネルでは `WNOHANG` の確認を繰り返します。`waitpid()` の `ECHILD` で終了を検出した場合は `CPLAT_OK` を返して終了済みとして扱い、終了コードを取得できなかったことを `cplat_process_get_exit_code()` の `CPLAT_ERR_NOT_FOUND` で知らせます ([Q-027](#q-027-linux-のプロセス終了待機の方式)、[Q-028](#q-028-自動回収された子プロセスの終了を検出した場合の待機の結果)、[Q-029](#q-029-自動回収された子プロセスの終了コードの扱い))。
- **検証**: 4 app (cplat、porter、string-catalog-sample、service-sample) のビルド (テストのビルドを含む) と、変更する同期・プロセス・ソケットの関数を参照するテスト、および変更した製品コード (porter を含む) を検証するテストを実行します ([Q-016](#q-016-api-体系の変更を加えた場合の検証範囲)、[Q-021](#q-021-プロセスとソケットの変更を加えた場合の検証範囲))。

### Q-001 保持中のローカル ロック解放の失敗をどう扱うか

**Status**

**Question**

BL-005 と BL-006 の対象箇所で、取得に成功したローカル ロックの解放 (`cplat_local_lock_unlock()`) の失敗をどう扱いますか。

**Context**

- **経緯と背景**: BL-005、BL-006 は「ローカル ロックの解放が失敗しても伝わらない」ことを問題としています。しかし [調査で確認した事実](#調査で確認した事実) の 1〜3 のとおり、`sync.h` は保持中のミューテックスの解放が `CPLAT_OK` を返すと契約しており、Linux と Windows の実装もこの契約を満たします。対象箇所はすべて取得の成功後に解放するため (事実 6)、解放の失敗経路には到達しません。
- **判断の影響**: A は第 2 バッチの規則に合わせ、理由コメントによる説明だけで解消します。B は到達しない経路に失敗処理を追加します。B の場合、`cplat_trace_file_sink_create()` で登録を終えた後に解放が失敗したとき、ハンドルを返すか、登録を取り消して `NULL` を返すかなどの設計を追加で決める必要があります。`cplat_trace_file_sink_dispose()` は戻り値を持たないため `CPLAT_ABORT` になります。

    (void)cplat_local_lock_unlock(s_sink_registry_lock);
}
```

### Q-004 cplat_local_lock_unlock の戻り値を void にするか

**Status**

解決済み

**Question**

`cplat_local_lock_unlock()` の戻り値を `int` から `void` へ変更しますか。

**Context**

- **経緯と背景**: [Q-002](#q-002-第-3-バッチで解放結果を確認するようにした箇所をそろえるか) の補足で「常に `CPLAT_OK` になるのであれば、関数の戻り値を void にしてもよいのではないか」とご意見を求められました。以下が AI の意見と、その根拠となる調査結果です。
- **意見**: void への変更に賛成します。理由は次の 4 点です。
    1. **戻り値が情報を持たない**: 契約の範囲内 (呼び出しスレッドが保持している状態) では、戻り値は常に `CPLAT_OK` です。契約の範囲外 (保持していないロックの解放) は、POSIX の既定型ミューテックスでも Windows の SRW ロックでも動作が未定義であり、戻り値で誤用を検出できる保証はありません。呼び出し元が確認しても判断材料になりません。
    2. **理由コメントの義務がなくなる**: 共通コーディング規範は「戻り値やエラーを意図的に処理しない」場合に理由コメントを求めます。`int` を維持すると、porter の約 190 箇所 (現在は理由コメントなしで戻り値を捨てている) にも `(void)` と理由コメントが必要です。void なら、これらは変更なしで規範を満たします。
    3. **先例がある**: Win32 の `ReleaseSRWLockExclusive()`、`LeaveCriticalSection()`、C++ の `std::mutex::unlock()` は戻り値を持ちません。一方、POSIX の `pthread_mutex_unlock()` と C11 の `mtx_unlock()` は `int` を返すため、先例は分かれます。cplat は失敗しない契約を定めている点で前者に近いと考えます。
    4. **BL-006 のような誤読がなくなる**: 戻り値がなければ、「失敗しうるのか」という疑問自体が生じません。[Q-003](#q-003-synch-の-cplat_local_lock_unlock-の契約文言を明確にするか) の文言の明確化も不要になります。
- **留意点**:
    - 公開関数 (`CPLAT_EXPORT`) の型の変更です。x86_64 では、戻り値を捨てていた既存バイナリは影響を受けません。戻り値を確認していた既存バイナリを再ビルドせずに新しいライブラリと組み合わせると、不定の値を読みます。リポジトリ内の利用者はすべて同時に修正します。
    - `NULL` を渡した場合は、共通コーディング規範「戻り値を持たない関数は、無処理 (no-op) で戻る契約を明示します」に従い、何もせずに戻る契約を Doxygen に記載します。
    - 読み書きロックの解放 (`cplat_local_rwlock_unlock_shared()`、`cplat_local_rwlock_unlock_exclusive()`) は、内部の読み取り数と書き込み状態を管理しているため、保持していない解放を検出して `CPLAT_ERR_INVALID_ARGUMENT` を返します。誤用を検出できるため、戻り値に意味があります。プロセス間ロックの解放 (`cplat_interprocess_lock_unlock()`) は `flock()` などの失敗を返します。このため、void にする対象はローカル ロックの解放だけが妥当と考えます。

- **終了を待つ理由**: Linux では、終了した子プロセスは親が `waitpid()` で回収するまで、プロセス表に残ります (ゾンビ プロセス)。現在の `cplat_process_dispose()` は回収しないため、終了を待たずに破棄すると、親プロセスが終わるまでゾンビ プロセスが残ります。Windows では、`TerminateProcess()` は終了の完了を待たずに戻ります。

    if (result == CPLAT_ERR_TIMEOUT)
    {
        const int terminate_result = cplat_process_terminate(process);
        if (terminate_result != CPLAT_OK)
        {
            result = terminate_result;
        }
        else
        {
            (void)cplat_process_wait(process); /* 強制終了した子プロセスの終了を待ち、回収する */
        }
    }
```

**Answer**

**Status**

**Question**

**Context**

- **経緯と背景**: 第 2 ゲートで、残課題一覧の BL-003 を今回の範囲に加えることになりました。

- **期限付きの待機の現状**: `WNOHANG` を付けた `waitpid()` を 1 ms 間隔で繰り返すため、この事象は起きません。対象の子プロセスが自動で回収された後は、`ECHILD` で終了を検出できます (そのときの結果は [Q-028](#q-028-自動回収された子プロセスの終了を検出した場合の待機の結果) で確認します)。
