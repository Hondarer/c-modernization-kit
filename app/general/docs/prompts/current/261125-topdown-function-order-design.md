# app 配下ソースのトップ ダウン記載統一 最終仕様

ファイル名: `261125-topdown-function-order-design.md`

## 目的と基本方針

第一者管理の `app/*/prod/` 配下の C ソース ファイル (`.c`) で、宣言を省略して下位関数から定義を重ねるボトム アップの記載を禁止します。`static` 関数の前方プロトタイプ宣言を先に記載し、主たる関数から順に関係性の強さの順に記載するトップ ダウンの記載へ統一します。

ファイルの先頭から読むだけで、コマンドやライブラリの全体像を把握できるようにし、可読性と保守性を高めます。

## 適用範囲

### 対象ファイルの決め方

対象は、ファイル単位で次の条件をすべて満たす `.c` ファイルです。app 名の列挙では決めません。

1. `app/<name>/prod/` 配下にある。
2. そのファイルを含む Git リポジトリ (親リポジトリまたはサブモジュール) の `git ls-files` で追跡されている。
3. ignore 対象ではない。
4. シンボリック リンクではない。

この条件により、次のファイルは対象外になります。

- `packages/` の配布物から展開した第三者のソース (追跡されず ignore 対象)
- 生成器の出力 (`gen/` 配下など、追跡されず ignore 対象)。自動生成物は手動変更の対象外であり、規則を適用する場合は生成元を直します。
- makefw がディレクトリ外のソースを取り込むために作るシンボリック リンク。実体のファイルが対象になります。

第三者の配布物を取り込む app に置いた第一者管理のソース (cJSON の拡張、サンプル コマンドなど) は、追跡されているため対象に含まれます。

### 対象外

- `test/` 配下のテストと mock のソース
- C++ のソース (`.cc`、`.cpp`)
- ヘッダー ファイル (`.h`)
- `app/makepart.mk`、`framework/makefw`、CI のワークフロー設定の変更

> [!NOTE]
> リポジトリ自体も OSS であるため、規範と関連文書では「非 OSS / OSS」ではなく「第一者管理 / 第三者管理」の表現を用います。

### 対象の実測

2026-11-25 時点の対象は 244 ファイルです。このうち 154 ファイルが規則に違反しています (違反の内訳は [既存コードの書き換え計画](#既存コードの書き換え計画) の表を参照)。

## コーディング規範の仕様

`app/general/docs/coding-guideline.md` に独立したレベル 2 見出し `## 関数の記載順と前方宣言` を新設し、概要の記載一覧と `## 実装コメント` 節を整合させます。規範の本文には個別の app 名や個別ファイルを規範として記載しません。

### 用語の定義

- **主たる関数**: 当該 `.c` ファイルで定義する、`static` でない関数です。次のどちらかに当たります。
    - ヘッダーで宣言された関数。命名規則のスコープ判定に従い、`prod/include/` の公開関数、`prod/include_internal/` のライブラリ内共有関数、モジュール私有ヘッダー (実装と同じディレクトリのヘッダー) のモジュール内共有関数のいずれかです。
    - プログラムの入口 (`main`、`wmain`)。
- **入口関数**: 主たる関数のうち `main` と `wmain` です。
- **ファイル内補助関数**: 当該 `.c` ファイル内に閉じた `static` 関数です。

> [!NOTE]
> `.c` ファイルには `inline` を書きません (既存の規範「inline 関数」節)。この規範は `inline` の有無で扱いを変えず、`static` の付いた関数定義をすべてファイル内補助関数として扱います。

### ファイル全体の構成

対象の `.c` ファイルは、上から次の順に構成します。該当する要素がない区分は省略します。

1. `#include` 指令
2. ファイル内の定数、マクロ、型の定義 (`typedef`、`struct`、`enum`)
3. **ファイル内補助関数の前方プロトタイプ宣言**
4. ファイル内共有変数 (`static` 変数) とファイル スコープの定数表
5. **主たる関数の定義**
    - コマンドのソース: 入口関数を最初の関数定義にします。
    - ライブラリとモジュールのソース: 公開関数、ライブラリ内共有関数、モジュール内共有関数の順に置きます。同じ区分の中は、ヘッダーの宣言順またはライフサイクル順 (初期化・生成、主操作、終了・破棄) にそろえます。
6. **ファイル内補助関数の定義**

前方プロトタイプ宣言を変数より前に置くのは、`static` 関数のアドレスで初期化する変数 (コールバック表、コマンド表、関数ポインターの既定値) が宣言を参照できるようにするためです。

### ファイル内補助関数の記載順の指針

ファイル内補助関数同士の並び順は、一意に決まる順序までは求めません。可読性のために次の 4 原則を指針とします。

1. **機能のまとまりと処理の流れの順 (深さ優先のステップ ダウン)**: 主たる関数から呼ばれる順に、機能や処理の段階のまとまりごとに並べます。特定の段階だけが使う補助関数は、その段階の関数の直後に続けます。
2. **共通補助の後置**: 複数の関数や段階から広く呼ばれる補助関数 (エラーの変換、文字列の整形、時刻の取得など) は、個別の段階の関数群の後ろにまとめます。
3. **対になる操作の隣接**: `init` と `dispose`、`lock` と `unlock`、`open` と `close`、`encode` と `decode` などの対になる操作は隣り合わせます。
4. **宣言と定義の順序の一致**: 前方プロトタイプ宣言の並びを、ファイル内補助関数の定義の並びと一致させます。

次の事項は指針の範囲で判断し、規則違反として扱いません。

- 原則 1 から 3 のどれを優先するか、およびそれによって決まる補助関数同士の順序
- 相互再帰、対になる操作の隣接、共通補助の後置によって、呼び出し先が呼び出し元より前に来ること
- 主たる関数同士の区分の順序と、同じ区分内の順序

### 実装コメントとの整合

- ファイル内補助関数の役割や戻り値の意味を説明する実装コメントは、既存の `## 実装コメント` 節の規定どおり定義の直前に置き、前方プロトタイプ宣言には重複して書きません。
- 論理的なまとまりを区切る短い見出しコメントは、必要に応じて宣言側と定義側に対応させて置けます。

### 条件付きコンパイルの扱い

- プラットフォームの分岐 (`#if defined(PLATFORM_LINUX)` と `#elif defined(PLATFORM_WINDOWS)` など) で同名のファイル内補助関数を出し分ける場合、シグネチャが共通であれば前方プロトタイプ宣言を分岐の外に 1 つ置きます。シグネチャや存在の有無が分岐ごとに異なる場合は、対応する分岐の中に置きます。
- ファイル全体を 1 つの条件で囲むファイル (OS 別の実装ファイルなど) では、条件の内側で上記の構成に従います。

### 実施の規則

- 対象の `.c` ファイルを新規作成または編集した場合は、そのファイルに対して `check_c_topdown.py` を実行し、エラーと警告を 0 件にします。
- `check_c_topdown.py` は `make` と CI には組み込みません。任意の時点での全件の確認にも使います。

## 機械的チェック ツールの仕様

> [!NOTE]
> GCC の `-Wmissing-prototypes` と `-Wmissing-declarations` は外部リンケージの関数だけを対象とし、`static` 関数の前方宣言の欠落やボトム アップの配置を検出しません。MSVC にも同等の警告はありません。Linux と Windows で同じ基準により検査できるよう、OS 共通の Python スクリプトとして実装します。

### 配置と運用

- ツール本体: `app/general/bin/check_c_topdown.py`
- 単体テスト: `app/general/bin_test/test_check_c_topdown.py`
- 運用: `make` と CI には組み込まず、既存の `check_c_blank_lines.py` と同様に独立したコマンドとして提供します。
- Python の規範: `app/general/docs/python-text-encoding-guideline.md` と `app/general/docs/python-import-path-guideline.md` に従います。後述の並べ替えツールと解析処理を共有する場合は、同じディレクトリのモジュールに置き、import の経路の規範に従います。

### 対象ファイルの選択

- 引数にファイルまたはディレクトリを受け取ります。ディレクトリを指定した場合は、配下の `.c` のうち [対象ファイルの決め方](#対象ファイルの決め方) の条件を満たすものを走査します。追跡の判定は、ファイルを含む Git リポジトリの `git ls-files` で行います。
- 引数を省略した場合は、ワークスペースの `app/*/prod/` 全体を同じ条件で走査します。
- 条件を満たさないファイル (未追跡、ignore 対象、シンボリック リンク) を明示的に指定した場合は、検査せず、対象外である旨を表示します。終了コードには影響しません。

### 解析の前提

- コメント、文字列リテラル、文字リテラルを除いたうえで、ファイル スコープ (波かっこの深さ 0) の関数定義と関数宣言を抽出します。
- 前処理指令の条件は評価しません。すべての分岐を 1 つの並びとして扱います。
- `static` の有無は宣言指定子で判定します。`inline` などほかの指定子の有無は判定に影響しません。

### 検査項目と判定レベル

Table: 検査項目と判定レベル

| 種別 | 判定基準 | レベル | 終了コード |
| --- | --- | --- | --- |
| `missing-prototype` | ファイル内補助関数の定義それぞれについて、同名の `static` 関数のプロトタイプ宣言が、ファイル内の最初の関数定義より前に存在する | `error` | 1 件以上で 1 |
| `non-topdown-order` | 主たる関数の定義がすべて、最初のファイル内補助関数の定義より前にある。入口関数がある場合は、入口関数の定義がほかのすべての関数定義より前にある | `error` | 1 件以上で 1 |
| `order-mismatch` | 前方プロトタイプ宣言に現れるファイル内補助関数の順序と、定義に現れる順序が一致する | `warning` | 影響しない |

同名の関数が条件付きコンパイルの複数の分岐に現れる場合は、次のように扱います。

- 定義: 同名の定義を 1 つの関数として扱い、位置は最初に現れた定義とします。`non-topdown-order` の判定では、各定義の位置をそれぞれ評価します。
- 宣言: 同名の宣言が複数あれば、最初に現れた宣言の位置を使います。どの分岐にあっても宣言ありとします。
- `order-mismatch`: 宣言と定義のそれぞれで最初に現れた位置の順序を比較します。

呼び出しの方向 (呼び出し元が呼び出し先より前にあるか) は、相互再帰や対になる操作の隣接など正当な例外があるため検査しません。

### コマンド ラインと出力

- 出力形式: `<path>:<line>: <error|warning>: [<rule>] <message>`
- 最後にサマリー (対象ファイル数、エラー件数、警告件数) を出力します。
- 終了コード: エラーが 1 件以上で 1、それ以外は 0。

## 並べ替えの補助ツールと等価性の検証

既存ファイルの書き換えは手作業に頼らず、再実行できるツールで行います。並行する案件の統合後に同じツールを再実行して揃えるためです。

### 配置

- ツール本体: `app/general/bin/reorder_c_topdown.py`
- 単体テスト: `app/general/bin_test/test_reorder_c_topdown.py`

### 並べ替えの仕様

- 入力ファイルのファイル スコープの要素 (関数定義、関数宣言、変数、型、マクロ、前処理指令) を、定義直前の実装コメントと Doxygen コメントを含めた単位で扱います。
- ファイル内補助関数の前方プロトタイプ宣言を生成して宣言の区分に置き、主たる関数の定義をファイル内補助関数の定義より前へ移します。入口関数は最初の関数定義にします。
- ファイル内補助関数の定義の相対順序は、入力の順序を保ちます。ファイル内補助関数同士の並びを 4 原則に沿って整える場合は、ツールの出力に対する追加の編集として行い、等価性の検証の対象に含めます。
- 前方プロトタイプ宣言は定義の宣言部 (戻り値の型、名前、仮引数並び、属性) から生成し、定義と同じ順に並べます。
- 前処理の分岐をまたいで要素を移しません。ファイル全体を囲む条件の内側では、その内側を 1 つのファイルとして扱います。部分的な分岐の中に定義がある場合は、分岐全体を 1 つの単位として移し、前方プロトタイプ宣言は同じ条件の分岐に入れて宣言の区分に置きます。
- 自動で並べ替えられない構造を検出した場合は、ファイルを変更せずに理由を表示して終了コード 1 を返します。そのファイルは手作業で書き換え、等価性の検証を同じく行います。
- 既定は差分の表示だけとし、`--in-place` を指定した場合にファイルを書き換えます。

### 等価性の検証

`reorder_c_topdown.py --verify <改修前のファイル> <改修後のファイル>` で、改修前後の等価性を検証します。改修前のファイルは `git show HEAD:<path>` などで取り出します。`--in-place` の書き換えでも、書き込む前に同じ検証を内部で行い、不一致なら書き込みません。

等価の条件は次のとおりです。

- コメントと空白を除いたトークン列で比較し、改修前後のファイル スコープの各要素 (関数定義、変数、型、マクロ、前処理指令) の集合が一致する。
- 各要素を囲む前処理の条件が、改修前後で同じである。
- 改修後にだけある要素は、ファイル内補助関数の前方プロトタイプ宣言だけであり、その宣言部のトークン列が対応する定義の宣言部と一致する。
- 実装コメントと Doxygen コメントの文字列の集合が一致する (コメントの内容を変えていない)。

### 段階の分け方

並行して進む案件と同じファイルを同時に書き換えないよう、2 段に分けます。

- **第 1 段**: 規範の節、`check_c_topdown.py`、`reorder_c_topdown.py` とそれぞれの単体テストを `app/general` に作成します。続けて、並行案件が大きく書き換える `cplat` と `porter` 以外の app を、`service-sample`、`string-catalog-sample`、`cjson` の拡張、確認だけの app の順に書き換えます。`struct-meta` は、並行案件 (`app/general/docs/prompts/current/261125-consumable-backlog-items-*`) の struct-meta の構文解析器の変更 (統合の単位 U1) が main へ統合された後に書き換えます。
- **第 2 段**: 並行案件 (`app/general/docs/prompts/current/261125-consumable-backlog-items-*` と `app/porter/docs/prompts/current/261123-porter-remaining-backlog-phase2-*`) が main へ統合された後に、`reorder_c_topdown.py` を再実行して `porter`、`cplat` の順に書き換えます。あわせて、第 1 段で書き換えた後に並行案件が変更したファイルにも道具を再実行し、全対象をエラー 0 件・警告 0 件に揃えます。

> [!NOTE]
> 2026-11-25 時点の並行案件の最終仕様では、第 1 段の対象のうち `cJSON_JSONC.c` (統合の単位 U3) と、`cplat_argparser_init` の呼び出し元 (統合の単位 U4。`service-sample`、`struct-meta` の `struct_meta_sample.c` など) も変更されます。第 1 段を先に main へ統合し、並行案件は統合時に main を取り込みます。第 2 段の再実行で、これらのファイルの記載順を確定させます。

> [!IMPORTANT]
> 第 2 段の開始条件は、2 つの並行案件がそれぞれ main へ統合されたこと、または統合せずに終了したことです。条件を満たすまで第 2 段の作業項目はブロック中にします。開始条件が満たされず第 2 段を実施できない場合は、残りの作業を残課題一覧へ送ります。

### 書き換え時の遵守事項

- 振る舞い、ABI、エラー処理、ログの出力、既存コメントの内容を変えません。等価性の検証に合格することを、各ファイルの書き換えの完了条件とします。
- 既存の実装コメント (定義直前のコメント、Doxygen の誘導マーカー、空行の規則、`#endif` のコメント) を維持し、`check_c_blank_lines.py` の検出を増やしません。
- 書き換えたファイルの行番号を `ファイル名.c:行番号` の形で引用している文書を検索し、引用を追従させます。2026-11-25 時点では `app/string-catalog-sample/docs/architecture.md` の 240 行 (`string-catalog-command-sample.c:273` を含むトレースの出力例) が該当します。行番号を含むテストの期待値は、各 app の `make test` で検出して追従させます。
- `make` は同時に 1 本だけ実行します。`make clean` は実行しません。サブエージェントへ委譲する場合は、担当の app を限定し、`clean` の禁止を依頼に明記します。
- 各 app の書き換えの後に、その app の `make`、対象範囲の `.warn` の確認、`make test` を行います。

## Git の運用と書き込み操作の許可の範囲

ユーザーは、この案件の成果物を main へコミットして push することを事前に許可しています。Git の書き込み操作は主エージェントだけが行い、サブエージェントには行わせません。

### 許可する操作

Table: 許可する Git の書き込み操作

| 操作 | 範囲 |
| --- | --- |
| ステージングとコミット (main) | この最終仕様の範囲の変更だけ。対象のパスを明示して `git add` する |
| 親リポジトリでのサブモジュールの参照 (gitlink) の更新のコミット (main) | サブモジュールのコミットを push した後 |
| `origin` の main への push | 早送りの push だけ。サブモジュール、親リポジトリの順 |

範囲の外の操作 (強制 push、rebase、stash、`git rm`、`git add -N`、ほかのブランチへのコミット、タグの作成) は行いません。ファイルの削除が必要な場合は `rm` で行い、ステージングは変更の確定後に行います。push が早送りにならない場合は、`git pull --ff-only` で取り込めるときだけ取り込み、取り込めない場合は作業を止めて状況を記録します。

### コミットの単位と書き方

- コミットの単位は作業の単位 (app ごと。サブモジュールの app はそのリポジトリのコミットと、親リポジトリの参照の更新のコミット) とします。規範とツールは `app/general` の 1 つの単位にします。
- コミット メッセージは、リポジトリの既存の形式 (`feat:`、`fix:`、`test:`、`docs:` の接頭辞と日本語の本文) に従います。
- `app/general/docs/prompts/` 配下だけのコミットには `[skip ci]` を含めます。
- 利用者が並行して作業ツリーを変更している場合があるため、自分が変更したパスだけをステージングします。

### push と CI の確認

CI は親リポジトリの GitHub Actions (`.github/workflows/ci.yml`) が担い、Linux と Windows/MSVC のビルドとテストを行います。

1. 各段の作業の単位を push するたびに、`gh run list` と `gh run watch` で親リポジトリの CI の結果を確認します。
2. 失敗または警告があれば、ログと警告のアーティファクトから原因を特定し、修正をコミットして push し、CI を再確認します。Windows 専用のコードの確認は、この CI の結果で行います。
3. 一過性の失敗であると根拠を確かめられた場合は、再実行します。再発した場合は永続的な問題として調査します。
4. 段の最後の単位の CI が成功した時点で、その段を完了とします。
