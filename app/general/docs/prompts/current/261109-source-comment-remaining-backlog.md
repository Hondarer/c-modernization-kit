## BL-008 確認できない設計理由を推測で補わず引き継ぐ

元の 187 項目のうち、14 項目は現行で元報告の問題を確認せず、5 項目を理由コメントの対象、2 項目を他課題との一体対処に分類しました。  
残る 166 項目は、理由の根拠を確定していない引き継ぎ候補です。  
これは修正済み件数ではなく、仕様策定時点の分類です。

対象には、argparser の表示開始列 28 とバッファー容量 512、pinned prompt の未設定行 9999、ロック解放の失敗を無視する方針、Windows のコンソール・UAC・ETW の説明の根拠などが含まれます。  
数値に名前を付けたことや、実装が移動したことだけでは、値の選定理由や失敗を処理しない理由まで確認できたとは扱いません。

今回の見送り理由は、根拠を確認できる項目から対処し、確認できない項目は引き継ぐというユーザーの回答です。  
推測の理由をコメントへ追加すると、将来の保守者がそれを契約や OS の仕様として扱うおそれがあります。  
後続の対処では、対象関数の契約、仕様、実装上の依存関係を照合し、確認できなければ設計者へ理由または変更方針を確認します。

最終整理では、元の列挙順に付けた枝番号 001〜187 と、報告時のパス・行番号・報告内容を対応付けます。  
各残件に、現行の対象関数、確認した事実、根拠の未確認点、次に必要な確認を記載します。  
今回の作業内で解消した項目は、この残課題一覧の最終版から除外します。

## BL-025 TCP 双方向 N:1 通信の判断と実装を先送りする

公開の通信種別には、過去に予定として `POTR_TYPE_TCP_BIDIR_N1 = 11` がコメントで残っていました。  
その無効なコードはすでに削除されており、この予定は実装済みの機能ではありません。  
今回の見送りは「機能を追加しない」という恒久的な採否の決定でもありません。

ユーザーは、実施要否の判断と対処をともに残課題として先送りするよう回答しました。  
実施する場合は利用目的、要求元、接続関係、送信先の識別、切断時の扱い、公開 API と列挙値の互換性を確認してから設計します。  
Linux と Windows の検証方法も別途定めます。  
利用目的が決まらないまま列挙子だけを復活させると、利用者が実装済みと誤認するおそれがあります。
