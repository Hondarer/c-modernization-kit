## BL-005 trace_file のローカル ロック解放結果が未処理

### 概要と問題点

- **現状の事象**: `app/cplat/prod/libsrc/cplat/trace/backends/file/trace_file.c` の `sink_registry_unlock()` は `cplat_local_lock_unlock()` の結果を確認しません。また、`cplat_internal_trace_file_sink_write_text()` はファイルを開き直せない場合にローカル ロックを解放しますが、その結果を確認せず `CPLAT_ERR_UNKNOWN` を返します。
- **本来あるべき姿**: ローカル ロックの解放失敗を見逃さず、各呼び出し元の戻り値契約に沿って失敗を伝達するか、安全に続行できない場合は異常状態として扱います。

### 経緯と見送り理由

- **摘出契機**: 第 3 バッチで `trace_file.c` の共有ローテーションにおけるプロセス間ロック解放失敗を処理する際、同じファイル内に残るローカル ロック解放の未処理を確認しました。
- **今回の見送り理由**: 承認済みの BL-002 は `pinned_prompt.c`、`pinned-prompt.c`、`string-catalog-filter-sample.c` の 13 組に限定されています。本項目の修正には、レジストリ解放ヘルパーとその複数の呼び出し元の戻り値契約を別途設計する必要があるため、範囲を広げませんでした。

### 影響範囲とリスク

- **影響対象**: `sink_registry_unlock()` を使う sink レジストリ処理と、`cplat_internal_trace_file_sink_write_text()` の再オープン失敗経路です。
- **放置した場合のリスク**: ローカル ロック解放が失敗しても呼び出し元へ伝わらず、後続処理の排他状態を誤認したり、同じロックを待つ処理が停止したりする可能性があります。

### 推奨される対応策

- **恒久対応案**: `sink_registry_unlock()` の結果を返す形にし、レジストリ操作の各呼び出し元で既存の戻り値に反映します。再オープン失敗時もロック解放結果を確認し、元の失敗と解放失敗の双方を安全に扱う経路を定めます。
- **参考情報**: `app/cplat/prod/include/cplat/sync/sync.h`、`app/cplat/prod/libsrc/cplat/trace/backends/file/trace_file.c`、[第 3 バッチの最終仕様](261115-source-comment-bl002-batch3-design.md)。

## BL-006 sample_filter_share_lock_acquire の回復時にローカル ロック解放結果が未処理

### 概要と問題点

- **現状の事象**: `app/string-catalog-sample/prod/src/cmd/string-catalog-filter-sample/sample_filter_share_region.c` の `sample_filter_share_lock_acquire()` は、ローカル ロック取得後に時計取得またはプロセス間ロック取得が失敗した場合、ローカル ロックの解放結果を破棄します。コメントは「取得に成功したロックの解放は失敗しない」と説明しますが、`sync.h` は OS のロック解除失敗時に `CPLAT_ERR_UNKNOWN` を返すと記載しています。
- **本来あるべき姿**: 回復経路でもローカル ロック解放の失敗を見逃さず、元の取得失敗との優先順位を定めたうえで結果を呼び出し元へ伝えます。

### 経緯と見送り理由

- **摘出契機**: 第 3 バッチで同じファイルの `sample_filter_share_lock_release()` におけるプロセス間ロック解放を修正し、同期 API の宣言を照合した際に確認しました。
- **今回の見送り理由**: 承認済み BL-002 は指定された 13 組に限定されており、本項目は異なる回復経路です。時計取得失敗とプロセス間ロック取得失敗が重なった場合に返す結果を新たに決める必要があるため、範囲を広げませんでした。

### 影響範囲とリスク

- **影響対象**: `sample_filter_share_lock_acquire()` の時計取得失敗後とプロセス間ロック取得失敗後のクリーンアップです。
- **放置した場合のリスク**: ローカル ロック解放が失敗しても元の時計またはプロセス間ロック取得エラーだけが返り、同じハンドルを使う後続スレッドがロック解放を待ち続ける可能性があります。

### 推奨される対応策

- **恒久対応案**: 2 つの回復経路でローカル ロック解放結果を取得し、元の失敗と解放失敗を呼び出し元へどう表現するかを決めて実装します。成功時の既存結果コードとタイムアウト動作は維持します。
- **参考情報**: `app/cplat/prod/include/cplat/sync/sync.h` の `cplat_local_lock_unlock()` 契約、`app/string-catalog-sample/prod/src/cmd/string-catalog-filter-sample/sample_filter_share_region.c`。
