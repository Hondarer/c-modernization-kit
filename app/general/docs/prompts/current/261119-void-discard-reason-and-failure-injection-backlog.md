## BL-001 override-sample の使い方の表示と終了の直前の検査に失敗時のテストがない

### 概要と問題点

- **現状の事象**: この案件で、`app/override-sample/prod/src/cmd/override-sample/override-sample.c` の `main` の `--help` の経路に使い方の表示の関数の戻り値と標準出力の検査 (最終仕様の S-016) を、終了の直前に標準出力の `fflush` の戻り値と `ferror` の検査 (S-017) を追加しました。これらの検査の失敗時の動作を確かめるテストがありません。既存の `override-sampleTest` はコマンドを子プロセスとして起動する形で、mock で失敗を注入できず、標準出力の書き込みを失敗させる手段もテストの仕組みにありません。
- **本来あるべき姿**: 失敗時だけ動作が変わる変更のすべてに、失敗を起こして動作を確認するテストがある状態です。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (検討用 Markdown の Q-050 の回答 A、2026-11-19)。
- **今回の見送り理由**: テストの構成を、子プロセスの起動からソースの組み込みへ作り替える必要があります。`main` は実行時に読み込むライブラリ (`base`) を使うため、組み込んだテストでは `--help` 以外の経路を実行しにくい状態です。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `remaining-backlog-items` (検討 ID: `remaining-backlog-items-20261123`、全体管理文書: `261123-remaining-backlog-items-overview.md`) で検討を開始しました。2026-11-23 09:24 JST に、継続案件の検討用 Markdown の回答で、対策の方針が決まりました (継続案件の簡易 ADR の LADR-006)。 2026-11-24 に、`main` を組み込み、mock で使い方の表示、`fflush`、`ferror` の失敗を注入するテスト `override-sampleIoTest` (7 件) を加えました (ルートのコミット `de529eb3`)。Windows で 7 件が成功しました。Linux の CI の結果は確認中です。

### 影響範囲とリスク

- **影響対象**: `app/override-sample/test/src/cmd/override-sampleTest`、`override-sample.c` の `main`。
- **放置した場合のリスク**: 終了の直前の検査が後の変更で壊れても、テストで検出できません。

### 推奨される対応策

- **恒久対応案**: (1) `override-sample.c` を `USE_WRAP_MAIN` で組み込む新しいテストを作り、`--help` の経路で `fflush` と `ferror` の mock を使う。(2) テストの仕組み (`framework/testfw` の `ProcessOptions`) に、子プロセスの標準出力を書き込めない出力先 (Linux の `/dev/full` など) へつなぐ項目を追加する。のどちらかを比べて選びます。
- **参考情報**: 検討用 Markdown の Q-036、Q-050。先例は `app/struct-meta/test` の `structMetaSampleIoTest`。

## BL-002 porter の REJECT を受けた経路で割り込みの PING を送るべきかを決める

- **本来あるべき姿**: REJECT を受けた経路で割り込みの PING を送るかどうかが、設計文書と機能仕様で決まり、実装がそれに従っている状態です。

### 経緯と見送り理由

- **今回の見送り理由**: 通信の動作の変更であり、仕様の確認と通信のテストが要ります。戻り値の扱いをそろえるこの案件とは目的が異なります。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `remaining-backlog-items` (検討 ID: `remaining-backlog-items-20261123`、全体管理文書: `261123-remaining-backlog-items-overview.md`) で検討を開始しました。2026-11-23 09:24 JST に、継続案件の検討用 Markdown の回答で、対策の方針が決まりました (継続案件の簡易 ADR の LADR-007)。

- **放置した場合のリスク**: REJECT を受けた後、相手の状態の確認が次のヘルス チェックの周期まで遅れる可能性があります。サブエージェントの調査では、設計文書の記載からは、この経路でもスレッドを起こすのが整合するという報告です。エージェントは設計文書を読んで確認していません。

## BL-003 porter の設定で、解釈できない値の一部が知らせなく既定値になる

- **今回の見送り理由**: この案件の対象は戻り値の破棄の箇所です。3 種類は書き方が異なり、対象の洗い出しをしていません。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `remaining-backlog-items` (検討 ID: `remaining-backlog-items-20261123`、全体管理文書: `261123-remaining-backlog-items-overview.md`) で検討を開始しました。2026-11-23 09:39 JST に、継続案件の検討用 Markdown の回答で、既知のキーの解釈できない値をすべて設定の誤りとして読み込みを失敗させる方針が決まりました (継続案件の簡易 ADR の LADR-031)。設定の確認用 CLI の作成も、継続案件の対象に加わりました (LADR-036)。 2026-11-24 に、対策の前提になる `app/cjson` の側 (JSONC の解析の結果の種別と位置を返す `cJSON_ParseJSONCWithLengthOpts()`、確保した領域の解放の前の消去、解析の共通ロック) を実装しました (`app/cjson` のコミット `8c7fe2d`、ルートのコミット `52422d1e`)。`app/porter` の側 (設定の誤りの結果コード、検証の作り直し、公開関数、確認用 CLI) は未着手です。

## BL-004 cplat のトレースのファイルを、ローテーションの後に開けないと書き込みが失敗し続ける

### 概要と問題点

- **現状の事象**: `app/cplat/prod/libsrc/cplat/trace/backends/file/trace_file.c:542` は、単一プロセスのモードで、ローテーションの後に新しいファイルを開く `open_file_truncate()` の結果を使っていません。531 行のコメントは「失敗しても未オープンのまま続行する」としています。サブエージェントの調査では、開き直す処理がないため、それ以後の書き込みは失敗し続けるという報告です。開き直す処理がないことは、エージェントは確認していません。
- **本来あるべき姿**: 一時的な失敗 (ディスクの空き不足など) の後に、トレースの出力が回復する状態です。

### 経緯と見送り理由

- **摘出契機**: 実装の前の調査で発見 (2026-11-19)。
- **今回の見送り理由**: 戻り値の扱いではなく、回復の処理の設計の問題です。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `remaining-backlog-items` (検討 ID: `remaining-backlog-items-20261123`、全体管理文書: `261123-remaining-backlog-items-overview.md`) で検討を開始しました。2026-11-23 09:24 JST に、継続案件の検討用 Markdown の回答で、対策の方針が決まりました (継続案件の簡易 ADR の LADR-008)。

### 影響範囲とリスク

- **影響対象**: `trace_file.c` の書き込みとローテーション。`cplat` のトレースを使うすべての app。
- **放置した場合のリスク**: 一時的な失敗の後、プロセスの終了までトレースが残りません。

### 推奨される対応策

- **恒久対応案**: 未オープンの状態で書き込みを受けたときに開き直す処理を加え、失敗時の再試行の間隔を決めます。
- **参考情報**: 先行案件の枝番号 110 (`traceFileCoverageTest.rotation_reports_close_failure_and_continues`)。

## BL-016 makefw が、app の並列数と各 app の並列度で 1 つの上限を共有しない

### 概要と問題点

- **現状の事象**: `app/makefile` (`framework/makefw/makefiles/__app_template.mk` の複製) の既定のターゲットは、make の並列度と同じ数の app を同時にビルドします。各 app の make も同じ並列度で動くため、同時に動くコンパイルとリンクは、最大で並列度の 2 乗になります。並列度 4 の CI では、`cplat` の後に複数の app を同時にビルドする区間で、コンパイルが最大 11 プロセス並びました。この区間で、ランナー (メモリ 16 [GB]) の空きメモリが 823 [MB]、スワップの空きが 13 [MB] まで減り、ol8 と ol10 のランナーが停止しました (exit 137)。
- **本来あるべき姿**: app の並列数と各 app の並列度が、1 つの上限 (`MAKEFW_CPU_BUDGET`) を共有し、同時に動くコンパイルとリンクが上限を超えない状態です。

### 経緯と見送り理由

- **摘出契機**: この案件の CI の回復で発見 (2026-11-20、run 44635072105 と 44674074388 のメモリの記録)。
- **今回の見送り理由**: CI の回復には、同時にビルドする app の数を指定する `MAKEFW_APP_BUILD_JOBS` (`framework/makefw` の `f38074d`。未指定なら従来どおり) を足し、Linux の CI で 1 を指定して対処しました。上限を共有する変更は makefw の並列化の設計に関わり、この案件の範囲の外です。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `remaining-backlog-items` (検討 ID: `remaining-backlog-items-20261123`、全体管理文書: `261123-remaining-backlog-items-overview.md`) で検討を開始しました。2026-11-23 09:24 JST に、継続案件の検討用 Markdown の回答で、対策の方針が決まりました (継続案件の簡易 ADR の LADR-014)。

### 影響範囲とリスク

- **影響対象**: `app/makefile` の既定のターゲットを使う、すべてのビルド。メモリの少ない環境と、mock を使うテストのようにコンパイル 1 つあたりのメモリが大きい app。
- **懸念されるリスク**: `MAKEFW_APP_BUILD_JOBS` を指定しない環境では、同じメモリ不足が起こり得ます。指定した環境では、app を 1 つずつビルドするため、app の間の並列化の効果を使えません。

### 推奨される対応策

- **次回以降の対応方針**: 外側の make のジョブ サーバーを各 app の make へ引き継ぐ方法、または app の並列数に応じて各 app の並列度を割り振る方法を検討します。`run_ordered_subdir_target.sh` は、各 app の起動の前に `MAKEFLAGS` を消しており、ジョブ サーバーを引き継いでいません。
- **完了の定義 (DoD)**: 既定の設定で、同時に動くコンパイルとリンクが `MAKEFW_CPU_BUDGET` から決まる上限を超えないこと。CI の `MAKEFW_APP_BUILD_JOBS` の指定を外しても、Linux の 3 つのジョブが成功すること。
