## BL-001 override-sample の使い方の表示と終了の直前の検査に失敗時のテストがない

### 概要と問題点

- **現状の事象**: この案件で、`app/override-sample/prod/src/cmd/override-sample/override-sample.c` の `main` の `--help` の経路に使い方の表示の関数の戻り値と標準出力の検査 (最終仕様の S-016) を、終了の直前に標準出力の `fflush` の戻り値と `ferror` の検査 (S-017) を追加しました。これらの検査の失敗時の動作を確かめるテストがありません。既存の `override-sampleTest` はコマンドを子プロセスとして起動する形で、mock で失敗を注入できず、標準出力の書き込みを失敗させる手段もテストの仕組みにありません。
- **本来あるべき姿**: 失敗時だけ動作が変わる変更のすべてに、失敗を起こして動作を確認するテストがある状態です。

### 経緯と見送り理由

- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `remaining-backlog-items` (検討 ID: `remaining-backlog-items-20261123`、全体管理文書: `261123-remaining-backlog-items-overview.md`) で検討を開始しました。2026-11-23 09:24 JST に、継続案件の検討用 Markdown の回答で、対策の方針が決まりました (継続案件の簡易 ADR の LADR-006)。 2026-11-24 に、`main` を組み込み、mock で使い方の表示、`fflush`、`ferror` の失敗を注入するテスト `override-sampleIoTest` (7 件) を加えました (ルートのコミット `de529eb3`)。Windows で 7 件が成功しました。Linux の CI の結果は確認中です。 2026-11-25 の CI (コミット m09a73\、実行 45552671556) で、Windows と Linux (ol8、ol9、ol10) のすべてのジョブが成功し、警告のアーティファクトがないことを確かめました。

## BL-002 porter の REJECT を受けた経路で割り込みの PING を送るべきかを決める

### 概要と問題点

- **現状の事象**: `app/porter/prod/libsrc/porter/thread/thread_recv_window.c:607` (REJECT を受けた経路) は、`thread_recv_set_all_path_ping_states()` の戻り値 (経路の状態が変わったか) を使っていません。ヘルス チェックのタイムアウトの経路 (`thread_recv_health.c`) は、この値を使い、1 対 1 の双方向の通信で割り込みの PING を送るためにヘルス チェックのスレッドを起こします。この案件では、607 行の戻り値を明示的な破棄とし、理由コメントを付けました。
- **本来あるべき姿**: REJECT を受けた経路で割り込みの PING を送るかどうかが、設計文書と機能仕様で決まり、実装がそれに従っている状態です。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (検討用 Markdown の Q-054 の回答 A、2026-11-19)。
- **今回の見送り理由**: 通信の動作の変更であり、仕様の確認と通信のテストが要ります。戻り値の扱いをそろえるこの案件とは目的が異なります。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `remaining-backlog-items` (検討 ID: `remaining-backlog-items-20261123`、全体管理文書: `261123-remaining-backlog-items-overview.md`) で検討を開始しました。2026-11-23 09:24 JST に、継続案件の検討用 Markdown の回答で、対策の方針が決まりました (継続案件の簡易 ADR の LADR-007)。 2026-11-24 に、一部を実装しました。REJECT を受けて受信の状態を破棄した場合と、受信通知キューの容量超過で切断した場合に、経路の状態の変化を戻り値で返し、双方向 UDP (1 対 1 と N 対 1) で、受信の側からヘルス チェックのスレッドを起こす形にしました。N 対 1 では、`peers_mutex` を解放した後に起こします。FIN による状態の変化、片方向、RAW、状態の変化がない場合、無視する REJECT では、割り込みの PING を要求しません。`dispatch_fin()` などのコメントを、「FIN による経路の状態の変化では割り込みの PING を要求しないため 0 を返す」という動作に合わせました (BL-007)。dispatch の戻り値は、状態の変化の真偽値 (0 または 1) に統一し、致命的な失敗は戻り値ではなく `fatal_error` で伝えます。設計文書 (`docs/health-check.md`、`docs/sequence-bidir.md`) と機能仕様 (`docs/functional-spec/delivery.md`、`health.md`) へ反映しました。あわせて、N 対 1 で FIN の発火の後に、解放済みの peer を参照していた箇所を直しました (`app/porter` のコミット `e19365b`)。Windows では、`app/cplat` と `app/porter` のビルドと全体のテストが成功しました。Linux は、WSL (Oracle Linux 8) で、ビルドと、関わるテストの成功を確かめました。CI (コミット `5542b692`) の結果は、まだ確かめていません。残る対処として、割り込みの PING の要求の保持と消費 (`health_send_pending`)、ヘルス チェックの同期の資源の寿命、停止との競合、既存の起床と開始の時の即時の送信の統一は、継続案件の項目「非ブロッキング通信と待機の解除による安全な停止」と同時に実装します。 2026-11-24 から 2026-11-25 にかけて、残っていた部分を実装しました。割り込みの PING の要求を、経路ごとに `health_send_pending` へ保持し、ヘルス チェックのスレッドが、状態の読み取りの前に消費します。消費の後に届いた要求も保持します。既存の起床、受信の期限の超過、開始の時の即時の送信を、同じ仕組みへ統一しました。ヘルス チェックの同期の資源の破棄を、すべての利用者の終了の後の共通の解放へ移し、停止と起床の競合で、破棄済みの資源を使わないようにしました (`app/porter` のコミット `c31c66c`)。 Windows では、各 app の全体のテストが成功しました。Linux は、WSL (Oracle Linux 8) で、ビルドと全体のテストの成功を確かめました (`app/porter` 962 件、`app/cplat` 2285 件)。Windows だけで書かれた Linux の側のテストと、GCC の警告は、WSL で確かめて直しました。 CI の結果は、まだ確かめていません。 2026-11-25 の CI (コミット m09a73\、実行 45552671556) で、Windows と Linux (ol8、ol9、ol10) のすべてのジョブが成功し、警告のアーティファクトがないことを確かめました。

### 影響範囲とリスク

- **影響対象**: `thread_recv_window.c`、`thread_recv_health.c`、設計文書 `app/porter/docs` の `health-check.md` (68 から 70 行付近)。
- **放置した場合のリスク**: REJECT を受けた後、相手の状態の確認が次のヘルス チェックの周期まで遅れる可能性があります。サブエージェントの調査では、設計文書の記載からは、この経路でもスレッドを起こすのが整合するという報告です。エージェントは設計文書を読んで確認していません。

### 推奨される対応策

- **恒久対応案**: 設計文書 `health-check.md` の割り込みの PING の条件を読み、REJECT の経路を含めるかを決めます。含める場合は、状態が変わったときにヘルス チェックのスレッドを起こし (`potr_internal_health_thread_wake()`)、通信のテストを追加します。含めない場合は、設計文書に例外として記載し、607 行の理由コメントをその記載に合わせます。
- **参考情報**: 検討用 Markdown の Q-054。FIN を受けた経路 (`thread_recv_fin.c:139`) は、相手が閉じた後なので対象外です。

## BL-016 makefw が、app の並列数と各 app の並列度で 1 つの上限を共有しない

### 概要と問題点

- **現状の事象**: `app/makefile` (`framework/makefw/makefiles/__app_template.mk` の複製) の既定のターゲットは、make の並列度と同じ数の app を同時にビルドします。各 app の make も同じ並列度で動くため、同時に動くコンパイルとリンクは、最大で並列度の 2 乗になります。並列度 4 の CI では、`cplat` の後に複数の app を同時にビルドする区間で、コンパイルが最大 11 プロセス並びました。この区間で、ランナー (メモリ 16 [GB]) の空きメモリが 823 [MB]、スワップの空きが 13 [MB] まで減り、ol8 と ol10 のランナーが停止しました (exit 137)。

### 経緯と見送り理由

- **摘出契機**: この案件の CI の回復で発見 (2026-11-20、run 44635072105 と 44674074388 のメモリの記録)。
- **今回の見送り理由**: CI の回復には、同時にビルドする app の数を指定する `MAKEFW_APP_BUILD_JOBS` (`framework/makefw` の `f38074d`。未指定なら従来どおり) を足し、Linux の CI で 1 を指定して対処しました。上限を共有する変更は makefw の並列化の設計に関わり、この案件の範囲の外です。
- **継続作業での経緯と対処**: 2026-11-23 に、継続案件 `remaining-backlog-items` (検討 ID: `remaining-backlog-items-20261123`、全体管理文書: `261123-remaining-backlog-items-overview.md`) で検討を開始しました。2026-11-23 09:24 JST に、継続案件の検討用 Markdown の回答で、対策の方針が決まりました (継続案件の簡易 ADR の LADR-014)。 2026-11-24 から 2026-11-25 にかけて、`app/makefile` の runner が、コンパイルの予算 (既定は CPU の数の半分の切り上げ) を、同時に起動する app へ割り振り、環境変数 `MAKEFW_APP_COMPILE_BUDGET` で各 app の make へ渡すようにしました。完了した app の予算は、後続の app へ回します。明示の並列の設定がある場合は、割り振りを行いません。Windows のルートのビルドで、同時に起動した 6 つの app へ 6 ずつ、単独の `cplat` へ 36 が渡されることを確かめました。この変更で、CI の Windows (4 CPU) の app ごとの並列度が 1 になり、以前からあった順序の不具合 (MSVC の一括コンパイルが、生成ヘッダーの生成を待たずに始まる) が表に出たため、あわせて直しました (`framework/makefw` のコミット `b7e48cb`、`b6b701c`、ルートのコミット `8b4413a5`、`dd6fbda8`)。 CI の結果は、まだ確かめていません。 2026-11-25 の CI (コミット m09a73\、実行 45552671556) で、Windows と Linux (ol8、ol9、ol10) のすべてのジョブが成功し、警告のアーティファクトがないことを確かめました。

### 影響範囲とリスク

- **影響対象**: `app/makefile` の既定のターゲットを使う、すべてのビルド。メモリの少ない環境と、mock を使うテストのようにコンパイル 1 つあたりのメモリが大きい app。
- **懸念されるリスク**: `MAKEFW_APP_BUILD_JOBS` を指定しない環境では、同じメモリ不足が起こり得ます。指定した環境では、app を 1 つずつビルドするため、app の間の並列化の効果を使えません。

### 推奨される対応策

- **次回以降の対応方針**: 外側の make のジョブ サーバーを各 app の make へ引き継ぐ方法、または app の並列数に応じて各 app の並列度を割り振る方法を検討します。`run_ordered_subdir_target.sh` は、各 app の起動の前に `MAKEFLAGS` を消しており、ジョブ サーバーを引き継いでいません。
- **完了の定義 (DoD)**: 既定の設定で、同時に動くコンパイルとリンクが `MAKEFW_CPU_BUDGET` から決まる上限を超えないこと。CI の `MAKEFW_APP_BUILD_JOBS` の指定を外しても、Linux の 3 つのジョブが成功すること。
