### Q-001 適用対象とするソース ファイルの範囲

**Question**

トップ ダウン記載の規範および機械的チェックの適用対象とするソース ファイルの範囲を、どこまでとしますか。

**Context**

- **経緯と背景**: 現在の `app/` 配下には、第一者管理の C/C++ ソースと、外部由来の OSS (`lua`、`sqlite`、`cjson`、`openssl`、`zlib`) が混在しています。また、各 app 内には製品コード (`prod/`) と Google Test / Google Mock ベースの単体テスト (`test/`) があります。
- **事前調査の結果**:
    - 外部 OSS (`lua`、`sqlite`、`cjson`、`openssl`、`zlib`) はルート `AGENTS.md` および `coding-guideline.md` により手動改変の対象外です。
    - 非 OSS の `app/*/prod/` には C/C++ ソースが合計 252 ファイルあります (`.c` が 250 ファイル、`.cc`/`.cpp` が 2 ファイル: `porter-bench.cc` 等)。

### Q-003 機械的チェックの実現方式

**Status**

解決済み

**Question**

トップ ダウン記載 (前方プロトタイプ宣言の必須化、順序一致、主たる関数の先頭配置) を機械的にチェックする主手段として、どの方式を採用しますか。

**Context**

- **経緯と背景**: ご依頼では「`app/makepart.mk` への GCC 向けフラグ追加」および「MSVC での機械的チェックのアイデア」について検討を求められました。これについて GCC 8.5.0 の実機および `app/makepart.mk`、`framework/makefw/makefiles/_flags.mk` を調査したところ、次の技術的事実が判明しました。
- **根拠資料と検証事実**:
    1. `app/makepart.mk` ([app/makepart.mk](file:///home/user/c-modernization-kit/app/makepart.mk#L12-L15)) には、すでに GCC 向け C 専用警告として `-Wmissing-prototypes`、`-Wstrict-prototypes`、`-Wmissing-declarations` が設定されています。
    2. しかし GCC の `-Wmissing-prototypes` と `-Wmissing-declarations` は **外部リンケージ (非 `static`) 関数のみ** を対象としており、**`static` 関数のプロトタイプ未宣言やボトム アップ配置には一切警告を出しません**。手元の GCC 8.5.0 で次のコードを `-Wall -Wextra -Wmissing-prototypes -Wmissing-declarations -Wstrict-prototypes` でコンパイルしても警告 0 件でした。

```c
static int helper(void) { return 1; }
int main(void) { return helper(); }
```

    3. GCC 自体に `static` 関数の事前プロトタイプ宣言や関数定義の順序を強制する警告オプションは存在しません (`gcc --help=warnings` で確認済み)。
    4. **MSVC 側** にも同様に、関数の事前プロトタイプ宣言や定義順序を強制するコンパイラ警告オプションは存在しません。MSVC の関連警告には `C4013` (未宣言関数の呼び出し) と `C4255` (引数リストが空の `f()` に対するプロトタイプ欠如警告。`/Wall` 相当で既定オフ) がありますが、ボトム アップで「先に定義してから呼ぶ」場合は定義が宣言を兼ねるため `C4013` は発火せず、`C4255` も `()` と `(void)` の区別のみを検査します。
- **MSVC を含む両環境での機械的チェックのアイデア**:
    - このリポジトリには、すでに `app/general/bin/check_c_blank_lines.py` (コーディング規範「処理を区切る空行」の機械チェック) をはじめとする Python 製の規範チェッカー群があります。
    - コンパイラ フラグに頼らず、**OS 非依存の Python チェッカー (例: `app/general/bin/check_c_topdown.py`)** を新設すれば、Linux (GCC) と Windows (MSVC) の双方でまったく同じ基準により、前方プロトタイプ宣言の有無、宣言順と定義順の一致、主たる関数 (`main` / 公開 API) の先頭配置を機械的に検出できます。
    - あわせて MSVC 側の補助策として、`app/makepart.mk` の Windows 用 `CFLAGS` に `/w14255` (`C4255` をレベル 1 警告として有効化。GCC の `-Wstrict-prototypes` に相当) を追加する選択肢もあります (ただしトップ ダウン強制そのものではなく、引数 `(void)` 漏れ検出の Linux/Windows 均質化が目的です)。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) `app/general/bin/` に OS 共通の Python チェッカー (`check_c_topdown.py` 相当) を新設し、Linux (GCC) と Windows (MSVC) の双方で同一基準の機械的チェックを行う (`app/makepart.mk` は変更しない)。
- [ ] B: 案 A の Python チェッカーを新設し、あわせて補助策として `app/makepart.mk` の Windows (MSVC) 用 `CFLAGS` に `/w14255` (`-Wstrict-prototypes` 相当) を追加してプロトタイプ記述の警告を均質化する。
- [ ] C: 機械的チェッカーは作成せず、コーディング規範の明文化とコード レビューのみで運用する。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足: CI 時間が非常に長くなる懸念があるので、チェッカーは CI ごとに実施するものとせず、任意のタイミング規範に合致しているかをチェックする用途としたい。(実際の時間を計測したうえで最終評価を行う)

回答者: Tetsuo Honda  
回答日時: 2026-11-25 21:24:15 JST

**Assessment**

案 A の選択および補足コメントを確認しました。`app/makepart.mk` は変更せず、`app/general/bin/` に OS 共通の Python チェッカー (`check_c_topdown.py`) を新設します。補足にある「CI ごとには実施せず任意タイミングで実行」「実際の実行時間を計測して最終評価を行う」は [Q-005](#q-005-機械的チェックの実行タイミング) の選択 A とも完全に整合しているため、全対象 250 ファイルに対するチェッカー実行時間の計測と報告を受入条件に組み込みます。

**Recommendation**

推奨: A  
優先した基準: GCC / MSVC 双方での確実な検出、リポジトリ既存のチェッカー運用 (`check_c_blank_lines.py` 等) との一貫性、および変更影響の局所化を優先しました。  
理由: GCC・MSVC ともにコンパイラ警告だけでは `static` 関数のボトム アップ配置を検出できないため、Python チェッカーが唯一確実に両環境で機能する機械的チェック手段です。案 B の `/w14255` 追加は有用ですが、Windows 側のシステム ヘッダーや既存コードで新たな警告が出ないか実機確認が必要になるため、まずはトップ ダウン検査の本丸に集中する A を推奨します (Windows ビルドでの `/w14255` 検証も含めて進める場合は B を選択してください)。

### Q-004 機械的チェックの検査項目と厳格度

**Status**

解決済み

**Question**

機械的チェッカーを導入する場合 ([Q-003](#q-003-機械的チェックの実現方式) で A または B を選択した場合)、違反 (終了コード 非 0) として検出する検査項目の範囲をどこまでとしますか。

**Context**

- **経緯と背景**: トップ ダウン記載の規則には、構文から決定論的に判定できる項目と、設計意図に依存する項目があります。
- **検査候補の整理**:
    1. **`static` 関数の前方プロトタイプ宣言の必須**: 翻訳単位内のすべての `static` 関数定義に対し、最初の関数定義より前の宣言セクションにプロトタイプ宣言が存在すること (決定論的)。
    2. **宣言順と定義順の一致**: 宣言セクションに並んだ `static` 関数の順序と、後続の `static` 関数定義の順序が一致していること (決定論的)。
    3. **主たる関数の先頭配置**: `main()` を持つファイルでは `main()` が最初の関数定義であること、またライブラリやモジュールでは非 `static` 関数 (公開 API・内部共有関数) が `static` 関数より前に定義されていること (決定論的)。
    4. **呼び出し方向のトップ ダウン度**: 関数 A が同一ファイル内の `static` 関数 B を呼ぶ場合、A が B より前に定義されていること (相互再帰や複数箇所から呼ばれる共通ユーティリティの配置、関数ポインター経由のコールバックなどでは例外が生じ得る)。
- **各案の違い**:
    - 案 A: 決定論的に判定できる 1〜3 を違反 (エラー) とし、4 の呼び出し順や凝集度に基づく細かな並び順は規範の指針＋レビュー (または任意の参考警告) に委ねます。誤検知が少なく運用しやすい構成です。
    - 案 B: 1 と 3 のみをエラーとし、2 (宣言順と定義順の一致) は警告またはレビュー確認にとどめます。
    - 案 C: 1〜4 すべてをエラーとし、相互再帰などの例外はソース内の明示コメントで抑止します。

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 項目 1 (`static` 関数の前方宣言必須)、項目 2 (宣言順と定義順の一致)、項目 3 (主たる関数 `main` / 非 `static` 関数を `static` 関数より前に配置) を違反 (エラー) とし、項目 4 (呼び出し方向の逆転) はエラーにしない。
- [x] B: 項目 1 (`static` 関数の前方宣言必須) と項目 3 (主たる関数の先頭配置) のみを違反 (エラー) とし、項目 2 (宣言と定義の順序一致) は警告またはレビュー確認とする。
- [ ] C: 項目 1〜4 すべてを違反 (エラー) とし、相互再帰などの正当な例外は専用コメントで抑止する。
- [ ] D: その他 (Q-003 で C を選んだ場合は対象外)
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足: 主たる関数とは include または include_internal または main のような、ファイル内にプロトタイプがないものを指すと理解している。

**Assessment**

案 B の選択および補足コメントを確認しました。

- 補足コメントの「主たる関数とは `include` または `include_internal` または `main` のような、ファイル内にプロトタイプがないもの」は、本リポジトリの C 構成 (GCC の `-Wmissing-prototypes` により `main` 以外の外部リンケージ関数は必ずヘッダーに宣言がある) と完全に整合しており、構文上「非 `static` の外部リンケージ関数 (`main`、公開 API、ライブラリ内・モジュール内共有関数)」と一意に一致します。認識のずれはありません。
