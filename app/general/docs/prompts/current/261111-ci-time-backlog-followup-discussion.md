### Q-001 CI の並列度の引き上げ

**Status**

解決済み

**Question**

BL-001 の対策として、CI のビルドとテストのジョブで、make の並列度を 2 から 4 に上げますか。

**Context**

CI のランナーは 4 論理 CPU ですが、makefw の自動設定により `make -j2` で動いています。  
makefw は、開発者の PC でほかの作業を妨げないことと、メモリ不足を避けることを目的に、CPU の半分だけを使う設計です。CI のランナーはビルド専用なので、この配慮は不要です。

`ci.yml` で環境変数 `MAKEFW_CPU_BUDGET` を 8 に指定すると、makefw の式は変えずに、Linux と Windows の両方で `make -j4` になります。makefw 本体は変更しません。

```yaml
# 案 A: ci.yml のビルドとテストのジョブに追加する
env:
  # ランナーは 4 論理 CPU でビルド専用のため、CPU をすべて使う。
  # makefw は CPU 予算の半分をコンパイルに使うので、予算を 2 倍に指定する。
  MAKEFW_CPU_BUDGET: "8"
```

効果は手元で測定できません。コンパイルが時間の大半を占めるため、Build ステップは最大で半分程度になると見込みます。テストの実行 (`_test_run`) がどの程度短くなるかは未確認です。

懸念は、メモリの不足です。同時に動くコンパイラが 2 個から 4 個に増えます。Windows の MSVC には、ヒープ不足 (C1060) の実績があり、makefw に再試行の仕組みがあります。不足した場合は、ジョブが失敗するか、再試行で時間が延びます。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) Linux と Windows の両方で `MAKEFW_CPU_BUDGET` を 8 に指定する。実走でメモリ不足が起きた OS は、指定を外す。
- [ ] B: Linux だけ指定する。Windows は現状のままにする。
- [ ] C: 並列度は変えない。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

回答者: Tetsuo Honda  
回答日時: 2026-11-12 05:37:48 JST (ファイルの保存時刻)

**Recommendation**

推奨: A  
理由: 変更が `ci.yml` の数行で済み、makefw の設計と式を変えません。効果が最も大きいと見込む対策です。メモリ不足は実走でしか確認できないため、起きた OS だけ元に戻す条件を付けます。

**Assessment**

A で確定しました。回答後の検証で、次の 2 点を確認しました。

- 環境変数は、Build と Run tests の 2 つのステップだけに指定します。ジョブ全体に指定すると、`make bin-test` が実行する makefw のテストにも値が伝わり、テストの前提を変えるおそれがあるためです。
- `MAKEFW_CPU_BUDGET` を 8 にすると、コンパイルの並列度だけでなく、テストを同時に実行する数も 2 から 4 に変わります (`makemain.mk` の `test:` は、`MAKEFW_TEST_RUN_JOBS` の指定がなければ make の並列度を使います)。この点は質問の時点で示していなかったため、[Q-008](#q-008-テストを同時に実行する数) で確認します。

### Q-003 記録だけのコミットで CI を起動しない方法

**Question**

### Q-008 テストを同時に実行する数

**Status**

解決済み

**Question**

CI で、テストを同時に実行する数を、コンパイルの並列度とあわせて 2 から 4 に上げますか。

**Context**

[Q-001](#q-001-ci-の並列度の引き上げ) の回答を検証して、`MAKEFW_CPU_BUDGET` を 8 にすると、テストを同時に実行する数も 2 から 4 に変わることを確認しました。質問の時点では示していなかった影響です。

makefw の `make test` は、テストのビルド (`_test_build`) とテストの実行 (`_test_run`) の 2 段階で動きます。実行の段階で同時に動かすテストの数は、`MAKEFW_TEST_RUN_JOBS` の指定がなければ、make の並列度と同じ値になります。

```text
# framework/makefw/makefiles/makemain.mk の test:
test_run_jobs="$(MAKEFW_TEST_RUN_JOBS)"; \
if [ -z "$$test_run_jobs" ]; then test_run_jobs="$$jobs"; fi; \
```

同時に実行する数を増やすと、Run tests ステップが短くなります。一方で、4 論理 CPU のランナーで 4 つのテストが同時に動くため、待ち時間やタイムアウトを検証するテストが、CPU の取り合いで失敗するおそれがあります。失敗が時々しか起きない場合は、原因の切り分けに時間がかかります。

`MAKEFW_TEST_RUN_JOBS` を 2 に指定すると、コンパイルの並列度だけを 4 に上げ、テストの実行は現状のままにできます。

```yaml
# 案 A: テストの実行も 4 にする
env:
  MAKEFW_CPU_BUDGET: "8"
```

```yaml
# 案 B: テストの実行は 2 のままにする
env:
  MAKEFW_CPU_BUDGET: "8"
  MAKEFW_TEST_RUN_JOBS: "2"
```

Run tests ステップのうち、テストのビルドと実行がそれぞれ何分かは、ログが app ごとにまとめて出力されるため、確認できていません。

**Answer**

選択方式: 単一選択

- [x] A: テストの実行も 4 にする。テストがタイミングの原因で失敗した場合は、2 に戻す。
- [ ] B: (推奨) テストの実行は 2 のままにする (`MAKEFW_TEST_RUN_JOBS` を 2 に指定する)。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足: テスト タイミングそのものに左右されない構造になっているはず。ただしタイムアウトはありうるので結果を確認する必要がある。

回答者: Tetsuo Honda  
回答日時: 2026-11-12 06:02:36 JST (ファイルの保存時刻)

**Recommendation**

推奨: B  
理由: コンパイルの並列度の効果だけを測定でき、テストの失敗の原因を増やしません。[Q-002](#q-002-並列度の引き上げで足りない場合の追加の対策) で、対策を 1 つずつ測定する方針を選んでいることとも合います。テストの実行の同時数は、今回の測定結果を見てから、別の対策として判断できます。A は、短縮の幅が大きくなる可能性がありますが、どの程度かは未確認です。

**Related**

[Q-001](#q-001-ci-の並列度の引き上げ)、[Q-002](#q-002-並列度の引き上げで足りない場合の追加の対策)

**Assessment**

A で確定しました。推奨案 (B) とは異なる選択です。補足に従い、受入の確認に、テストのタイムアウトによる失敗がないことの確認を加えます。タイミングが原因でテストが失敗した場合は、`MAKEFW_TEST_RUN_JOBS` を 2 に指定して再コミットします。  
コンパイルとテストの実行を同時に変えるため、Build ステップと Run tests ステップの時間を分けて記録し、効果を区別できるようにします。[Q-007](#q-007-時間短縮の判定方法) の判定 (Build ステップの中央値との比較) は変わりません。
