## 回答後に確認した現物と残る調査

BL-012 の `app/cplat/prod/libsrc/cplat/clock/clock.c` では、時刻取得の 3 関数が `clock_gettime()` の戻り値を確認していません。  
`cplat_clock_get_monotonic_ms()` は値を返し、`cplat_clock_get_monotonic()` と `cplat_clock_get_realtime()` は戻り値が `void` です。  
いずれも結果コードによる失敗通知の経路がありません。  
porter の `potr_health_thread.c`、`potr_recv_thread.c` などは、単調増加時刻を期限や経過時間の計算に使っています。  
失敗時に単にゼロを返す案は、正常な時刻と区別できないため、採用を推奨しません。  
まず [Q-002](#q-002-時刻取得-api-のシグネチャ互換性) で互換性の条件を確認し、その回答に沿って失敗通知と呼び出し側の扱いを具体化します。

BL-010 の `app/struct-meta/prod/include/struct_meta/access/access.h` は、パス解決 2 関数の `field_out` に NULL を許可しています。  
`app/struct-meta/prod/libsrc/struct_meta/access/path.c` は、両関数で NULL を拒否します。  
契約と実装のどちらを維持するかは [Q-003](#q-003-パス解決の-field_out-を省略できる契約) です。

BL-012 の `trace_file.c` では、初回のロック生成結果を捨て、その後のロック取得へ渡しています。  
`potr_peer_table.c` でも、送信ウィンドウのロック生成結果を確認せず、後続のバッファー確保へ進みます。  
失敗時の解放、呼び出し側への通知、再試行の可否は追加調査が必要です。  
メモリ確保失敗を理由とする異常終了は、共通コーディング規範が禁止しているため、既定の対処にはしません。

BL-022 の生成元 `struct_meta_gen_emit.c` では、報告されたコメント文字列 6 件と、自動生成通知の別の出力箇所を確認しました。  
生成物への直接編集は行わず、生成元、設計文書の例、検証方法を照合します。  
BL-006 の重複関数は存在しますが、`app_lock_take()` は `operation` を引数に持ち、`interprocess_lock_take()` とシグネチャが異なります。  
共通化の前に、ロック種別と待機処理の差を確認します。  
指摘箇所の確認結果と修正案は、次のとおりです。  
「案」は未承認です。回答で決まる方針とともに最終仕様へまとめ、最終仕様の承認後に反映します。

### BL-006 の共通化は型とロック操作を維持する案です

`app_lock_open_identity()` と `interprocess_lock_open_identity()` は型以外の処理が一致します。  
取得処理は、前者が `operation` を受け取り、後者が `LOCK_EX` に固定する点を除いて同じ構造です。  
案は、ファイルのオープンと識別文字列の確保、ファイル記述子への `flock()` と期限待機をそれぞれ共通化し、型別のオブジェクト確保と `locked` 状態の更新を呼び出し側へ残すことです。  
異なる構造体へのキャストによる共通化は行わず、公開 API と結果コードは維持します。  
`syncTest` で共有・排他、無期限・即時・有限待機、シグナル中断と解放経路を確認します。
