## BL-001 makefw 製の第三者管理ライブラリのシンボル名の衝突

### 概要と問題点

- **現状の事象**: zlib、cjson、lua、sqlite の共有ライブラリには、SONAME もシンボル バージョンもありません。システムの同種ライブラリ (`libz.so.1` など) を読み込むプロセスに載ると、同名の関数 (`deflate` など) の呼び出しが、先に読み込まれた側へ束縛される可能性があります。
- **本来あるべき姿**: このワークスペースの第三者管理ライブラリを使う呼び出しが、同じプロセスにあるシステム側のライブラリと混ざらないことです。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (検討用 Markdown の Q-007)。
- **今回の見送り理由**: 今回の目的 (OpenSSL の共有ライブラリ化と mock の実委譲) には必要がなく、対策は makefw の機能追加になり、影響範囲が別であるためです。

### 影響範囲とリスク

- **影響対象**: `app/zlib`、`app/cjson`、`app/lua`、`app/sqlite` の共有ライブラリと、その利用側。
- **放置した場合のリスク**: システム側のライブラリを直接リンクした実行ファイルへ組み込んだ場合に、版の異なるライブラリの関数が呼ばれます。

### 推奨される対応策

- **恒久対応案**: makefw の共有ライブラリのリンクに、SONAME とバージョン スクリプトを付ける機能を追加します。
- **参考情報**: OpenSSL は `shlib_variant` により、シンボル バージョンを `OPENSSL_APP_<バージョン>` に変えて同じ問題を避けています。

## BL-002 第三者管理ライブラリの mock に呼び出し元情報がない

### 概要と問題点

- **現状の事象**: zlib、cjson、lua、sqlite の mock (`mock_zlib` など) は、公開関数と同じ名前の関数を定義する方式であり、`MOCK_METHOD` の引数に呼び出し元のファイル名、行番号、関数名がありません。テストで「どこから呼ばれたか」を検証できず、トレース出力にも呼び出し元が出ません。
- **本来あるべき姿**: testfw の標準ライブラリ mock や OpenSSL の mock と同じく、mock 関数の先頭 3 引数で呼び出し元のファイル名、行番号、関数名を受け取り、テストの検証に使えることです。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (検討用 Markdown の Q-011)。OpenSSL の mock を zlib などと同じ方式にそろえる案に対し、呼び出し元情報は検証に有効であり、ほかの mock にないことが問題であるとユーザーから指摘がありました。
- **今回の見送り理由**: 4 つの app の mock の方式変更と、利用側のテストの `EXPECT_CALL` の書き換えが必要であり、今回の目的 (名前の変更と OpenSSL の共有ライブラリ化) とは影響範囲が別であるためです。

### 影響範囲とリスク

- **影響対象**: `app/zlib`、`app/cjson`、`app/lua`、`app/sqlite` の `test/include/mock_*.h`、`mock_*_api_table.h`、`test/libsrc/mock_*/`、これらの mock を使う利用側のテスト、`app/general/docs/shared-library-mock-guideline.md`、`create-mock-shared-lib` スキル。
- **放置した場合のリスク**: 第三者管理ライブラリの mock の方式が、OpenSSL とそれ以外で分かれたままになります。呼び出し元による検証が必要なテストを書けません。

### 推奨される対応策

- **恒久対応案**: 各 app に `test/include_override/` の差し替えヘッダーを追加し、テスト対象の呼び出しをマクロで `mock_<関数名>(__FILE__, __LINE__, __func__, ...)` へ置き換えます。API 表のマクロに先頭 3 引数を加え、宣言、`MOCK_METHOD`、real delegate を同じ表から生成します。規範 (`shared-library-mock-guideline.md`) を、呼び出し元情報を持つ方式へ改めます。
- **参考情報**: 関数形式マクロによる置換は、関数ポインターとして渡す使い方 (`inflateInit` 系のコールバックや Lua の C 関数登録など) には効きません。対象の API ごとに、置換できない呼び出しの扱いを設計する必要があります。OpenSSL の mock の構成は `app/openssl/README.md` の「単体テスト用のモック」を参照してください。

## BL-003 OS 側が OpenSSL 3.x の環境での同居の確認

### 概要と問題点

- **現状の事象**: `libcrypto_app.so.3` と OS の libcrypto が同じプロセスに載る場合の動作は、OS 側が OpenSSL 1.1.1 の開発環境 (Oracle Linux 8) でだけ確認しています。OS 側が OpenSSL 3.x の環境 (Oracle Linux 9 以降など) では、ファイル名の版の番号 (`.so.3`) と関数名が OS 側と同じになりますが、この組み合わせでの動作は確認していません。
- **本来あるべき姿**: OS 側が OpenSSL 3.x の環境でも、`libcrypto_app.so.3` を使う呼び出しと OS の libcrypto を使う呼び出しが、それぞれ自分のライブラリの関数を呼ぶことを、実行して確認済みであることです。

### 経緯と見送り理由

- **摘出契機**: 事前検証と受入確認の中で、開発環境では確認できない組み合わせとして判明しました。
- **今回の見送り理由**: 開発環境の OS 側が OpenSSL 1.1.1 であり、OpenSSL 3.x の環境を用意する作業が今回の範囲に含まれないためです。設計上は、シンボル バージョンが `OPENSSL_APP_3.0.0` と `OPENSSL_3.0.0` で異なるため、呼び出しは混ざりません。

### 影響範囲とリスク

- **影響対象**: `app/openssl` の共有ライブラリと、それを使う `libcplat.so`、および `libcplat.so` を読み込む実行ファイル。
- **放置した場合のリスク**: 想定と異なる束縛が起きる環境があった場合に、配布後まで気付けません。

### 推奨される対応策

- **恒久対応案**: OS 側が OpenSSL 3.x の環境 (CI のコンテナーなど) で、OS の libcrypto を使う共有ライブラリと `libcrypto_app.so.3` を使う実行ファイルを同じプロセスに載せ、双方の `OpenSSL_version()` が自分の版を返すことを確認するテストを `app/openssl` に追加します。
- **参考情報**: `app/openssl/README.md` の「ライブラリの名前」、OpenSSL の `Configurations/README.md` の `shlib_variant`。
