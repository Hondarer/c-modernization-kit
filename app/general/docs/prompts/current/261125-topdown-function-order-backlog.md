## BL-001 移行前のファイルを部分的に編集する場合のチェッカーの扱い

### 概要と問題点

- **現状の事象**: 規範は、対象の `.c` を新規作成または編集した場合に、そのファイルに対して `check_c_topdown.py` を実行してエラーと警告を 0 件にすると定める。第 2 段の書き換え (`cplat`、`porter`) が終わるまでの間、移行前のファイルを数行だけ編集した場合も、ファイル全体の書き換えが必要になるのかが定まっていない。
- **本来あるべき姿**: 移行前のファイルの部分的な編集で、ファイル全体の書き換えを求めるか、編集した関数の範囲に限るか、移行の完了まで適用を猶予するかが規範に明記されている。

### 経緯と見送り理由

- **今回の見送り理由**: ユーザーの指示により、問い合わせずに規範の文言どおりに記載し、未確定の細部を残課題へ送った。
- **継続作業での経緯と対処**: なし

### 影響範囲とリスク

- **影響対象**: 第 2 段の完了までに `cplat`、`porter` を編集する作業
- **放置した場合のリスク**: 小さな修正に大規模な並べ替えが混ざり、レビューと統合の負担が増える。逆に適用を省くと規則が形骸化する。

### 推奨される対応策

## BL-004 複数の分岐にそれぞれ完全な実装を持つファイルとチェッカーの判定

### 概要と問題点

- **現状の事象**: 1 つの前処理の分岐の各分岐に、主たる関数とファイル内補助関数の完全な実装を持つファイル (2026-11-26 時点で `cplat` の `libsrc/cplat/console/console.c` と `src/cmd/etw-viewer/etw-viewer.c`。`#if defined(PLATFORM_WINDOWS)` と `#elif defined(PLATFORM_LINUX)` の各分岐に実装がある) は、`reorder_c_topdown.py` で各分岐の内側を並べ替えても、`check_c_topdown.py` の `non-topdown-order` が残る。チェッカーは最終仕様どおり前処理の条件を評価せず、すべての分岐を 1 つの並びとして扱うため、後の分岐の主たる関数が前の分岐のファイル内補助関数より後に来るためである。
- **本来あるべき姿**: 規範の「ファイル全体を 1 つの条件で囲むファイルでは、条件の内側で構成に従う」と、チェッカーの判定が両立し、該当するファイルもエラー 0 件にできる。

### 経緯と見送り理由

- **摘出契機**: 作業 WBS 4.1.3 で `reorder_c_topdown.py` を全対象の違反ファイル (154 ファイル) へ一時的に適用した試行 (2026-11-26、リポジトリのファイルは変更していない)
- **今回の見送り理由**: 該当するファイルは第 2 段の `cplat` だけであり、第 1 段の作業に影響しない。チェッカーの判定基準の変更 (関数定義をすべて含む 1 つの分岐の各分岐を、別のファイルとして評価する) と、ファイルの OS 別の分割のどちらで解消するかは、最終仕様の変更または `cplat` の構成の判断を要する。自走の指示により、問い合わせずに残課題へ送った。
- **継続作業での経緯と対処**: なし

### 影響範囲とリスク

- **影響対象**: 作業 WBS 4.2.4 (`cplat` の書き換え) と 4.3 (全対象のエラーと警告 0 件の確認)、受入条件 4
- **放置した場合のリスク**: 第 2 段の完了時に 2 ファイルのエラーが残り、受入条件 4 を満たせない。

### 推奨される対応策

- **恒久対応案**: 第 2 段の着手前に、(a) チェッカーで、関数定義をすべて含む 1 つの分岐の各分岐を別の並びとして評価する (`reorder_c_topdown.py` の範囲の決め方と同じ) か、(b) 該当ファイルを OS 別のファイルへ分割するかを決める。(a) は規範の「条件の内側で構成に従う」と一致し、`reorder_c_topdown.py` の振る舞いとも揃う。
- **参考情報**: 最終仕様の「機械的チェック ツールの仕様」の「解析の前提」、`coding-guideline.md` の「関数の記載順と前方宣言」節の「条件付きコンパイル」

## BL-005 Doxygen の誘導マーカーと定義側のコメントの全件の精査、static 関数の前方宣言への Doxygen コメントの付与

### 概要と問題点

- **現状の事象 (誘導マーカー)**: ユーザーが `app/porter/prod/libsrc/porter/api/api_open_paths_tcp.c` で、次の 2 つの逸脱を指摘した (2026-11-27)。どちらも第 2 段の書き換えの前からある。
    - 誘導マーカー `/* Doxygen コメントは、ヘッダーに記載 */` と関数定義の間に、空行がない。
    - マーカーの直前に、関数の説明が通常のコメント (`/* TCP / TCP_BIDIR: RECEIVER は listen ソケット作成、SENDER はアドレス解決のみ行う。 */`) で置かれている。この説明は宣言側の Doxygen にも出力にも載らない。
- **2026-11-27 時点の件数**: 主エージェントがワークスペースの第一者管理の `.c` と `.cpp` を数えた結果は、次のとおり。数えたのはこの 2 つの型だけで、全件の精査ではない。
    - 空行なし: `app/porter` 51 (9 ファイル)、`app/cjson` 2、`app/cplat` 1
    - マーカーの前の通常のコメント: `app/porter` 8 (`api_open_paths_tcp.c`、`api_open_paths_udp.c`、`thread_recv_health.c`。うち 1 件は複数行のコメントの後。拡張した `check_c_blank_lines.py` の検出による)
- **逸脱の理由**:
    - 空行の規則は `app/general/docs/doxygen-comment-guideline.md` にあったが、機械的な確認の手段がなかった。
    - 宣言側に説明がある関数へ定義側で補足を書く方法が、正本の規範になかった。
- **現状の事象 (static 関数の前方宣言)**: 第 2 段の書き換えで、static 関数の前方プロトタイプ宣言がファイルの先頭にまとまる (例: `api_open_paths_tcp.c` の 28 から 30 行の 3 つ)。ユーザーは、これらの宣言に Doxygen コメントを付け、定義ではなく前方宣言に置くのが望ましいと考えている (2026-11-27)。
    - 現行の規範 (`doxygen-comment-guideline.md` の「静的関数とファイル内シンボル」と「先行宣言のない関数」) は、static 関数の説明を定義側に置く前提で書かれている。前方宣言がある static 関数の説明を、宣言と定義のどちらに置くかを定めていない。
- **本来あるべき姿**:
    - 誘導マーカーと定義側のコメントが、すべて規範に沿っている。
    - static 関数の前方宣言と定義の、Doxygen コメントの置き場所が規範で決まり、既存のファイルが移行済みである。

### 経緯と見送り理由

- **摘出契機**: 第 2 段の `porter` の書き換え中に、ユーザーが指摘 (2026-11-27)。
- **今回の対処**:
    - `doxygen-comment-guideline.md` の「定義側の誘導マーカー」に、規範を足した。内容は、マーカーの前のコメントの禁止、定義側の補足、機械的な確認の 3 つ。定義側の補足には、詳細説明として成り立つ範囲で必要なタグをすべて使える。`@brief` と宣言側と同じ内容は書かない。
    - `app/general/bin/check_c_blank_lines.py` に、2 つの検出の種別を足す (マーカーの後の空行、マーカーの直前のコメント)。
- **今回の見送り理由**: ユーザーの提案 (2026-11-27「backlog に回して全件精査を改めてするのはどうか」) による。見送りの理由は次の 3 つ。
    - 第 2 段の書き換え (`cplat`、`porter`) と同じファイルを触る。
    - 数えた 2 つの型のほかにも逸脱がある見込みがある。
    - 7 か所のコメントは、定義側の補足にするか宣言側へ移すかを 1 件ずつ判断する必要がある。
- **継続作業での経緯と対処**: なし

### 影響範囲とリスク

- **影響対象**: ワークスペースの第一者管理のすべての C/C++ のソースとヘッダー、`doxygen-comment-guideline.md`、`check_c_blank_lines.py`
- **放置した場合のリスク**:
    - 関数の説明が宣言側と定義側に分かれ、Doxygen の出力から欠ける。
    - エディターがマーカーを関数のホバー説明として誤って示す。
    - static 関数の前方宣言だけを読んでも、役割が分からない。

### 推奨される対応策

- **恒久対応案**: 第 2 段 (作業 WBS 4.2) の main への統合の後に、新しい案件として agree-before-implement で始める。
    - `check_c_blank_lines.py` の新しい検出で、全件の一覧を作る。
    - 次の型も合わせて精査する: 宣言側に説明があるのにマーカーがない関数、static 関数への不要なマーカー、宣言側と定義側の説明の重複。
    - static 関数の前方宣言と定義の、Doxygen コメントの置き場所を規範に書く。ユーザーは、前方宣言に置くのが望ましいと考えている (2026-11-27)。この方針を前提に、定義の直前の扱い (公開関数と同じ誘導マーカーを置くか) と、前方宣言のない static 関数の扱いを決める。
    - 決めた規範に従って、全 app を移行する。
- **参考情報**:
    - `doxygen-comment-guideline.md` の「定義側の誘導マーカー」と「静的関数とファイル内シンボル」
    - `coding-guideline.md` の「関数の記載順と前方宣言」
