## BL-001 移行前のファイルを部分的に編集する場合のチェッカーの扱い

### 概要と問題点

- **現状の事象**: 規範 (`app/general/docs/coding-guideline.md`) は、対象の `.c` を新規作成または編集した場合に、そのファイルに対して `check_c_topdown.py` を実行してエラーと警告を 0 件にすると定める。第 2 段の書き換え (`porter`、`cplat`) の完了により、現行 main の移行前ファイルは解消した (残存違反は BL-004 の 2 ファイルのみ) が、既存違反を含むファイル (BL-004 該当ファイルや、今後取り込む未移行ブランチ・コードなど) を数行だけ編集した場合にファイル全体の書き換えを求めるのか、編集範囲に限るのかが規範に明記されていない。
- **本来あるべき姿**: 既存違反を含むファイルを部分的に編集する場合に、ファイル全体の書き換えを求めるか、編集した関数の範囲に限るか、並べ替えを別コミットへ分けるかが規範に明記されている。

### 経緯と見送り理由

### 影響範囲とリスク

- **影響対象**: BL-004 該当ファイル (`console.c`、`etw-viewer.c`) や、今後マージ・追加される未移行の `.c` ファイルを部分編集する作業

### 推奨される対応策

## BL-004 複数の分岐にそれぞれ完全な実装を持つファイルとチェッカーの判定

### 概要と問題点

- **現状の事象**: 1 つの前処理の分岐の各分岐に、主たる関数とファイル内補助関数の完全な実装を持つ 2 ファイル (`app/cplat/prod/libsrc/cplat/console/console.c` と `app/cplat/prod/src/cmd/etw-viewer/etw-viewer.c`。`#if defined(PLATFORM_WINDOWS)` と `#elif defined(PLATFORM_LINUX)` の各分岐に実装がある) は、`reorder_c_topdown.py` で各分岐の内側を並べ替えても、`check_c_topdown.py` の `non-topdown-order` が残る (作業 WBS 4.3 の 2026-11-27 実行結果で、`console.c` 5 件、`etw-viewer.c` 2 件の計 7 件)。チェッカーは最終仕様どおり前処理の条件を評価せず、すべての分岐を 1 つの並びとして扱うため、後の分岐の主たる関数が前の分岐のファイル内補助関数より後に来るためである。
- **本来あるべき姿**: 規範の「ファイル全体を 1 つの条件で囲むファイルでは、条件の内側で構成に従う」と、チェッカーの判定が両立し、該当する 2 ファイルを含め全対象でエラー 0 件にできる。

### 経緯と見送り理由

- **摘出契機**: 作業 WBS 4.1.3 で `reorder_c_topdown.py` を全対象の違反ファイル (154 ファイル) へ一時的に適用した試行 (2026-11-26、リポジトリのファイルは変更していない)。作業 WBS 4.2.4・4.3 (2026-11-27) で実ファイルでも同様に計 7 件が残存することを確認した。
- **今回の見送り理由**: 解消するには、(a) チェッカーの判定基準の変更 (関数定義をすべて含む 1 つの分岐の各分岐を、別のファイルとして評価する) か、(b) 該当 2 ファイルの OS 別ファイル分割のどちらかを決める設計判断が要る。本案件では解消せず、受入条件 4 は BL-004 の 7 件を除きエラー・警告 0 件として「条件付きで適合」(最終仕様の定義どおりでは不適合) とする判断を第 3 ゲートでユーザーへ提示する。
- **継続作業での経緯と対処**: 2026-11-28 に BL-006 の継続案件 `261128-reorder-topdown-conditional-blocks` (`app/general/docs/prompts/current/261128-reorder-topdown-conditional-blocks-overview.md`、`261128-reorder-topdown-conditional-blocks-discussion.md`、`261128-reorder-topdown-conditional-blocks-lightadr.md`、`261128-reorder-topdown-conditional-blocks-backlog.md`) を開始し、Q-004 で本案件へ BL-004 を含めるか (チェッカー改修 / ファイル分割 / 別案件へ見送り) を確認中 (フェーズ 1、回答待ち)。

### 影響範囲とリスク

- **影響対象**: `app/cplat/prod/libsrc/cplat/console/console.c` (エラー 5 件)、`app/cplat/prod/src/cmd/etw-viewer/etw-viewer.c` (エラー 2 件)、`app/general/bin/check_c_topdown.py`、および全対象走査 (終了コード 1 が返る)
- **放置した場合のリスク**: `python3 app/general/bin/check_c_topdown.py` を引数なしで全対象実行すると常にエラー 7 件 (終了コード 1) になり、新たな違反の発生を見落としやすくなる。

### 推奨される対応策

- **恒久対応案**: 次期案件で、(a) `check_c_topdown.py` において、関数定義をすべて含む 1 つの前処理分岐の各分岐を別の並びとして評価する (`reorder_c_topdown.py` の範囲の決め方と同じ) か、(b) 該当 2 ファイルを OS 別のファイル (`*_linux.c`、`*_windows.c`) へ分割するかを決めて実施する。(a) は規範の「条件の内側で構成に従う」と一致し、`reorder_c_topdown.py` の振る舞いとも揃う。BL-006 の分岐の扱い設計と合わせて検討すると整合しやすい。
- **参考情報**: 最終仕様の「機械的チェック ツールの仕様」の「解析の前提」、`coding-guideline.md` の「関数の記載順と前方宣言」節の「条件付きコンパイル」、BL-006

## BL-005 Doxygen の誘導マーカーと定義側のコメントの全件の精査、static 関数の前方宣言への Doxygen コメントの付与

### 概要と問題点

- **現状の事象 (誘導マーカー)**: ユーザーが `app/porter/prod/libsrc/porter/api/api_open_paths_tcp.c` で、次の 2 つの逸脱を指摘した (2026-11-27)。どちらも第 2 段の書き換えの前からある。
    - 誘導マーカー `/* Doxygen コメントは、ヘッダーに記載 */` と関数定義の間に、空行がない。
    - マーカーの直前に、関数の説明が通常のコメント (`/* TCP / TCP_BIDIR: RECEIVER は listen ソケット作成、SENDER はアドレス解決のみ行う。 */`) で置かれている。この説明は宣言側の Doxygen にも出力にも載らない。
- **2026-11-27 時点の件数**: 主エージェントがワークスペースの第一者管理の `.c` と `.cpp` を数えた結果は、次のとおり。数えたのはこの 2 つの型だけで、全件の精査ではない。
    - 空行なし: `app/porter` 51 (9 ファイル)、`app/cjson` 2、`app/cplat` 1
    - マーカーの前の通常のコメント: `app/porter` 8 (`api_open_paths_tcp.c`、`api_open_paths_udp.c`、`thread_recv_health.c`。うち 1 件は複数行のコメントの後。拡張した `check_c_blank_lines.py` の検出による)
- **逸脱の理由**:
    - 空行の規則は `app/general/docs/doxygen-comment-guideline.md` にあったが、機械的な確認の手段がなかった。
    - 宣言側に説明がある関数へ定義側で補足を書く方法が、正本の規範になかった。
- **現状の事象 (static 関数の前方宣言)**: 第 2 段の書き換えで、static 関数の前方プロトタイプ宣言がファイルの先頭にまとまる (例: `api_open_paths_tcp.c` の 28 から 30 行の 3 つ)。ユーザーは、これらの宣言に Doxygen コメントを付け、定義ではなく前方宣言に置くのが望ましいと考えている (2026-11-27)。
    - 現行の規範 (`doxygen-comment-guideline.md` の「静的関数とファイル内シンボル」と「先行宣言のない関数」) は、static 関数の説明を定義側に置く前提で書かれている。前方宣言がある static 関数の説明を、宣言と定義のどちらに置くかを定めていない。
- **本来あるべき姿**:
    - 誘導マーカーと定義側のコメントが、すべて規範に沿っている。
    - static 関数の前方宣言と定義の、Doxygen コメントの置き場所が規範で決まり、既存のファイルが移行済みである。

### 経緯と見送り理由

- **摘出契機**: 第 2 段の `porter` の書き換え中に、ユーザーが指摘 (2026-11-27)。
- **今回の対処**:
    - `doxygen-comment-guideline.md` の「定義側の誘導マーカー」に、規範を足した。内容は、マーカーの前のコメントの禁止、定義側の補足、機械的な確認の 3 つ。定義側の補足には、詳細説明として成り立つ範囲で必要なタグをすべて使える。`@brief` と宣言側と同じ内容は書かない。
    - `app/general/bin/check_c_blank_lines.py` に、2 つの検出の種別を足す (マーカーの後の空行、マーカーの直前のコメント)。
- **今回の見送り理由**: ユーザーの提案 (2026-11-27「backlog に回して全件精査を改めてするのはどうか」) による。見送りの理由は次の 3 つ。
    - 第 2 段の書き換え (`cplat`、`porter`) と同じファイルを触る。
    - 数えた 2 つの型のほかにも逸脱がある見込みがある。
    - 8 か所のコメントは、定義側の補足にするか宣言側へ移すかを 1 件ずつ判断する必要がある。
- **継続作業での経緯と対処**: なし (第 2 段は親 `3c9e0c08`・CI 45964310605 で main へ統合完了しており、新規案件として着手可能な状態)

### 影響範囲とリスク

- **影響対象**: ワークスペースの第一者管理のすべての C/C++ のソースとヘッダー、`doxygen-comment-guideline.md`、`check_c_blank_lines.py`
- **放置した場合のリスク**:
    - 関数の説明が宣言側と定義側に分かれ、Doxygen の出力から欠ける。
    - エディターがマーカーを関数のホバー説明として誤って示す。
    - static 関数の前方宣言だけを読んでも、役割が分からない。

### 推奨される対応策

- **恒久対応案**: 第 2 段の main 統合が完了したため、新しい案件として agree-before-implement で始める。
    - `check_c_blank_lines.py` の新しい検出で、全件の一覧を作る。
    - 次の型も合わせて精査する: 宣言側に説明があるのにマーカーがない関数、static 関数への不要なマーカー、宣言側と定義側の説明の重複。

## BL-006 reorder_c_topdown.py が、条件付きコンパイルの分岐の中の #include、マクロ、型の定義を主たる関数の後ろへ移す

### 概要と問題点

- **現状の事象**: 第 2 段の `cplat` の書き換え (作業 WBS 4.2.4、2026-11-27) で、`reorder_c_topdown.py --in-place` の結果が、`make -C app/cplat` でコンパイル エラーになった。
    - `#if defined(PLATFORM_LINUX) ... #elif defined(PLATFORM_WINDOWS) ... #endif` の分岐の中に、`#include`、マクロ、型の定義、ファイル内変数、`static` 関数の定義が混在していた。
    - ツールが、この分岐をまとめて主たる関数の後ろへ移した。このため、`elevated_process.c` で、`#include <unistd.h>` より前に `geteuid()` の呼び出しが来た。
    - `process.c` でも、`struct process_start_resources` と `typedef struct wide_buffer` が、主たる関数や前方プロトタイプ宣言の後ろへ移った。これは Windows でだけコンパイル エラーになる。
    - 実装の担当 (agy) が、`elevated_process.c`、`process.c`、`eventlog-register.c` を手作業で直した。Windows の検証 (依頼 20) および CI 45964310605 (親 3c9e0c08) で、今回の書き換え対象については Windows でも崩れが見つからず全テストが合格することを確認済みだが、`reorder_c_topdown.py` 自体の欠陥は未修正である。
- **`--verify` で見つからない理由**: `--verify` は、関数の集合とトークンの一致を確かめるだけで、宣言と定義の前後関係 (使う前に宣言されているか) を確かめない。
- **本来あるべき姿**: ツールが、`#include`、マクロ、型の定義、ファイル内変数を、それを使う関数の前に残す。崩れが起きた場合は、`--verify` か、書き換え後のコンパイルで必ず止まる。

### 経緯と見送り理由

- **摘出契機**: 作業 WBS 4.2.4 の `make -C app/cplat` (2026-11-27)
- **今回の見送り理由**: 第 2 段の書き換えは、手作業の修正で完了させた。ツールの修正は、分岐の扱いの設計 (BL-004 と同じく、分岐の中の並べ替えの範囲の決め方) と合わせて決める必要があるため。
- **継続作業での経緯と対処**: 2026-11-28 に継続案件 `261128-reorder-topdown-conditional-blocks` (`app/general/docs/prompts/current/261128-reorder-topdown-conditional-blocks-overview.md`、`261128-reorder-topdown-conditional-blocks-discussion.md`、`261128-reorder-topdown-conditional-blocks-lightadr.md`、`261128-reorder-topdown-conditional-blocks-backlog.md`) を開始した。現行実装の原因箇所の特定、一時ディレクトリでの最小再現、`app/*/prod/` 259 ファイルの混在件数調査を終え、検討用 Markdown (版 1、Q-001 〜 Q-007) を作成してフェーズ 1 の回答待ち。

### 影響範囲とリスク

- **影響対象**: `app/general/bin/reorder_c_topdown.py` を使う、すべての書き換え。特に、OS ごとの分岐の中に宣言を持つファイル。
- **放置した場合のリスク**: 書き換えが、片方の OS でだけコンパイル エラーになる。Linux だけで確かめると、Windows の崩れを見落とす。優先度を高とした理由は、ツールの結果が、確認なしでは正しいと扱えないため。

### 推奨される対応策

- **恒久対応案**:
    - ツールで、関数の定義だけを並べ替えの単位にし、`#include`、マクロ、型の定義、ファイル内変数は元の位置 (関数より前) に残す。
    - 分岐の中に関数の定義とそれ以外が混在する場合は、書き換えを止めて、手作業を求める。
    - `--verify` に、宣言より前の使用がないことの確認を加えるか、書き換えたファイルのコンパイルを確認の手順に入れる。
