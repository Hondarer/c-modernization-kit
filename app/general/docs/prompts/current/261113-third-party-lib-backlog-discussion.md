## 事前検証でシンボル バージョンだけでは防げない衝突を確認しました

2026-11-13 に `/tmp` の一時ディレクトリだけで C の小規模な共有ライブラリを作り、実行しました。  
リポジトリ内の成果物や生成元は変更していません。

- app 側の `collision()` は 22 を返し、SONAME と `APP_1` シンボル バージョンを設定
- OS 側を模したライブラリの同名関数は 11 を返し、シンボル バージョンは未設定
- app 側だけの実行結果は 22
- OS 側を `LD_PRELOAD` した実行結果は 11
- `LD_PRELOAD` を使わず、OS 側のライブラリと app 利用側の共有ライブラリを通常リンクした場合も `os=11 app=11`

最後の構成では、app 利用側の共有ライブラリが `collision@APP_1` を要求していることも `readelf --dyn-syms --wide` で確認しました。  
期待値は `os=11 app=22` です。この環境では、固有のシンボル バージョンを付けても未バージョンの同名関数による置換を防げませんでした。  
したがって、元 backlog の推奨策をそのまま実施して BL-001 を解消済みとは判断できません。

バージョン スクリプトの構文と目的の参考は [GNU ld の VERSION](https://sourceware.org/binutils/docs/ld/VERSION.html) です。  
上記の混在結果は、その文書からの推測ではなく、今回の実行で確認した事実です。

makefw の共有ライブラリのリンク処理は `makefiles/makelibsrc_c_cpp.mk` にあり、Linux の `shared` と `both` の双方で `-shared` を指定しています。  
SONAME とバージョン スクリプトの専用設定は見当たりませんでした。  
設定を追加する場合は、未指定時の既存動作を維持し、スクリプト変更時の再リンクも検証対象に含める案です。

BL-002 の主な既存利用側は、4 app 内の mock テスト、zlib の sampleTest、cplat の圧縮と symLoader のテストです。  
makefw の `prepare.mk` には、依存 app の `test/include_override` をテスト対象のコンパイルに追加する仕組みがすでにあります。  
Lua と SQLite には可変長引数の専用 mock があり、SQLite の公開変数と `sqlite3ext.h` は関数 API 表とは別の扱いです。  
API 表だけの一律変更では完了しません。

BL-003 の実行確認では、既存の Oracle Linux 9 開発イメージを使い、OS が 9.8、OS 側の OpenSSL が 3.5.5 であることを確認しました。  
OS 側の `OpenSSL_version` は `OPENSSL_3.0.0`、app 側は `OPENSSL_APP_3.0.0` で公開されます。  
両方の `libcrypto` を同じプロセスへ読み込み、読み込み順を逆にした別々のプロセスでも、各 `OpenSSL_version` が所属するライブラリと版を `dladdr()`、`OpenSSL_version()`、`OpenSSL_version_num()` で確認しました。  
同居の実行確認は完了しているため、OpenSSL のビルドを変更しない今回の作業に恒久テストを加える必要はないと判断します。

### Q-003 利用側の API 名も刷新する範囲

**Status**

解決済み

**Question**

旧 API 名のソース互換マクロと mock 用の旧名ラッパーを廃止し、ワークスペース内の利用側を新しい固有 API 名へ移行する方針で進めますか。

**Context**

現行の最終仕様案は、実ライブラリのシンボル名を固有名へ変更する一方、公開ヘッダーの `deflate` などは対応マクロで残し、関数ポインター経由の mock 呼び出しには同名ラッパーを残しています。  
このため既存バイナリ ABI は変わりますが、利用側のソース表記には旧名が残ります。

完全なソース API 刷新では、公開する関数と変数を `zlib_app_deflate` などの名前で宣言し、cplat 等の利用側も新名に書き換えます。  
旧名への公開 alias と旧名の実シンボルは生成しません。  
mock の関数ポインター経由の呼び出しは、新名のラッパーで維持し、呼び出し元情報を取得できない場合は Q-001 の合意どおり unknown 値を使います。  
第三者管理のソースは直接編集せず、ビルド時の内部対応で新しい名前の実体を生成します。  
型名、列挙定数、構造体のレイアウトも再命名するかは公開関数名の変更とは別の判断です。案 A ではそこまで変更せず、OS との動的シンボル衝突に関係する公開関数・変数を対象にします。

案 B は旧 API 名のソース表記をヘッダーの alias として残します。  
この案では利用側の更新範囲を抑えられますが、旧名を使う source compatibility は残ります。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 旧 API 名の公開 alias と mock ラッパーを廃止し、利用側を新しい固有 API 名へ移行する。関数ポインターは新名で取得する。
- [ ] B: バイナリ ABI は破壊するが、利用側の旧 API 名と関数ポインター呼び出しの source compatibility は維持する。

推奨: A

「過去の互換性制約による歪を残さない」というご意向を、バイナリ ABI だけでなく旧 API 名の source compatibility も捨てる意味として反映できるためです。  
既知の利用側を一括移行し、将来の呼び出し元にはライブラリ固有名を明示します。  
型名などの非シンボル API は Q の案 A に示したとおり対象を分け、必要な根拠なく変更範囲を広げません。

**Related**

[Q-001](#q-001-関数ポインター経由の-mock-呼び出しの扱い) の回答は、旧名ではなく新しい公開関数名のポインター経由の呼び出しに適用します。  
[Q-002](#q-002-衝突を防ぐためのシンボル名の変更) の実シンボル名と利用側の表記を本問で確定します。

**Assessment**

A の選択により、旧 API 名の公開 alias と旧名の mock ラッパーを作らず、ワークスペース内の利用側を新しい固有 API 名へ移行します。  
Q-001 の関数ポインター対応は、新しい固有 API 名の関数ラッパーに適用します。取得不能な呼び出し元情報は、ファイル名と関数名を `"<unknown>"`、行番号を `0` とします。  
関数呼び出しを提供する公開 API 呼び出しマクロも新しい固有名へ移行し、展開後の動作は維持します。定数・型・構造体フィールドの名前は、衝突回避の対象外として変更しません。  
補足に基づき、zlib、cJSON、Lua、SQLite の各 app の README に、分離が必要な背景と利用方法を記載します。利用側にはソース API とバイナリ ABI の変更、再ビルド・再リンク、文字列による動的参照名も説明します。

## 第 1 ゲートの合意内容と受入条件

[Q-001](#q-001-関数ポインター経由の-mock-呼び出しの扱い) と [Q-003](#q-003-利用側の-api-名も刷新する範囲) に基づき、通常の mock 呼び出しではファイル名、行番号、関数名を取得します。  
関数ポインター経由の呼び出しは、新しい固有 API 名の mock ラッパーを経由し、呼び出し元が取得不能であることを明示します。旧名 alias と旧名ラッパーは作りません。

[Q-002](#q-002-衝突を防ぐためのシンボル名の変更) と Q-003 に基づき、実ライブラリの公開関数・変数を固有名へ変更し、利用側のソースも新しい API 名へ移行します。  
ソース API と従来のバイナリ ABI は維持せず、ワークスペース内の利用側を再ビルド・再リンクします。  
既存の展開後パッチと共通生成処理を使い、生成物の直接編集は行いません。

受入条件は、全公開名の一致、旧名の非公開、新名での利用側の移行、同名の未バージョン関数との両順序での同居、通常呼び出しの位置情報、新名の関数ポインター経由での取得不能表示、可変長引数・既定の実委譲の維持、および SQLite 拡張 API 表との整合です。  
正式な検証対象と確認方法は最終仕様に記載します。  
Windows でのリンク確認は Linux の成功で代用せず、実行できない場合は未確認として明示します。
