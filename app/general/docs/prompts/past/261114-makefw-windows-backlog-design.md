## BL-002 では実際のリンク構成の差異を追跡します

### 各ターゲットが実効構成を提供します

ターゲットの種別は、実行体、共有ライブラリ、静的ライブラリとして明示します。  
`CURDIR` の文字列から種別を推定しません。  
`LIB_TYPE=both` の共有出力と静的出力は別々に追跡します。

実際のリンク・アーカイブ レシピで使用するツールと構成引数を、順序を保って記録します。  
実行体では `LD`、`LDFLAGS`、`LIBS`、`LIBSFILES`、共有ライブラリでは実際に使用する `CC` または `LD`、`LDFLAGS`、`STATIC_LIBS`、`DYNAMIC_LIBS`、静的ライブラリでは `AR` と当該プラットフォームで使用する `LIB_LTCG` を反映します。  
`LIBSDIR` 由来の実効検索オプションと解決済みライブラリの差異も検出します。  
既存のオブジェクト・リソース・追加入力の追跡と、入力ファイルの更新時刻による判定を維持します。

一時レスポンス ファイル名など実行ごとに変化する作業用情報を、構成変更の根拠にしません。  
同じ構成の反復ビルドで不要なリンクを起こさないようにします。

### 記録・読取・比較で構成文字列を変質させません

状態は既存の `$(OBJDIR)/$(notdir <target>).link.mk` を拡張して保持します。  
記録には種別と構成の差異を保持する表現を使用し、引用符内の連続空白を `strip` で圧縮しません。  
引用符、`$`、`#`、バックスラッシュ、および符号化用文字列そのものを含む場合にも、Make の include やシェル展開で別の構成へ変質・衝突しないようにします。  
構成引数の並べ替えや重複除去は行いません。

Linux の Make 解析時と Linux / Windows のリンク レシピ内で、同じ構成表現を用いて記録済み構成と現在構成を比較します。  
構成変更がある場合は、Linux では対象成果物のレシピを起動し、Windows ではレシピ内の再リンク判定へ比較結果を反映します。  
変更なしの Linux 解析時に、構成比較のための外部プロセスを追加しません。  
保存済みの長い入力一覧を、そのままシェル コマンドへ埋め込みません。

旧形式で構成記録がない場合は再リンクし、成功後に新形式へ移行します。  
新状態はリンク・アーカイブ成功後だけ一時ファイルから置換します。  
失敗・中断時は前回成功時の記録を維持し、次回の再実行を妨げません。  
既存の空入力時の生成物削除規則も維持します。

## BL-003 ではパスと依存関係から警告を保存します

### 警告の発生元が曖昧な場合も診断を保持します

今回のソース一覧、`/sourceDependencies` JSON の Includes、PCH の依存情報から診断先候補を求めます。  
診断パスと依存パスは、絶対パス、区切り文字、Windows の大文字小文字、短い名前と長い名前を照合可能な形へそろえます。  
既存の診断表示と `.d` 生成を維持し、依存情報を再利用します。

| 診断の条件 | 保存先 |
| --- | --- |
| 今回のソース自身のパスと一致 | 一致したソースの `.warn` |
| 依存情報が完全で、ヘッダーなどの参照先と一致 | そのファイルに依存する今回の全翻訳単位の `.warn` |
| 依存情報が不完全、照合不能、またはパスのない警告 | 今回の全翻訳単位の `.warn` |

Table: MSVC 警告の保存先

依存情報から発生元を一意に特定できない診断は、複数の `.warn` へ保存される場合があります。  
直前に出力されたソース名へフォールバックしません。  
コンパイル成功・失敗の終了コードを維持し、依存情報の欠落だけを理由に新たな失敗へ変更しません。  
JSON の欠落や解析失敗を、警告の破棄につなげません。

### 既存 warn の清掃は今回のソース由来の行へ限定します

今回の各ソースの `.warn` は新しい収集結果で更新し、警告がなければ削除します。  
同じディレクトリにある今回コンパイル対象外の既存 `*.warn` は、診断パスが今回のソース自身に一致する古い行だけを除去します。  
清掃後に空となったファイルは削除し、残る行は保持します。

共有ヘッダー由来の行、照合不能の行、今回コンパイルしないソース由来の行は、一律に削除しません。  
パスの照合は割り当てと同じ正規化を使用し、単なる部分文字列一致で他ソースの警告を削除しません。

> [!NOTE]
> 共有ヘッダー由来や照合不能の警告は、今回コンパイル対象外の `.warn` に残る場合があります。
> この清掃では今回のソース由来と判定できる行を対象とし、不明な帰属を推測して削除しません。

## BL-004 では分類の互換性を維持して長い展開を除去します

### ソースの分類と clean の除外条件を維持します

外部ソース判定は既存の `_makefw_path_abspath` などの Make 関数を共通利用します。  
Linux の同名ローカル実体ファイル優先、シンボリック リンクの区別、inject・filter によるコピー扱いを維持します。  
Windows では外部ソースを `CP_SRCS` として追跡し、コピー済みのローカル実体がある反復ビルドでも取りこぼしません。

clean 時に `.gitignore` へ反映する外部ソース名の判定は、実行体とライブラリで共有します。  
参照ディレクトリへ到達できない入力をその収集対象から除外する現行条件を維持します。  
字句的な `abspath` だけでは実体の同一性や存在を判定できない入力を区別します。  
シンボリック リンク経由、大文字小文字、短い名前・長い名前などの別名は、単純な文字列比較だけで分類しません。  
必要な実体・到達可能性の確認でも、ソース一覧全体を長いシェル コマンドへ展開しません。

### 入力数に比例してシェル コマンドを長大化させません

`EXTERNAL_SRCS`、実行体・ライブラリの `MAKEFW_CLEAN_GITIGNORE_SRCS`、`_DIRECT_SYMLINKS` を対象とします。  
Make 関数による判定を優先し、ファイル システムの確認が必要な箇所は入力を分割するなど、単一コマンドへの一覧展開を避けます。  
対象のシェル確認が失敗した場合は、空の判定結果を正常な分類として使用しません。

特定のコマンド ライン上限値や脱落件数を正常性の基準にせず、多数入力と元ソース更新が正しく処理されることを確認します。

### Linux の実機検証条件と既存環境の制約

検証コマンドでは `LIBSDIR` に app 側の製品・テスト ライブラリを先に、testfw と Google Test のライブラリを後に指定しました。  
この既存環境の問題は、通常の探索順で解消したとは扱いません。

共有ディスク上のレポート生成は中断し、生成済みの同じバイナリ、依存する共有ライブラリ、および証明書データを Linux の一時領域へ複製して検証しました。
