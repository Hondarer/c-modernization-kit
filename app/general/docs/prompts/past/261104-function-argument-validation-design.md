# 関数引数の妥当性検査 最終仕様

検討 ID: function-argument-validation-20261104

ユーザーの「OK、承認。作業を進めてください。」により、仕様版 2 の反映を開始します。

## 変更対象と目的

[コーディング規範](../../coding-guideline.md) の「関数引数の異常入力対応」と、整合性に必要な関連記述を改訂します。  
入力検査の対象を NULL から引数の妥当性全般へ広げ、境界での検査と内部関数で省略できる再検査を区別します。  
実装コードの変更、既存コード全体の適合監査、ビルド構成の変更は含めません。  
既存コードへの適用は、現行の段階的適用方針を維持します。

「命名規則 → モジュール私有ヘッダー → NULL 検査」も改訂対象とします。  
その節の無条件に検査を省略するように読める説明を、全経路で保証済みの条件に限って再検査を省略する規則に合わせます。

## 妥当性検査の対象

NULL、数値の範囲、列挙値、長さと容量の関係、引数の組み合わせなど、関数が要求する事前条件を対象とします。  
条件は関数の契約に基づいて定めます。  
文字列の内容などの検査も同じ責務分担に従います。

> [!NOTE]
> NULL 検査だけでポインターの参照先の生存期間や実際のバッファー容量を証明することはできません。
> 呼び出し側の契約と、関数側が値から判定できる条件を区別します。

## 関数の層と検査責務

ヘッダー配置による現行の層分けを維持し、表の対象を NULL 検査から妥当性検査へ広げます。

Table: 関数の層に応じた妥当性検査の責務

| 層 | 判定基準 | 検査責務 |
| --- | --- | --- |
| 公開 | prod/include/ 配下のヘッダー | 関数の入口で、契約上必要で値から判定可能な条件を検査 |
| ライブラリ内共有 | prod/include_internal/ 配下のヘッダー | 公開と同じ |
| モジュール内共有 | 実装と同じディレクトリのモジュール私有ヘッダー | 呼び出し側が保証した条件の再検査を省略可能 |
| ファイル内 | ヘッダーで宣言せず static を付けた関数 | モジュール内共有と同じ |

必須ポインター引数の NULL 検査義務は維持します。  
省略可能な出力引数や、NULL を正常入力とする契約も維持します。  
許容された入力値に応じた動作の分岐は、その関数の責務として実装します。

## 内部関数で再検査を省略できる条件

モジュール内共有関数とファイル内関数では、次の条件をすべて満たす場合に同じ条件の再検査を省略します。

- 事前条件が Doxygen に記載されている
- すべての呼び出し経路で、上位の検査や値の生成処理によって事前条件を保証している
- 引数を使用する時点まで事前条件が成立する

関数が内部にあるという理由だけでは省略しません。  
呼び出し箇所が多いなどの理由で保証を確認できない場合は、検査を追加するか、保証を確認できるように呼び出し構造を見直します。

未検査のファイル・通信データなどを内部関数が受ける場合は、必要な検査を行います。  
コールバックも呼び出し側との契約と値の保証で判断し、保証できない場合は呼び出し先で検査します。  
qsort の比較関数のように、引数の値を呼び出し側が保証できる例は区別します。

検査後に共有状態が変更され得る場合など、条件が使用時まで維持されないときは、先行する検査だけで保証済みとは扱いません。  
内部演算で新たに生じるオーバーフローや、メモリ確保・入出力の失敗に対する検査は、引数の再検査の省略に含めません。  
整数演算の安全性については、既存の該当節を参照します。

## 失敗の通知と Doxygen

検査対象の値、許容範囲、引数間の条件を Doxygen に記載します。  
境界での引数不正は現行の戻り値規約で通知し、互換 API やコールバックはそれぞれの失敗表現に従います。  
明示的に無処理を定義した void API の契約は維持します。

内部関数で契約違反を検出した場合、無処理の正常終了として扱いません。  
失敗を通知できない関数は、通知方法または呼び出し側の保証を見直します。  
正常入力として許容した値に対する無処理と、契約違反の隠蔽を区別します。

## 判定手順とコード例

正本には、次の順序で判断できる手順を記載します。

1. 宣言ヘッダーから関数の層を特定します。
2. 引数ごとの条件と引数間の条件、正常入力として許容する値を確認します。
3. 内部関数では、全経路での保証と使用時までの維持を確認します。
4. 保証がない条件に必要な検査を割り当て、失敗の通知方法を決めます。

NULL に加えて整数範囲や長さと容量を扱うコード例を示します。  
望ましい例では、境界で条件を検査し、内部関数では保証済みの条件の再検査を省略します。  
望ましくない例では、未検査の値を内部へ渡す場合や、内部の契約違反を正常終了として扱う場合を示します。  
例中の整数演算でも、前提条件から安全性を確認できるようにします。

## 外部事例の記載方法

正本の根拠注記に、次の 8 例の比較を記載します。  
各例について、検査対象、呼び出し側と関数側の責務、本規範に活かす判断、適用の限界を示します。  
単なる出典の列挙にせず、保証済みの条件の再検査と、残すべき検査を比較できる構成にします。

Table: C の実例による検査責務と省略条件の比較

| 事例 | 確認できる設計 | 本規範への示唆と限界 |
| --- | --- | --- |
| GLib の UTF-8 入力 | 入力時やプログラム・ライブラリ境界で検査し、各関数では文字列の妥当性を再検査しない | NULL 以外も境界で保証して再検査を省略できる。内部関数だけを対象とした方針ではない |
| GLib の公開関数の事前条件 | オブジェクトの種類や引数間の条件を入口で検査する | 単一引数の値以外も契約に含める。契約違反後の状態や検出機構は本規範と異なる |
| SQLite の内部事前条件 | assert と ALWAYS / NEVER を使い分け、製品でも残す防御を区別する | 保証が不明な条件に防御を残す。本規範では assert を使わず、同等の検出力があるとは説明しない |
| Microsoft CRT の memcpy | コピー先容量や領域の非重複を呼び出し側に要求する。ライブラリ内部の使用も安全性を確認する | 値を渡す側が具体的に保証する設計の例。公開 API の契約であり、内部関数の省略条件を直接定めるものではない |
| Microsoft CRT の memcpy_s | コピー数が 0 でない場合の NULL とコピー数に対する容量不足を検査する | 引数間の条件を検査する例。ただし重複領域のコピーは未定義動作であり、検査付き API でもすべてを保証しない |
| OpenSSL の内部異常の扱い | 回復可能な内部異常を ossl_assert とエラー返却で扱う | 内部でも検出・通知を残す例。debug と release で挙動が異なり、本規範には機構をそのまま導入しない |
| zlib の展開処理と公式使用例 | 圧縮データ不正とストリーム状態不正を区別し、呼び出し条件から保証した事柄には assert を用いる | 外部データ検査と内部契約を分ける。公式例の assert は本規範のコード例として転用しない |
| Linux の refcount | 参照カウントのオーバーフローや不正な減算に警告・飽和などの防御を残す | 内部演算や状態遷移に伴う異常は再検査省略の対象にしない。カーネル固有の警告や飽和を採用する提案ではない |

公開 API の契約、内部契約の検証、内部演算の防御を区別します。  
外部事例を、内部の検査省略全般や本リポジトリのヘッダー配置による層分けの無条件な根拠とはしません。  
memcpy_s は不正パラメーター ハンドラーを呼び、続行が許された場合にエラーを返すため、本規範と同じ単純な結果コード方式とは説明しません。

assert 不使用の方針は維持します。  
内部契約は、呼び出し側の保証、Doxygen、テストとレビューで確認する方針とします。  
関連節にある「契約違反も一律に引数検査」といった説明は、保証済みの内部条件の再検査を省略する規則と整合させます。  
外部資料の URL は既存の記述形式に従って末尾の参照節へ集約します。

## 検証と受入条件
