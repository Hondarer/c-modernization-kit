## BL-001 状態と手順の説明文の書き方の規則化

### 概要と問題点

- **現状の事象**: `[状態]`、`[手順]`、`[Pre-Assert手順]` の説明文は、今回の案件で関数名の `()` とバッククォートだけをそろえました。主語の置き方や文型 (「〜を呼び出す。」「〜にて X を返す。」「〜から X を返却する。」など) は定めておらず、テストによって書き方がばらついています。
- **本来あるべき姿**: 確認タグと同じく、状態と手順の説明文の文型を `framework/testfw/docs/about-test-phase.md` に定め、`results.md` の状態節と手順節を同じ書き方で読めるようにする。

### 経緯と見送り理由

- **摘出契機**: 前提検討 (検討用 Markdown の Q-009 の選択肢 B)。
- **今回の見送り理由**: ユーザーの指示 (Q-009 の補足「B はバックログにする」)。状態と手順の文型という新しい論点を開くため、別の案件とする。

### 影響範囲とリスク

- **影響対象**: 全 app と `framework/testfw` のテスト コードの状態と手順の説明文 (約 8,500 行)。
- **放置した場合のリスク**: `results.md` の手順節の書き方が揺れ、新しいテストの手本が定まらない。

### 推奨される対応策

- **恒久対応案**: 代表的な文型 (関数の呼び出し、モックの戻り値の注入、出力引数の設定、待機) ごとに書き方を定め、一括で移行する。BL-002 と BL-003 も同じ案件で扱う。

## BL-002 状態と手順の説明文の NULL の表記

### 概要と問題点

- **現状の事象**: C++ のコードの `NULL` を `nullptr` に置き換えましたが、最終仕様の対象外としたため、状態と手順の説明文には「NULL」が残っています (約 720 行。例: `app/calc/test/src/libcalcbaseTest/addTest/addTest.cc` の「calcbase_add(1, 2, NULL) を呼び出す。」に対し、コードは `calcbase_add(1, 2, nullptr)`)。
- **本来あるべき姿**: 説明文がコードの値を引用している箇所は、コードと同じ `nullptr` と書く。C の API の契約として「NULL」と書いている箇所との書き分けを定める。

### 経緯と見送り理由

- **摘出契機**: 作業後の差分の点検 (2026-10-16)。
- **今回の見送り理由**: 最終仕様はコメントと文字列の中の `NULL` を対象外とし、確認コメントだけを `nullptr` にしたため。

### 影響範囲とリスク

- **影響対象**: C++ のテスト コードの状態と手順の説明文。
- **放置した場合のリスク**: 手順節と確認節、説明文とコードで空ポインターの表記が食い違う。

### 推奨される対応策

- **恒久対応案**: BL-001 の文型の規則と合わせて、説明文の空ポインターの表記 (コードの値の引用は `nullptr`、C の API の契約の説明は NULL) を定め、移行する。

## BL-003 関数名を動詞として使う説明文

### 概要と問題点

- **現状の事象**: 関数名に `()` を付けた結果、「push() する」「set_name() する」「fopen() する」のように、関数名を動詞として使う説明文が 26 件あります。
- **本来あるべき姿**: 「push() を呼び出す」「push() で要素を追加する」のように、関数の呼び出しと操作の内容が分かる文にする。

### 経緯と見送り理由

- **摘出契機**: 作業後の差分の点検 (2026-10-16)。関数でない語に付いた `()` (「dispose() する」「default()」など) は作業中に直しました。
- **今回の見送り理由**: 最終仕様は文の書き方を変えないと定めたため。

### 影響範囲とリスク

- **影響対象**: `app/cplat` のテストの状態と手順の説明文 26 件。
- **放置した場合のリスク**: 読み手にとってやや不自然な文が残る (意味は通じる)。

### 推奨される対応策

- **恒久対応案**: BL-001 の文型の規則に含めて直す。

## BL-004 スマート ポインターをそのまま条件にする書き方

### 概要と問題点

- **現状の事象**: 空ポインターの規範は「ポインターをそのまま条件にしない」と定めましたが、`shared_ptr` などのスマート ポインターの扱いを定めていません。`framework/testfw/libsrc/test_com/processController.cc` の `if (!handle)` (`AsyncProcessHandle` は `shared_ptr`) や、`app/porter/test/src/integration/porterSendRecvTest/porterSendRecvTest.cc` の `if (send_h_)` などが残っています (約 8 件)。
- **本来あるべき姿**: スマート ポインターを規則の対象とするかを決め、対象とする場合は `handle == nullptr` などに直す。

### 経緯と見送り理由

- **摘出契機**: `tryWaitForOutput()` の実装時 (2026-10-16)。新しく書いたコードは `handle == nullptr` としました。
- **今回の見送り理由**: 最終仕様が生ポインターとスマート ポインターを区別していないため、移行の範囲を決められなかった。

### 影響範囲とリスク

- **影響対象**: C++ のテスト コードと `framework/testfw` のスマート ポインター。
- **放置した場合のリスク**: 同じファイルの中で、生ポインターは明示的な比較、スマート ポインターはそのまま条件、と書き方が分かれる。

### 推奨される対応策

- **恒久対応案**: ユーザーが判断し、対象とする場合は `coding-guideline.md` の「空ポインターの表記」に明記して移行する。

## BL-005 コメント中の単独の波括弧の誤検出

### 概要と問題点

- **現状の事象**: `text_style_jp.py` の C/C++ のコメント処理で、引用符で囲んだ部分は整形の対象から外しましたが、引用符の外にある波括弧の文字 (例: `stringCatalogRenderTest.cc` 157 行目の `({{ と }} が 1 文字の波括弧になったことの確認)`、`stringCatalogValidateTest.cc` の `対を成さない } だけの書式`) は、引き続き `space-inside-brackets` で指摘されます。
- **本来あるべき姿**: 文字そのものを指す波括弧を誤検出しない、または説明文で引用符に入れる書き方を規則にする。

### 経緯と見送り理由

- **摘出契機**: 最終仕様の作成時に対象外と定めた (2026-10-16)。
- **今回の見送り理由**: 単独の波括弧が文字そのものか括弧かを機械的に判定できないため。

### 影響範囲とリスク

- **影響対象**: 波括弧を扱う書式処理のテストの確認コメント (数件)。
- **放置した場合のリスク**: `--in-place` で整形すると、確認コメントがコードと食い違う。

### 推奨される対応策

- **恒久対応案**: 確認コメントで文字そのものを指す場合は `"}"` のように引用符に入れる規則を `about-test-phase.md` に加え、該当箇所を直す。

## BL-006 空ポインターの規範の検証コマンドの精度

### 概要と問題点

- **現状の事象**: `coding-guideline.md` の「空ポインターの表記」の検証コマンドのうち、ポインターをそのまま条件にする候補の抽出は、真偽値の変数も拾うため候補が約 300 件になり、目視での選別が必要です。三項演算子や `&&` の中の条件は抽出できません。
- **本来あるべき姿**: 型を考慮した点検 (clang-tidy の `readability-implicit-bool-conversion` など) で、ポインターだけを機械的に検出する。

### 経緯と見送り理由

- **摘出契機**: 規範の検証コマンドの試行 (2026-10-16)。
- **今回の見送り理由**: 型を考慮した点検ツールの導入は今回の範囲外のため。

### 影響範囲とリスク

- **影響対象**: C と C++ の全コード。
- **放置した場合のリスク**: 新しいコードで規則の逸脱が見逃される。

### 推奨される対応策

- **恒久対応案**: clang-tidy などの導入を検討し、規範の検証節を置き換える。

## BL-007 関数名の () の付け忘れの網羅的な点検

### 概要と問題点

- **現状の事象**: 状態と手順の説明文の関数名に `()` を付ける移行は、作業者の判断と目安の点検 (識別子の形による抽出) で行いました。目安の点検は変数名も拾うため、残り約 290 件の大半は誤検出ですが、付け忘れがないことを機械的には確かめられていません (例: `shutdownTest.cc` の「atexit が呼び出された際に」は抽出されない形)。
- **本来あるべき姿**: 説明文の関数名を機械的に判定できる仕組みで点検する。

### 経緯と見送り理由

- **摘出契機**: 作業後の点検 (2026-10-16)。
- **今回の見送り理由**: 識別子が関数か変数かを説明文だけから判定できないため。

### 影響範囲とリスク

- **影響対象**: 全テストの状態と手順の説明文。
- **放置した場合のリスク**: `()` のない関数名が一部残る (表記の揺れ)。

### 推奨される対応策

- **恒久対応案**: テスト コードの中で呼ばれている関数名の一覧と説明文の識別子を照合する点検を、`text_style_jp.py` の `test-comment-*` に加えることを検討する。
