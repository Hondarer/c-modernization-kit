## Q-002 EACCES の結果分類

**Status**

解決済み

**Question**

Linux の `map_wait_rc()` で、`EACCES` をどう扱いますか。

**Context**

`map_wait_rc()` を呼ぶ箇所は、mutex のロック・ロック解除と条件変数の待機・通知です。  
現在は `EACCES` を `CPLAT_ERR_BUSY` に変換しますが、根拠となる pthread の戻り値は確認できませんでした。  
POSIX の [mutex 関数](https://man7.org/linux/man-pages/man3/pthread_mutex_lock.3p.html) と [条件変数の待機](https://man7.org/linux/man-pages/man3/pthread_cond_wait.3p.html) の ERRORS 節にも、この組み合わせでの `EACCES` は記載されていません。  
一方、`syncBoundaryTest` と `syncFailureInjectionTest` は、`EACCES` を人工的に渡して `CPLAT_ERR_BUSY` を期待しています。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) `EACCES` の専用分岐を削除し、未知の結果として `CPLAT_ERR_UNKNOWN` に分類する。既存テストの期待値も更新する。
- [ ] B: `EACCES` を `CPLAT_ERR_BUSY` に分類し続け、必要な根拠を示す。
- [ ] C: その他。扱いと根拠を下に指定する。
- [ ] X: 意図不明。質問を具体化する。

その他の回答 / 補足:

2026-11-09 07:50 JST に、ユーザーが検討文書で A を選択したことを確認しました。

**Recommendation**

推奨: A  
理由: 現在の呼び出し元と pthread の仕様からは、アクセス拒否をロック競合として扱う根拠を確認できません。人工的な失敗注入の期待値を、結果分類の正本にはしません。
