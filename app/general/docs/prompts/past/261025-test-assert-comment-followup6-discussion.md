### libclang のホイールの制約

- PyPI の `libclang` のホイールは、`libclang.so` (Windows では `libclang.dll`) だけを同梱し、clang 自身の組み込みヘッダー (`stddef.h` など) を含みません。
- そのため、ビルドと同じオプションだけで解析すると、`/usr/include/stdlib.h:31:10: fatal error: 'stddef.h' file not found` で解析が止まります。Linux では、GCC の組み込みヘッダーのディレクトリ (`gcc -print-file-name=include`) を `-isystem` で加えると、解析エラーなしで解析できました (`app/tutorial/test/src/static-access/static-access.cc`、Google Test を含む C++)。
- 解析の時間は、上記のファイルで約 1.2 秒 (1 スレッド) でした。コンパイルと同程度の時間が、点検するファイルごとに加わります。前回の一時点検の対象は、Linux の翻訳単位 1076 個でした。
- Windows で MSVC のヘッダーを解析する場合は、clang の組み込みヘッダー (`intrin.h` などのコンパイラ組み込み関数の宣言) がないために解析エラーになるおそれがあります。この開発環境に Windows がないため、実際の動作は確認できていません。Windows の CI に libclang を導入すれば、CI で確認できます。

### makefw のコンパイルと警告の記録

- Linux では、ソースごとのパターン ルールで `gcc` / `g++` を実行し、警告を `<ソース>.warn` に記録します (`capture_warnings.sh`)。
- Windows では、複数のソースをまとめて `cl.exe` に渡します (`msvc_compile.ps1`)。
- 外部由来のコード (cjson、zlib、lua、sqlite の取り込みソース) も、makefw の同じ規則でコンパイルされます。これらのディレクトリの `makepart.mk` は、警告の抑止のオプションを個別に加えています。`app/cjson/prod/libsrc/cjson/` では、外部由来の `cJSON.c` / `cJSON_Utils.c` と、第一者管理のサブディレクトリが同じディレクトリにあります。
- 外部由来のヘッダー (Google Test、`cjson/prod/include`、`zlib/prod/include`) は、`-isystem` で渡されています。libclang では、`-isystem` のヘッダー内の位置をシステム ヘッダーとして判別できます。

## 明確化のための確認項目

### Q-001 点検を実行する契機

**Status**

取り下げ

**Question**

点検を、どの契機で実行しますか。

**Context**

- 点検は、ビルドと同じインクルード パスとマクロ定義でソースを解析する必要があります。オプションが異なると、前回の一時点検のように解析エラーが出て、エラーの箇所より後ろが点検されないおそれがあります。
- 案ごとの違いは次のとおりです。

```text
A の場合: 通常のビルド (make、make test) で、ソースをコンパイルした直後に、同じオプションで同じソースを点検する
  - 再コンパイルしたソースだけを点検するため、変更のない 2 回目以降のビルドでは時間が増えない
  - 開発者が意識しなくても、libclang があれば常に点検される
  - フル ビルドでは、ソースごとに解析の時間 (Google Test を含む C++ で約 1.2 秒) が加わる
B の場合: 点検専用の make 対象 (例: make check-pointer-conditions) を設け、app 直下から各ディレクトリへ再帰して点検する
  - 開発者や CI が明示的に実行したときだけ点検する
  - ビルドの時間は増えない。実行のたびに、対象のすべてのソースを解析する
  - CI と Jenkins に、点検を実行する手順を加える必要がある
```

- 「インストールされていたら処理を行い、ない場合はスキップ」という指示は、A の自動の実行と整合します。B では、libclang があっても make 対象を実行しない限り点検されません。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 通常のビルドで、コンパイルの直後に同じソースを点検する。
- [ ] B: 点検専用の make 対象を設け、明示的に実行する。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:
