# 第三者管理ライブラリの OS 側との分離と mock の呼び出し元情報

検討 ID: 261113-third-party-lib-backlog

仕様の版: 2

状態: 完了

zlib、cJSON、Lua、SQLite の実ライブラリに固有の公開シンボル名を付け、OS 側の同名ライブラリと分離します。  
4 app の公開 API 名を刷新し、mock は通常の呼び出し元情報を取得し、新しい API 名の関数ポインター経由の呼び出しも維持します。  
OpenSSL は現在の分離方法を維持します。OS 側も OpenSSL 3.x の環境で同居することを両方の読み込み順で事前確認したため、恒久テストは追加しません。

## 対象と互換性

対象は、4 app の実ライブラリ、mock、これらを使う既存のコードとテスト、および必要な共通生成処理です。  
第三者の配布物と生成済みのソース・ヘッダー・ライブラリは直接編集しません。  
既存の展開器、展開後パッチ、第一者管理の対応表を変更元とします。

共有ライブラリのファイル名と `LIBS` の指定は維持します。  
公開関数・変数と利用側のソース API の両方を固有名へ変更します。旧 API 名の公開 alias、旧名の mock ラッパー、従来のバイナリ ABI は維持しません。  
ワークスペース内の利用側を新しい名前へ移行して再ビルド・再リンクします。  
ワークスペース外の利用者も新しい API 名へ移行する必要があります。旧名を受け付ける互換アダプターは用意しません。  
`dlsym()` や `GetProcAddress()` に渡す文字列はプリプロセッサで置換されないため、文字列による参照も固有名へ移行します。

mock だけをリンクし、実ライブラリは動的な実委譲先として読み込む規則を維持します。  
実ライブラリと mock の両方をリンクして解決する構成へは変更しません。

## 公開シンボルを共通の対応表で固有名へ変更します

### 名前と公開境界

| app | 実ライブラリの接頭辞 | 従来 API 名と公開する固有名の例 |
| --- | --- | --- |
| zlib | `zlib_app_` | `deflate` → `zlib_app_deflate` |
| cjson | `cjson_app_` | `cJSON_Parse` → `cjson_app_cJSON_Parse` |
| lua | `lua_app_` | `luaL_newstate` → `lua_app_luaL_newstate` |
| sqlite | `sqlite3_app_` | `sqlite3_open` → `sqlite3_app_sqlite3_open` |

Table: 実ライブラリの公開名

対象は公開関数、可変長引数の公開関数、公開変数、およびこれらを呼び出す公開 API 呼び出しマクロです。利用側が記述する API 名も接頭辞付きにし、旧関数名・旧変数名・旧 API 呼び出しマクロ名は公開しません。  
cJSON の Integer と JSONC の公開関数も対象に含めます。  
`zlib_version` のようなオブジェクト形式でも公開関数を呼び出すマクロは改名し、定数やデータ操作だけのマクロは維持します。  
型名、列挙定数、構造体のレイアウト、コールバックの型、SQLite の拡張 API 表のフィールド名、および関数呼び出しを行わない定数・データ操作マクロは変更しません。  
内部シンボルを新たに公開せず、現在の hidden と公開属性による境界を維持します。  
Windows の IDENT 用シンボルなど、すでにライブラリ固有の名前を持つ付随シンボルは現在の規則で扱います。

各 app の `prod/public_symbols.txt` に、名前を対応付ける公開シンボルの一覧を置きます。  
API 呼び出しマクロは `prod/public_api_macros.txt` に別途列挙し、マクロ名と呼び出す公開 API の対応を記録します。  
本番ビルドの対応表を `test/` の API 表に依存させません。  
mock の API 表と公開変数・可変長引数の補足を含む期待値から、実際の公開シンボルとの過不足を検査します。  
対応表に未登録の新しい公開名が生じた場合は、元の名前で漏れたシンボルとして検査を失敗させます。

### 共通生成処理と展開後パッチ

makefw に `bin_internal/generate_symbol_namespace.py` を追加します。  
入力は公開シンボル一覧、API 呼び出しマクロ一覧、接頭辞です。生成器は、第三者ソースの実装をコンパイルするときに使う内部名前対応ヘッダーと対応解除ヘッダーを生成し、展開器は同じ対応表を使って配布ヘッダーの公開関数・変数・API 呼び出しマクロ名を固有名へ変換します。  
個別 app 名や特定の公開 API を共通生成処理へ埋め込みません。  
一覧の不正な識別子と重複はエラーとし、更新内容が同じ場合は出力の更新日時を変えません。

内部ヘッダーの出力先は各 app の `prod/include_internal/<lib>_app_namespace.h` と `prod/include_internal/<lib>_app_undef.h` です。  
ここで `<lib>` は `zlib`、`cjson`、`lua`、`sqlite3` です。  
対応ヘッダーは、第三者ソースの元の識別子を固有名へ展開するオブジェクト形式のマクロを定義します。第三者ソースの実装翻訳単位へ適用し、公開関数の定義と内部呼び出しを固有名へ変換します。  
展開器は対応表の識別子を配布ヘッダーの宣言へ適用し、利用側には固有名の宣言だけを提供します。旧名を新名へ置き換える alias マクロは公開ヘッダーに残しません。API 呼び出しマクロは新しい固有名で提供し、既存の version・構造体サイズを渡す意味を保ったまま新しい固有 API を呼びます。通常呼び出しと関数アドレス取得はいずれも同じ新シンボルを参照します。  
SQLite の amalgamation 内の宣言・定義も同じ対応表に従います。SQLite 拡張 API 表のフィールドと外部モジュールの入口名は変換対象から除外します。

既存の `bin_internal/extract_package.py` から共通生成処理を呼びます。  
展開器の依存判定にシンボル一覧、生成器、パッチの変更を含め、生成したヘッダーが欠落した場合も再生成します。  
生成物は既存の展開物と同様に Git の管理対象から除き、生成元を追跡します。  
Python の文字コード、モジュール探索経路、並列実行時の更新は既存の規範に従います。

展開後パッチで、各ライブラリの公開ヘッダーと本体を展開器の対応表へ適合させます。  
SQLite の amalgamation 内にはヘッダー相当の宣言が含まれるため、`sqlite3.c` と外部の `sqlite3.h` の双方を変換します。  
既存の可視性、Windows の import/export、cJSON の整数拡張などのパッチを維持し、その後に適用します。

### ライブラリ固有のマクロと拡張 API

zlib の初期化マクロは、新しい固有名へ改名し、バージョンと構造体サイズを渡す現在の動作を維持します。  
`gzgetc` のマクロと同名の実関数、64 bit API への展開は、対応ヘッダーと衝突しないよう局所パッチで整合させます。  
`_FILE_OFFSET_BITS`、`_LARGEFILE64_SOURCE`、Windows の 64 bit offset に関する既存設定と型の幅を維持します。  
公開名の一括変更のために型名まで変更する構成にはしません。

Lua の `luaopen_*` など、本体が公開する関数には固有名を付けます。  
外部 C モジュールの入口を探す `luaopen_<モジュール名>` の規則や、登録済みコールバックのアドレスは一律に変更しません。  
外部モジュールが本体の API を直接参照する場合は、ワークスペースのヘッダーとライブラリで再ビルドする対象になります。

SQLite の `sqlite3_version`、`sqlite3_temp_directory`、`sqlite3_data_directory` も実シンボル名を変更します。  
`sqlite3ext.h` の API 表経由の関数も新しい固有 API 名で提供し、API 表のフィールド名は配布元の名前を維持します。  
`SQLITE_CORE` などにより本体の関数を直接使う経路では固有名への対応を維持します。  
拡張の入口名や API 表の構造は維持します。  
直接 API を使うコード、拡張 API 表を使うコード、両ヘッダーを順に取り込むコードを検証します。

### SONAME とシンボル バージョン

Linux の 4 app の SONAME は、現在のファイル名である `libzlib_app.so`、`libcjson_app.so`、`liblua_app.so`、`libsqlite3_app.so` に設定します。  
既存の `LDFLAGS` で設定し、そのためだけの makefw のリンク設定機能は追加しません。  
OS 側との関数の分離は固有の実シンボル名で行うため、4 app のシンボル バージョンとバージョン スクリプトは追加しません。  
OpenSSL の `shlib_variant`、SONAME、`OPENSSL_APP_*` のシンボル バージョンは維持します。

## mock は呼び出し元情報と新しい API 名を扱います

### API 表と C 用の差し替えヘッダー

4 app の関数 API 表は、第三者ライブラリ内の元識別子と利用側に公開する固有 API 名を別々に記録し、実 API の引数・戻り値と mock の引数・呼び出し式も区別します。  
mock の先頭 3 引数は、呼び出し元のファイル名、行番号、関数名とします。  
実 API の引数列を残すことで、実関数のシグネチャ検査と新しい固有名のラッパー生成を行います。  
引数なしの API とコールバックを引数に取る API も、正しい型で宣言します。

API 表から mock の宣言、`MOCK_METHOD`、実委譲、C ラッパー、既定の `ON_CALL` を生成します。  
testfw に、API 表を入力として C 用の宣言と呼び出し元注入マクロを生成する共通処理を追加します。  
配置は `bin_internal/generate_shared_lib_mock_overrides.py`、その検証は `bin_test/` とします。  
可変長引数 API は専用の情報から生成し、通常の関数 API 表と混同しません。  
生成物と生成元が一致することも局所テストで確認します。

各 app の `test/include_override/` に、本来の公開ヘッダーと同じ名前の差し替えヘッダーを用意します。  
mock をリンクするテストの明示的な有効化マクロがある場合だけ注入し、同じ依存 app の実ライブラリを使うテストでは通常の宣言を提供します。  
実ヘッダーを先に取り込み、固有 API 名に対応する C 用 mock 宣言と注入マクロを有効にします。  
関連する実ヘッダーの読み込み中は注入を遅延し、後から宣言がマクロで書き換えられることを防ぎます。  
Linux は `#include_next`、Windows は現在の include 配置からたどれる参照を用います。

テスト対象の C ソースには Google Mock や C++ のヘッダーを取り込みません。  
Google Mock のクラス定義は `mock_<lib>.h` の C++ 部分に置き、C リンケージの宣言と分離します。  
テスト翻訳単位は `mock_<lib>.h` を取り込み、Windows の静的 mock ライブラリからの実装取り込みも確認します。  
既存 makefw の `TEST_SRCS` 用の差し替え探索を使い、通常の本番ソースへ mock の探索パスを加えません。

### 通常呼び出しと関数ポインター経由の呼び出し

通常の固有名 API 呼び出しは、対応する `mock_<固有名>(__FILE__, __LINE__, __func__, args)` へ置き換えます。  
Google Mock の検証とトレースへ、この 3 つの情報をそのまま渡します。  
トレースには対象 API 名と呼び出し元を表示し、既存の出力レベルによる戻り値の表示も維持します。

公開 API と同じ新しい固有名の C ラッパーを mock ライブラリに用意します。  
`&zlib_app_deflate` など新しい公開関数のアドレスを取得した場合や、その関数ポインター経由の呼び出しでは、固有名ラッパーから同じ mock 処理へ渡します。  
その場合の取得不能値は、ファイル名と関数名を `"<unknown>"`、行番号を `0` とします。  
トレースも取得不能を示し、ラッパー自身のソース位置を利用側の位置として出力しません。  
通常呼び出しと、位置情報を取得できない呼び出しをテストで区別します。

実ヘッダーを先に取り込んだテストでも、`mock_<lib>.h` が必要な対応を行い、固有名ラッパーの宣言を用意します。  
旧 API 名への alias は追加せず、`EXPECT_CALL` と `ON_CALL` も新しい API 名へ移行します。  
zlib の初期化マクロなど、別 API を呼ぶマクロから渡される位置情報も、利用側の呼び出し位置として検証します。  
同名のフィールドを読むマクロなど、関数 API に到達しない処理は関数 mock の限界として現在の区別を維持します。

### 実委譲と可変長引数

mock 未注入時と、個別動作を設定していない場合の実委譲を維持します。  
実委譲先は従来のライブラリ名と固有のシンボル名を組み合わせ、`resolveSharedSymbolOrExit()` で解決します。  
従来名の OS 側シンボルへ戻す探索は追加しません。  
解決失敗時は現在の理由・探索パスの出力と終了動作を維持します。

zlib の `gzprintf`、Lua の `lua_pushfstring`・`lua_gc`・`luaL_error`、SQLite の可変長引数関数も呼び出し元情報を受け取ります。  
既存の `va_list` への集約と、操作コードに応じた型付きの実呼び出しを維持します。  
`va_list` の開始・終了や引数の消費を重複させず、固有名の関数ポインター入口と呼び出し元付きの入口から共通処理へ渡します。  
SQLite の mock が提供する公開変数の現在の値と扱いは維持し、関数用の位置情報を追加しません。

## OpenSSL の同居確認は検討記録に残し、恒久テストを追加しません

OpenSSL の実装、ビルド設定、SONAME、`OPENSSL_APP_*` のシンボル バージョンは本作業で変更しません。  
Oracle Linux 9.8 で OS 側の OpenSSL 3.5.5 と app 側の OpenSSL 3.5.9 を同じプロセスへ読み込み、OS → app と app → OS の両順を確認済みです。`OpenSSL_version()`、`OpenSSL_version_num()`、および `dladdr()` により各関数が対応するライブラリへ解決されることを確認しました。  
この実測を BL-003 の解消根拠として元 backlog に記録し、再現用の恒久テスト資産は追加しません。検討記録には環境、読み込み順、結果を残します。

## 局所検証と受入条件

### 共通生成処理と展開処理

共通生成器は、正常入力、不正・重複入力、ゼロ引数、関数ポインター引数、条件付き API、更新不要時の不変性を確認します。  
名前対応ヘッダーと解除ヘッダーが同じ一覧に従い、C と C++ の宣言として使えることを確認します。  
展開処理では、一時 app への展開とパッチ適用、一覧の変更、生成物の欠落、再実行、並列更新を確認します。  
Python のテストは `-X warn_default_encoding -W error::EncodingWarning` を付けて実行します。  
生成器や app の局所テストを個別に指定し、framework 全体のテストは実行しません。

### 公開名と同居

4 app の実ライブラリと mock ライブラリの公開シンボルを、それぞれ期待する固有名と完全一致で検査します。  
従来の関数・変数名がどちらのライブラリからも公開されず、公開ヘッダーにも旧 API 呼び出しマクロ名や新旧名をつなぐ alias macro がないことも合格条件とします。新しい固有名の API 呼び出しマクロは、対応する公開関数へ正しく展開されることを確認します。  
シンボルの型と元の関数シグネチャは維持し、Linux の SONAME を検査します。  
Windows では DLL の公開名、呼び出し規約、mock を含むリンクを確認します。

同名の未バージョン関数を公開する検証用共有ライブラリを作り、app の利用側と同じプロセスで動かします。  
OS 側を模した関数は app 側と異なる既知の結果を返すようにします。  
読み込み順を両方試し、OS 側と app 側がそれぞれの結果と関数の所属先を維持することを確認します。  
実ライブラリ内部から別の公開 API を呼ぶ経路も含め、内部参照の取り違えを検出します。  
実際の OS ライブラリが用意されている場合は、その同居確認を補足できますが、版の偶然の差だけを判定根拠にはしません。

### mock と利用側

4 app の mock テストで、既定の実委譲、注入した結果、ファイル名・行番号・関数名、関数ポインター経由の取得不能値、トレースを確認します。  
通常の C と C++ のテスト対象から差し替えヘッダーを使えることも確認します。  
初期化マクロ、可変長引数、公開変数、SQLite 拡張 API 表の経路を確認します。  
利用側の `EXPECT_CALL` と `ON_CALL` は先頭 3 引数へ追従し、戻り値と引数の既存の検証を維持します。  
影響する cplat の圧縮と symLoader 関連の末端テスト、および 4 app 内の関係する末端テストを実行します。

ビルド後に対象範囲の内容がある `.warn` を確認し、変更起因の失敗を修正して影響範囲を再検証します。  
Windows を実行できない場合は未確認として報告し、Linux の成功を代用しません。
