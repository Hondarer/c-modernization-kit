## 現行の合意内容

ユーザーが明示した内容のみを記載します。根拠はいずれも 2026-11-07 の対話での Tetsuo Honda の発言です。

- C ソースのコメント規範を作成します。抜粋数本にコメントを付与しながらルールを策定し、最終的に規範へ取り入れます。根拠は「抜粋数本でコメントを付与しながら、ルールを策定したい」「その結果を最終的には規範に取り入れる」です。
- 主要な制御構造と、処理の意図に補足が必要な箇所にはコメントを記述する考え方を取り入れ、インターネット上の事例も踏まえます。根拠は「主要な制御構造や、当該処理の意図に補足が必要な場合はコメントをすべきという考え方を取り入れ、インターネット上の事例も踏まえて」です。
- `if` ブロックなどの連続するブロックの間には空行を設けます。根拠は「ifブロックなどで連続したブロックの間には空行を設けたほうが読みやすい」です。
- ブロックの解説ではなく当該行に絞った解説として、後置コメントの例を盛り込みます。根拠は「後置コメントの例も盛り込んでほしい。(ブロックの解説ではなく、当該行に絞った解説もあると思う)」です。
- 前置コメントの直前には空行を設け、上の処理と分離します。根拠は、`sync_linux.c` の L433 と L434 の間 (閉じ波括弧と前置コメントの間) について「ブロックコメントの作用先は下側であって、上側と分離したほうが読みやすいため」と指示したことです。
- 数値リテラルの単位は `[ms]` のように角括弧で明示し、コメントの文中の単位にも角括弧を付けます。根拠は「数値リテラルの単位は、`[ms]` のように括弧で明示したい」「コメントの文中の単位にも `[]` を付与すべき」です。
- 検討文書は `app/general/docs/prompts/current/` に置き、ファイル名の先頭に `yymmdd-` を付けます。根拠は、検討文書の移動と `yymmdd-` の付与の指示です。

各事例に共通するのは、コードを読めば分かる手順 (HOW) を繰り返さず、コードから読み取れない目的と理由 (WHAT と WHY) を記述する点です。  
コメントで補う前に命名や関数分割でコードを分かりやすくし、外部仕様への依存、慣用から外れた書き方、一見不要に見える防御処理には、誤った削除や変更を防ぐ説明を残します。

ユーザーの指示である「主要な制御構造と、意図に補足が必要な箇所にはコメントを書く」は、Google や Linux の「分かりにくいブロックの前に配置する」方針に該当します。  
一方で、Linux の「関数本体には原則として記述しない」をそのまま適用すると、本リポジトリの複数の段階からなる長い関数を説明できません。  
そのため、試案では、関数本体で制御構造の単位 (処理の段落) に区切って段階の目的を記述することを許容しています。

同様に `reorder_gap_ready()` では、待機時間をずらす目的を前置コメントに残し、算出結果の範囲 (`ms 以上 2 * ms 未満`) を計算式の行の後置コメントにしました。

### 試行で分かった注意点

- **コメント内の `/*`**: `doc.c` の説明に Doxygen の開始記号を記述した際、コメント内に `/*` が入りました。`-Wcomment` の警告対象であり、CERT MSC04-C にも反するため、`'*'` と `'/'` に分解して記述します。
- **宣言側との重複**: porter のヘッダーには、N:1 で `peer` が解放されるなどの契約がすでに記載されています。関数本体では契約を繰り返さず、本体でしか分からない理由 (`slot_drain_recv_window()` で発火前に判定を控える理由など) だけを記述しました。
- **`static` 関数の定義前と本体内の使い分け**: 戻り値の意味や共通結果コードの対象外理由など、関数全体の契約に関わる説明は `static` 関数の定義直前に配置し、個々の制御構造や処理段階の説明は関数本体内の該当箇所の直前に配置しました。
- **句点の有無**: 前置コメントは完結した文として文末に句点 `。` を付け、後置コメントは行末の短い補足として句点を省くと、両者の役割と粒度が揃います (定型の誘導マーカー `/* Doxygen コメントは、ヘッダーに記載 */` は句点を付けません)。
- **識別子と用語の統一**: Doxygen の処理対象外である実装コメントでは Markdown のバッククォートを使用せず、識別子はコード上の表記 (`CLOCK_MONOTONIC`、`POTR_TYPE_UNICAST_BIDIR`、`pthread_mutex_trylock()` など) をそのまま記述します。1 文字の記号を地の文と区別する場合は `'<'` のようにシングル クォートで囲みます。また、モジュール内で確立した専門用語 (`ペイロード`、`リセット`、`起床` など) に統一します。
- **段落コメントの番号**: 当初は「1. 投入する」のように番号を付与しましたが、段階を追加・削除した際に振り直しが必要になるため廃止しました。
- **既存のコメントとの整合**: `sync_linux.c` や `thread_recv_window.c` に残っていた既存の実装コメントについて、敬体 (`ありません。`) や旧式の複数行形式 (` * ` なし) を今回の形式と常体へ統一しました。
- **推測による理由**: 理由を文書やコードで確認できない箇所があります。ソースから確認できたもの以外は、作者への確認が必要です ([Q-004](#q-004-読み書きロックで-pthread_rwlock_t-を使わない理由) から [Q-010](#q-010-制御パケットの送信失敗を再試行しないこと))。
- **後置コメントの長さ**: 後置コメントの説明を 2 行目へ続けると、`clang-format` がその行を直前の文の字下げ位置へ移します (ソース スタイル維持ガイドラインに記載の挙動)。後置コメントは 1 行に収まる長さに限り、収まらない場合は前置コメントにします。
- **後置コメントの桁揃え**: `clang-format` は、連続する行の後置コメントを同じ桁に揃えます。手作業では揃えません。
- **誘導マーカーの位置**: `doc.c` では、`/* Doxygen コメントは、ヘッダーに記載 */` が `static` 関数の前に 1 か所だけあり、ヘッダーで宣言した関数の前には配置されていませんでした。Doxygen コメント規範に合わせて移動しました。

配置先は [Q-001](#q-001-実装コメント規範の配置先) と [Q-012](#q-012-空行規則の配置先)、個別の Q がない規則の採否は [Q-019](#q-019-試案のうち個別の-q-がない規則の採否) で確認します。

### 実装コメントの試案

#### 適用範囲

- 関数本体のコメント、`static` 関数とファイル内変数の定義側コメント、プリプロセッサ分岐のコメントを対象とします。
- 宣言側の契約 (引数、戻り値、所有権、スレッド セーフ) は Doxygen コメント規範に従い、実装コメントでは繰り返しません。

#### 書く場面

次のいずれかに該当する場合は、実装コメントを記述します。

| 場面 | 記述する内容 |
|---|---|
| `static` 関数の役割や戻り値の意味が名前・型から自明でない | 関数の定義直前に、関数の目的、戻り値の意味、共通結果コードの対象外理由 |
| 関数が複数の段階からなる | 各段階の制御構造の前に、その段階が達成すること |
| 条件式の意味が式から読み取れない | 条件が表すドメイン上の状態 |
| ループの終了条件や走査範囲が自明でない | 停止する条件と、停止した後の状態 |
| より自然な書き方を選択しなかった | 選択しない理由。OS や規格に由来する場合は `see: <URL>` |
| 文の順序に制約がある | 入れ替えると整合性が崩れる理由 |
| 一見不要な処理、通常は到達しない経路がある | 削除すると発生する不具合 |
| 戻り値やエラーを意図的に処理しない | 処理しない理由 |
| 解放の位置や所有権の移動が非自明 | その位置で解放する理由、または所有権の移動先 |
| しきい値や定数の意味が名前から読み取れない | 値の意味と算出方法の根拠 |
| 書式や仕様の正本が別にある | 正本の文書と節 |

Table: 実装コメントを記述する場面と内容

#### 書かない内容

- コードの逐語訳 (「`i` を 1 増やす」など)、関数名や変数名から分かる内容
- 宣言側の Doxygen コメントにある契約の繰り返し
- 変更の経緯、作者、日付 (Git の履歴に残す)
- コメント アウトしたコード、`#if 0` で無効化したコード
- 確認していない推測の理由

コメントで補う前に、命名、関数分割、名前付き定数で意図を表せないかを検討します。  
TODO コメントの扱いは [Q-018](#q-018-todo-コメントの扱い) で確認します。

#### 配置と形式

前置コメントと後置コメントを、説明が及ぶ範囲で使い分けます。

| 種類 | 使用する場面 | 形式 |
|---|---|---|
| 前置コメント | ブロック、複数の文、関数全体にかかる説明、または 2 行以上になる説明 | 対象の直前に、同じ字下げで独立した行として配置し、文末に句点 `。` を付ける |
| 後置コメント | その行に限った説明 (単位、値の範囲、その 1 文の理由、メンバーの意味など) | 対象の行末に配置し、句点 `。` を省いて 1 行に収める |

Table: 前置コメントと後置コメントの使い分け

次の例 (`cplat` の `app_lock_take()`) では、ループ全体の方式と根拠を前置コメントに、1 行の数値の単位を後置コメントに記述しています。

```c
/*
 * flock() には期限付きの待機がないため、LOCK_NB で試行し、取得できなければ 1 [ms] 待機して期限まで繰り返す。
 * 呼び出し元で timeout_ms < 0 を拒否済みのため、ここでの timeout_ms は 0 以上の有限値である。
 * see: https://man7.org/linux/man-pages/man2/flock.2.html
 */
deadline = monotonic_ms() + (uint64_t)timeout_ms;
do
{
    if (flock(lock->fd, operation | LOCK_NB) == 0)
    {
        lock->locked = 1;
        return CPLAT_OK;
    }

    if (errno != EWOULDBLOCK && errno != EINTR)
    {
        return CPLAT_ERR_UNKNOWN;
    }

    if (timeout_ms == CPLAT_SYNC_NO_WAIT)
    {
        return CPLAT_ERR_BUSY;
    }

    {
        struct timespec sleep_ts = {0, 1000000L}; /* 1 [ms] */
        nanosleep(&sleep_ts, NULL);
    }
} while (monotonic_ms() < deadline);
```

```c
/* 望ましくない: 1 文だけに関わる説明を前置にし、後続の文にもかかるように読める */
/* NACK と REJECT は対象通番を ack_num に持つ。 */
memcpy(nonce + 6, &pkt->ack_num, 4);
memset(nonce + 10, 0, 2);

/* 望ましい: その行に限った説明は後置にする */
memcpy(nonce + 6, &pkt->ack_num, 4); /* NACK と REJECT は対象通番を ack_num に持つ */
memset(nonce + 10, 0, 2);
```

- 後置コメントは、`if`、`for`、`while` の条件の行と、波括弧だけの行には付与しません。ブロック全体の説明と区別できなくなるため、前置コメントにします。
- 後置コメントの桁は `clang-format` の整形結果に従い、手作業で揃えません。
- 後置コメントを 2 行以上に続けません。1 行に収まらない場合は前置コメントにします。
- コメント中の単位は、後置コメントか文中かによらず、値の後ろへ半角空白を置いて角括弧で示します (`/* 1 [ms] */`、「1 [ms] 間隔で繰り返す」)。
- リテラルと異なる単位へ換算して示す場合は、換算後の値と単位を記述します (ナノ秒の値である `1000000L` を `1 [ms]` と記述するなど)。
- 角括弧を付けるのは、時間、データ量、割合などの単位 (`[ms]`、`[ns]`、`[s]`、`[byte]`、`[%]` など) とします。データ量は `[byte]` と記述します。「1 文字」「10 倍」「3 件」などの助数詞は単位ではないため、角括弧を付けません。
- 1 行に収まる前置コメントは `/* 文。 */`、複数行の前置コメントは次の形式とします (形式は [Q-003](#q-003-複数行コメントの形式) で確認します。定型の誘導マーカー `/* Doxygen コメントは、ヘッダーに記載 */` は句点を付けません)。

```c
/*
 * 1 行目の文。
 * 2 行目の文。
 * see: https://example.com/
 */
```

- `see: <URL>` は、その根拠に依存する説明の最終行に配置します。
- コメント内に `/*` を記述しません。記号を説明する場合は分解して記述します。
- C のソースでは `//` を使用しません。Doxygen の `@code` 内のコード例は、既存の「Doxygen コード例内のコメント形式」に従って `//` を使用します。C++ のテスト コードは対象外とします。
- 段落コメントに番号を付けません。

#### 文体と表記

- 実装コメントは常体 (「〜する」「〜である」) で記述し、Doxygen コメントの敬体と区別します (文体は [Q-002](#q-002-実装コメントの文体) で確認します)。
- 識別子は Markdown のバッククォートで囲まず、コード上の表記をそのまま使用します。関数は `name()` と記述し、1 文字の記号を地の文と区別する場合は `'<'` のようにシングル クォートで囲みます。
- 日本語の表記と表現は [日本語技術文書の文章規範](../../../../../framework/docsfw/docs/japanese-technical-writing-guideline.md) に従います。

#### 保守

- コードを変更する際は、同じ変更の中で該当するコメントを更新します。コードと矛盾するコメントは不具合として扱います。
- 説明の対象がなくなったコメントは削除します。

#### 検証

コメント内の `/*` は、GCC の `-Wall` に含まれる `-Wcomment` が警告します。ビルド後の `.warn` が空であることで確認します。  
`grep` による検出は、ポインターの間接参照で始まる行を誤検出するため採用しません。

```bash
# C のソースの行頭 // (Doxygen の @code 内のコード例を目視で除外し、残りが 0 件であること)
grep -rn -P '^\s*//' --include='*.c' --include='*.h' <対象 app>/prod

# コメントアウトしたコードの候補 (セミコロンや波括弧で終わる 1 行コメント。0 件であること)
grep -rn -P '^\s*/\*(?![*!]).*(;|\{|\})\s*\*/\s*$' --include='*.c' --include='*.h' <対象 app>/prod
```

試行時点で、`cplat`、`porter`、`struct-meta` の `prod` 配下は、行頭 `//` がすべて `@code` 内のコード例であり、コメント アウトの候補は 0 件でした。  
ただし、この `grep` はコメント アウトしたコードをすべては検出できません。`app/override-sample/prod/libsrc/base/sym_loader_libbase.c` の `/* &sfo_base_name, */ /* 将来追加 */` は、カンマで終わり後置コメントが続くため検出されません。検出の補助にとどめ、レビューで確認します。

### 空行の試案 (コメントとは別の規則)

#### 規則

次の 2 か所には空行を 1 行挿入します。

| 対象 | 理由 |
|---|---|
| 連続するブロックの間 | ブロックの境目を見分けやすくする |
| 前置コメントの直前 | 前置コメントが作用する下の処理とひとまとまりにし、上の処理と切り離す |

Table: 空行を入れる箇所と理由

ここでのブロックは、`if`、`for`、`while`、`switch`、`do` の文と、波括弧だけで始まるブロックを指します。  
`do` 文の末尾 `} while (...);` もブロックの終わりとして扱います。

```c
/* 望ましい: 連続する if の間に空行を入れる */
if (rc == 0)
{
    return CPLAT_OK;
}

if (rc == ETIMEDOUT)
{
    return CPLAT_ERR_TIMEOUT;
}
```

```c
/* 望ましくない: 閉じ波括弧の直後に次の if が続く */
if (rc == 0)
{
    return CPLAT_OK;
}
if (rc == ETIMEDOUT)
{
    return CPLAT_ERR_TIMEOUT;
}
```

```c
/* 望ましくない: 前置コメントが直前の if に接し、どちらにかかるか見分けにくい */
if (timeout_ms == CPLAT_SYNC_NO_WAIT)
{
    return map_wait_rc(pthread_mutex_trylock(&mtx->native));
}
/*
 * pthread_mutex_timedlock() は期限を CLOCK_REALTIME で判定するため使わず、
 * ...
 */
deadline = monotonic_ms() + (uint64_t)timeout_ms;
```

```c
/* 望ましい: 前置コメントの上に空行を入れ、下の処理とひとまとまりにする */
if (timeout_ms == CPLAT_SYNC_NO_WAIT)
{
    return map_wait_rc(pthread_mutex_trylock(&mtx->native));
}

/*
 * pthread_mutex_timedlock() は期限を CLOCK_REALTIME で判定するため使わず、
 * ...
 */
deadline = monotonic_ms() + (uint64_t)timeout_ms;
```

連続するブロックの間では、次の場合は同じ文の続きか外側のブロックの終わりであるため、空行を入れません。

- `else`、`else if` が続く場合
- `do` 文の `} while (...);` の場合 (閉じ波括弧と `while` の間)
- 外側のブロックの閉じ波括弧が続く場合
- 字下げの異なる行 (プリプロセッサ指令、`case` ラベルなど) が続く場合

前置コメントの直前では、次の場合は空行を入れません。

- ブロックの先頭 (`{` の直後)
- `case`、`default`、`goto` のラベルの直後
- プリプロセッサ指令の直後
- 別のコメントの直後

後置コメントはその行の一部であるため、この規則の対象外とします。

`clang-format` には、この空行を挿入する設定がありません。  
一方で、既存の空行は `MaxEmptyLinesToKeep` (LLVM の既定値は 1) の範囲で保持されるため、手作業で入れた空行は整形後も維持されます。

#### 試行と件数

試行の 3 本へ機械的に適用しました。連続するブロックの間が 61 件 (`porter` 2 件、`struct-meta` 26 件、`cplat` 33 件)、前置コメントの直前が 3 件 (`struct-meta` 1 件、`cplat` 2 件) でした。  
前置コメントの直前の 3 件は、閉じ波括弧の後に前置コメントと通常の文が続く形 (`cplat` の `cplat_local_lock_lock()`)、ループの後に前置コメントが続く形 (`struct-meta` の `extract_brief_tag()`)、`} while (...);` の後に前置コメントが続く形 (`cplat` の `cplat_thread_join()`) です。
