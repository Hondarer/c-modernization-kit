# 失敗を検査していない 16 件の対処と、失敗の扱いの 5 分類の規範化 最終仕様

## 目的と範囲

戻り値を検査していない、または失敗を呼び出し元へ伝えていない 16 件の呼び出しについて、失敗の扱いを決めて実装へ反映します。  
あわせて、扱いを決めるための分類を、コーディング規範へ追加します。今後の変更でも同じ判断ができるようにするためです。

対象は次の 3 つです。

- 16 件の対象ソース、関連する公開ヘッダー、テスト
- コーディング規範 (`app/general/docs/coding-guideline.md`、`app/cplat/docs/coding-guideline.md`)
- 規範を確認するスキル (`check-coding-guideline`)

対象外は次のとおりです。

- 16 件以外の既存の `(void)` の呼び出しへの理由コメントの追加
- 規範への適合を機械的に判定する仕組み (コンパイラの警告、解析ツール)
- 失敗を注入できない呼び出しのための、テスト用の差し替えの仕組みの追加

## 失敗の扱いの 5 分類

### 分類の定義

失敗しうる呼び出しの扱いを、失敗の情報の行き先で 5 つに分類します。

Table: 失敗の扱いの 5 分類

| 分類 | 失敗の情報の行き先 | 判定の条件 | 扱い |
| --- | --- | --- | --- |
| 異常終了 | プロセスの終了 | 原因が OS や基盤の異常、または内部状態の破壊に限られる。かつ、続行が危険または構造上できない。 | 異常終了の機構を呼ぶ。Doxygen に、プロセスを終了させうることを記載する。 |
| 伝達 | 呼び出し元 | 失敗すると、関数が文書で約束した結果、またはコマンドの成果物が成立しない。呼び出し元が失敗を受けて行動できる。 | 戻り値または終了コードで伝える。 |
| 診断して続行 | 診断の出力 | 関数の主な結果は成立するが、利用者が知らないと後で原因を調べられない。 | その場所ですでに使っている診断の経路へ出力し、処理を続ける。 |
| 明示的な破棄 | 呼び出し元が受け取って捨てる | 呼び出した関数は結果を返すが、失敗しても呼び出し側の結果が変わらない。または、失敗を伝える先がない。 | 呼び出しに `(void)` を付け、理由コメントを付ける。 |
| 通知なし (void) | 関数の外へ出さない | 関数の呼び出し元が、失敗を受けても取れる行動がない。解放、破棄、表示、通知の関数が該当する。 | 関数の戻り値を `void` とする。Doxygen に、失敗を通知しないことを記載する。 |

異常終了の条件は、既存の規範「プロセスの異常終了 (abort)」の条件と同じです。引数の不正、外部入力の不正、ファイル、通信、メモリ確保の失敗、呼び出し元が回復できる失敗には適用しません。

### 判定の手順

呼び出し 1 箇所ごとに、次の問いを上から順に当てはめ、最初に当てはまった分類を採用します。

1. 失敗の原因は、OS や基盤の異常、または内部状態の破壊に限られますか。かつ、続行すると危険ですか、または構造上続行できませんか。当てはまる場合は、異常終了とします。
2. 失敗すると、関数が文書で約束した結果、またはコマンドの成果物が成立しなくなりますか。かつ、呼び出し元は失敗を受けて行動できますか。当てはまる場合は、伝達とします。
3. 利用者が失敗を知らないと、後で原因を調べられなくなりますか。当てはまる場合は、診断して続行とします。
4. いずれにも当てはまらない場合は、明示的な破棄とします。

関数の型は、呼び出しの扱いとは別に決めます。呼び出し元が失敗を受けて取れる行動がある場合は、結果を返す型とします。行動がない場合は、通知なし (void) とします。

### 重なりの規則

通知なし (void) は関数の型についての決定であり、ほかの 4 つは呼び出し 1 箇所ごとの決定です。そのため、次の規則を置きます。

- 関数を通知なし (void) とした場合も、関数の中の失敗しうる呼び出しには、異常終了、診断して続行、明示的な破棄のいずれかを必ず決めます。
- 検査も `(void)` もない呼び出しを残しません。

> [!IMPORTANT]
> 「関数が `void` だから、中の呼び出しの戻り値は扱わなくてよい」とは読みません。今回の 16 件のうち 7 件は、`void` の関数の中に、検査も理由もない呼び出しが残っていた箇所です。

### ストリームへの出力の検査

標準入出力のストリームへの書き込みは、書き込みごとに検査しなくてもかまいません。書き込みの失敗はストリームのエラー指示子に残るためです。  
この場合は、成果物を確定する位置 (ファイルを閉じる直前、コマンドの終了の直前) で、`fflush` の戻り値と `ferror` をまとめて検査します。途中の書き込みと `fflush` は明示的な破棄とし、まとめて検査する位置を理由コメントに書きます。

### 明示的な破棄の理由コメント

`(void)` で戻り値を破棄する呼び出しには、破棄する理由のコメントを常に付けます。置き方は、既存の規範「前置コメントと後置コメント」に従います。

- 理由が短く、呼び出しの内容から読み取れる可能性が高い場合は、後置コメントとします。
- 説明が必要な場合 (1 行に収まらない場合、根拠の URL を付ける場合) は、前置コメントとします。
- 同じ理由の破棄が連続する場合は、そのまとまりの直前の前置コメント 1 つでかまいません。まとまりは、連続する文、1 つの関数、または同じ役割の関数が並ぶ節とします。

```c
(void)cplat_fprintf(stderr, "error: failed to open %s\n", csv_path); /* 診断の出力先がほかにない */
```

```c
/* _dup2 失敗後の後始末であり、すでに -1 を返す経路のため _close 失敗で結果は変わらない。 */
(void)_close(new_fd);
```

> [!NOTE]
> 3 つ目の規則 (まとまりの前の前置コメント 1 つ) は、「常に付ける」という決定と、「理由を 1 か所に記載する」という個別の決定 (ワーカーのトレース出力) の両方を満たすための規定です。同じ文面のコメントが並んで、読む価値のあるコメントが埋もれることを避けます。

### crypto_windows.c (032)

`BCryptDestroyKey`、`BCryptDestroyHash`、`BCryptCloseAlgorithmProvider` の 8 箇所を、失敗時に異常終了する内部関数の呼び出しへ置き換えます。

- 解放関数ごとに `static` の内部関数を 1 つ設けます。内部関数は戻り値を検査し、失敗時に `CPLAT_ABORT` を呼びます。
- 内部関数のコメントに、異常終了とする理由と、根拠の URL (`see:`) を記載します。
- 暗号化、復号、鍵導出の公開関数の Doxygen に、`@attention` でプロセスを終了させうることを記載します。終了させうるのは Windows の実装であることも記載します。
- `app/cplat/docs/api-cheatsheet.md` の該当箇所を確認し、必要な場合は更新します。

Linux の実装 (`crypto_linux.c`) は変更しません。解放に使う `EVP_CIPHER_CTX_free()` と `EVP_MD_CTX_free()` は戻り値が `void` であり、失敗を返しません。検査する対象がないため、5 分類のどの扱いも要りません。  
OS による扱いの違いは、バックエンドの API が失敗を返すかどうかの違いから生じます。この違いを、公開関数の Doxygen の `@attention` に記載します。

> [!NOTE]
> Microsoft の文書が挙げる解放関数の失敗は、ハンドルが無効な場合だけです。ハンドルは直前まで正常に使えていたため、失敗は内部状態の破壊を示します。続行すると、鍵のデータが解放されないままプロセスのメモリに残る可能性があります。同期プリミティブの実装が、正しく使っていれば失敗しない解放の失敗で異常終了している扱いと同じです。  
> 無効なハンドルをテストで作る手段がないため、異常終了の経路は実行して確認しません。  
> OpenSSL の文書は、`EVP_CIPHER_CTX_free()` がコンテキストの情報をすべて消去してメモリを解放すること、引数が NULL の場合は何もしないことを定めています。戻り値の節に、2 つの解放の関数の記載はありません。  
> see: https://docs.openssl.org/3.0/man3/EVP_EncryptInit/  
> see: https://docs.openssl.org/3.0/man3/EVP_DigestInit/

### elevated_process.c と elevated_process.h (043、044、045、047、048)

`reopen_std_stream()` と `cplat_elevated_process_attach_output_pipes()` を変更します。

- 044: `(void)fflush(stream);` に理由コメントを付けます。プログラムの開始直後に呼ぶ契約であり、未出力のデータがなく、付け替え前の出力先は捨てる対象です。
- 045: `(void)_close(expected_fd);` に理由コメントと `see:` を付けます。失敗はファイル記述子がすでに無効な場合だけであり、閉じられずに残った場合も、後続の `_dup2` が複製先を閉じてから複製します。
- 047: `_dup2` 成功後の `(void)_close(new_fd);` に理由コメントを付けます。付け替え先のファイル記述子はすでに成立しており、失敗しても余分なファイル記述子が 1 つ残るだけです。
- 048: `SetStdHandle()` の戻り値を検査し、失敗時は `reopen_std_stream()` が -1 を返します。公開関数は、既存の経路で `CPLAT_ERR_UNKNOWN` を返します。
- 043: `setvbuf()` の戻り値を検査し、失敗時は公開関数が `CPLAT_ERR_UNKNOWN` を返します。

公開ヘッダーの `cplat_elevated_process_attach_output_pipes()` の Doxygen に、次の契約を追加します。

- 失敗を返した場合、標準ストリーム (stdin、stdout、stderr) と Win32 の標準ハンドルの状態は不定です。付け替え前の状態へは戻しません。
- 失敗を受けた呼び出し元は、標準出力と標準エラー出力に頼らず、プロセスを終了します。

`app/cplat/docs/api-cheatsheet.md` の該当箇所を確認し、必要な場合は更新します。

> [!NOTE]
> 付け替え前の出力先は、昇格プロセスの非表示のコンソールです。戻しても利用者は出力を見られないため、戻す処理は追加しません。stdout の付け替えに成功した後で stderr の付け替えに失敗した場合に状態が戻らないことは、変更前の実装も同じです。

### trace_file.c (110)

`close_file()` が結果を返すように変更し、書き込みの経路で失敗を伝達します。公開関数の型は変わりません。

- `close_file()` は、`cplat_file_close()` が失敗した場合に `CPLAT_ERR_UNKNOWN`、それ以外の場合に `CPLAT_OK` を返します。
- `rotate_file()` は、閉じる処理の結果を返します。閉じる処理が失敗しても、世代の移動と新しいファイルを開く処理は続けます。
- `check_rotate_shared()` は、閉じる処理の失敗とプロセス間ロックの解放の失敗のいずれかがあった場合に `CPLAT_ERR_UNKNOWN` を返します。
- 書き込み関数は、書き込み前の開き直しとローテーションで閉じる処理が失敗した場合も、開き直しと書き込みを続け、最後に `CPLAT_ERR_UNKNOWN` を返します。
- `free_sink()` は、`(void)close_file(p);` として理由コメントを付けます。破棄の後に失敗を受けても、呼び出し元が取れる行動がないためです。

> [!NOTE]
> `cplat_file_close()` は、閉じる処理を呼ぶ前にハンドルを無効な値へ書き換えます。そのため、失敗の後に同じハンドルを再び閉じることはなく、続けて新しいファイルを開けます。  
> 閉じる処理が失敗した場合、成功を返した過去の行が保存されていない可能性があります。失敗を返すのは、その可能性を呼び出し元へ知らせるためです。

### bench-io (121)

`main` で、CSV を閉じる前に書き込みの失敗を検査します。

- `fclose(csv)` の前に `ferror(csv)` を検査します。エラーがある場合は、標準エラー出力へ診断を出し、失敗の件数を増やします。終了コードは `EXIT_FAILURE` になります。
- `bench_report_begin_csv()` と `bench_report_row()` は `void` のままとします。各関数の CSV への書き込みのまとまりの前に、理由コメント (書き込みの失敗はストリームに残り、`main` が閉じる前に検査する) を付けます。
- 2 つの関数の Doxygen に、書き込みの失敗を通知しないことと、呼び出し元が `ferror` で検査することを記載します。

### override-sample (137、138)

- 137: `base_console_output()` は `void` のままとします。実装の `vprintf` に `(void)` と理由コメントを付けます。公開ヘッダー `base_spec.h` の Doxygen に、出力の失敗を通知しないことを記載します。`prod/README.md` の関数の説明を確認し、必要な場合は更新します。
- 138: `onLoad()` で、一時ディレクトリの取得に失敗した場合は、原因によらず設定ファイルのパスを空にし、`CPLAT_DLLMAIN_INFO_MSG` で上書きを無効にしたことを出力します。`cplat_module_get_basename()` が失敗した場合も、同じ扱いとします。診断の文面は、原因 (パスが長すぎる、一時ディレクトリを取得できない、モジュール名を取得できない) を区別します。

### service-sample_windows.c (163、166)

- 163: `ChangeServiceConfig2U()` (サービスの説明) の戻り値を検査し、失敗時に WARNING のトレースを `GetLastError()` の値を付けて出します。インストールは続けます。直後の同種の設定 3 件と同じ書き方です。
- 166: `SetServiceStatus()` の 3 箇所の呼び出しを、1 つの `static` の内部関数にまとめます。内部関数は、失敗時に `GetLastError()` の値を付けた ERROR のトレースを出し、処理を続けます。再試行はしません。

> [!NOTE]
> 通知が失敗した場合、サービスを停止へ進めても、その停止の通知が同じ理由で失敗する可能性が高く、SCM (Windows のサービスを管理する機構) が持つ状態とのずれは解消できません。トレースに残して、原因を後から調べられるようにします。  
> 再試行をしないのは、Microsoft の文書が `SERVICE_STOPPED` の通知を 1 回だけとしているためです。

### string-catalog-sample (168、170、172)

- 168: `string-catalog-filter-sample.c` の `emit_*()` の 7 関数の並びの直前に、前置コメントで理由を 1 か所に記載します。トレースは動作を観測する手段であり、出力の失敗でワーカーの処理を止めないためです。動作は変えません。
- 170: `string-catalog-library-sample.c` の `main` で、途中の 3 箇所の `fflush(stdout)` に `(void)` と理由コメントを付けます。`main` の終了の直前に `fflush(stdout)` と `ferror(stdout)` を検査し、失敗時は標準エラー出力へ診断を出して `EXIT_FAILURE` を返します。
- 172: `samplecatalog_trace_key_lookup_performed()` の戻り値を検査し、失敗時は標準エラー出力へ診断を出して `EXIT_FAILURE` を返します。

> [!NOTE]
> 168 と 172 は同じ種類の呼び出しですが、扱いが異なります。172 はサンプルが見せる手順そのものであり、`main` の中で 1 回だけ呼ぶため、終了コードで伝えられます。168 はワーカーの処理に付随する観測であり、周期ごとに繰り返されます。

### struct_meta_sample.c (184)

`cmd_dumpjson()`、`cmd_catjson()`、`cmd_dumpbin()`、`cmd_catbin()` の `cplat_fflush(stdout, NULL)` の戻り値を検査します。失敗時は、標準エラー出力へ結果コードを付けた診断を出します。関数は `void` のままとし、対話を続けます。同じ関数の中の書き込みの失敗と同じ扱いです。

## 規範への反映

### 共通のコーディング規範

`app/general/docs/coding-guideline.md` の「エラー処理と戻り値規約」に、小節「失敗の扱いの分類」を「適用対象外」の前へ追加します。内容は、この文書の「失敗の扱いの 5 分類」の各節です。

Table: 共通の規範へ追加する内容

| 追加する項 | 内容 |
| --- | --- |
| 分類 | 5 分類の表。分類の名前に、原文を確認できた英語の呼び方を併記する。 |
| 判定の手順 | 上から順に当てはめる 4 つの問いと、関数の型の決め方。 |
| void の関数の中の呼び出し | 重なりの規則。 |
| ストリームへの出力の検査 | まとめて検査する規則。 |
| 明示的な破棄の理由コメント | 常に付けること、置き方、まとまりの扱い、望ましい例と望ましくない例。 |
| レビューの手順 | 次項に示す自然文の手順。 |
| 既存コードへの適用 | 新規のコードと変更するコードに適用する。既存の `(void)` の箇所は、残課題として管理し、変更の機会に適用する。 |

共通の規範は、個別の app の機構の名前を使いません。異常終了の機構は、既存の節「プロセスの異常終了 (abort)」を参照する形で示します。

既存の節には、次の参照を追加します。

- 「実装コメント」の「書く場面」の行「戻り値やエラーを意図的に処理しない」から、新しい小節への参照
- 「プロセスの異常終了 (abort)」から、新しい小節への参照
- 「エラー処理と戻り値規約」の「検証」に、理由コメントのない `(void)` の候補を探すコマンド

> [!NOTE]
> 検証のコマンドは、候補を探す補助です。合否は判定しません。関数が値を返すかどうか、理由が妥当かどうかは文字列の検索では判定できないため、判定はレビューの手順で行います。

### レビューの手順

レビューの手順は、人とエージェントが同じ観点で確認できるよう、自然文で記載します。記載する手順は次のとおりです。

1. 変更した範囲から、戻り値を返す関数の呼び出しを挙げます。関数が値を返すかどうかは、宣言を読んで確かめます。
2. それぞれの呼び出しが、戻り値を検査しているか、`(void)` を付けているかを確かめます。どちらでもない呼び出しは指摘します。
3. 戻り値を検査している呼び出しは、失敗時の扱いが判定の手順の結果と合うかを確かめます。
4. `(void)` を付けている呼び出しは、理由コメントがあるか、理由が判定の手順の 4 つ目に当たるかを確かめます。理由が「失敗しないはず」だけの場合は、根拠 (契約、一次資料) があるかを確かめます。
5. `void` の関数を追加または変更した場合は、呼び出し元が失敗を受けて取れる行動がないかを確かめます。Doxygen に、失敗を通知しないことが書かれているかも確かめます。
6. 異常終了を使っている場合は、条件を満たすか、Doxygen にプロセスを終了させうることが書かれているかを確かめます。

### cplat のコーディング規範

`app/cplat/docs/coding-guideline.md` の `CPLAT_ABORT` を定める節に、共通の規範の「異常終了」に当たる機構が `CPLAT_ABORT` であることと、共通の規範の小節への参照を追加します。

### スキル

`app/general/.agents/skills/check-coding-guideline/SKILL.md` の、節を選ぶ手がかりの列挙に「失敗の扱い (戻り値の検査と破棄)」を加えます。手順の本文は規範に置き、スキルには複製しません。  
変更後、スキルの同期の手順 (`app/general/docs/skill-sync.md`) に従って配布先へ反映します。
