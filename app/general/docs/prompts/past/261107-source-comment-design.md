# C ソースの実装コメント規範と空行規則 最終仕様

ファイル名: `261107-source-comment-design.md`

## 目的と範囲

C / C++ のソースで、コードから読み取れない目的と理由を保守者へ伝えるため、実装コメントの規範と、処理を区切る空行の規則を定めます。  
規範は `app/general/docs/coding-guideline.md` に記載し、第一者の全 app の製品コードへ同じ作業の中で適用します。

| R-2 | 空行規則の新設 (`coding-guideline.md` に「処理を区切る空行」節を新設) |

| T-1 | 空行の検出・挿入スクリプトとテストの追加 (`app/general/bin/`、`app/general/bin_test/`) |
| A-1 | 各 app の `prod/` 配下 (10 app、418 本) への書式、空行、内容の一括適用 |

範囲外は次のとおりです。

## 実装コメント規範 (R-1)

`coding-guideline.md` の「コメントの記載量」節を「実装コメント」節へ拡張し、既存の makefile 断片の例 (自明な追加には理由を書かない例と、非標準の指定に理由を書く例) を同じ節に残します。  
本節の内容は、次の小節として記載します。

### 適用範囲

- 関数本体のコメント、`static` 関数とファイル内変数の定義側コメント、プリプロセッサ分岐のコメントを対象とします。プリプロセッサ分岐 (`#else`、`#endif`) の書式は [fix-if-comments](../../fix-if-comments.md) に従います。
- 宣言側の契約 (引数、戻り値、所有権、スレッド セーフ) は [app 向け Doxygen コメント](../../doxygen-comment-guideline.md) に従い、実装コメントでは繰り返しません。
- `app/` 配下の `makepart.mk` など make ファイル断片のコメントにも、記載量の原則 (自明な内容を書かず、読み取れない意図を書く) を適用します。

### 書く場面

次のいずれかに該当する場合は、実装コメントを記述します。

| 場面 | 記述する内容 |
|---|---|
| `static` 関数の役割や戻り値の意味が名前・型から自明でない | 関数の定義直前に、関数の目的、戻り値の意味、共通結果コードの対象外理由 |
| 関数が複数の段階からなる | 各段階の制御構造の前に、その段階が達成すること |
| 条件式の意味が式から読み取れない | 条件が表すドメイン上の状態 |
| ループの終了条件や走査範囲が自明でない | 停止する条件と、停止した後の状態 |
| より自然な書き方を選択しなかった | 選択しない理由。OS や規格に由来する場合は `see: <URL>` |
| 文の順序に制約がある | 入れ替えると整合性が崩れる理由 |
| 一見不要な処理、通常は到達しない経路がある | 削除すると発生する不具合 |
| 戻り値やエラーを意図的に処理しない | 処理しない理由 |
| 解放の位置や所有権の移動が非自明 | その位置で解放する理由、または所有権の移動先 |
| しきい値や定数の意味が名前から読み取れない | 値の意味と算出方法の根拠 |
| 書式や仕様の正本が別にある | 正本の文書と節 |

Table: 実装コメントを記述する場面と内容

### 書かない内容

- コードの逐語訳 (「`i` を 1 増やす」など)、関数名や変数名から分かる内容
- 宣言側の Doxygen コメントにある契約の繰り返し
- 変更の経緯、作者、日付 (Git の履歴に残します)
- コメント アウトしたコード、`#if 0` で無効化したコード
- コードや文書で確認していない推測の理由
- TODO コメント。ただし、利用者が処理を書き足す位置を示す雛形 (サンプルの `/* TODO: ここに初期化処理を書く */` など) は許容します。

コメントで補う前に、命名、関数分割、名前付き定数で意図を表せないかを検討します。

> [!NOTE]
> Linux kernel coding style は関数本体のコメントを短い注記に限りますが、本規範は複数の段階からなる長い関数を説明するため、制御構造の単位 (処理の段落) で段階の目的を記述することを許容します。

### 前置コメントと後置コメント

| 種類 | 使用する場面 | 形式 |
|---|---|---|
| 前置コメント | ブロック、複数の文、関数全体にかかる説明、または 2 行以上になる説明 | 対象の直前に、同じ字下げで独立した行として配置し、文末に句点 `。` を付ける |
| 後置コメント | その行に限った説明 (単位、値の範囲、その 1 文の理由、メンバーの意味など) | 対象の行末に配置し、句点 `。` を省いて 1 行に収める |

Table: 前置コメントと後置コメントの使い分け

- 後置コメントは、`if`、`for`、`while` の条件の行と、波括弧だけの行には付与しません。
- 後置コメントを 2 行以上に続けません。1 行に収まらない場合は前置コメントにします (2 行目は `clang-format` が直前の文の字下げ位置へ移すためです)。
- 閉じ波括弧と `else` の間にはコメントを置きません。`else` 側の説明は、`if` の連鎖の前の前置コメントか、`else` のブロックの中に書きます。
- 後置コメントの桁は `clang-format` の整形結果に従い、手作業で揃えません。
- 定義群や節の見出しなど、文ではない体言止めのラベル (`/* 分類不能 */`、罫線付きの節見出しなど) と、定型の誘導マーカー `/* Doxygen コメントは、ヘッダーに記載 */` は句点を付けません。

正本には、cplat の `app_lock_take()` のループ (前置コメントで方式と根拠、後置コメントで `/* 1 [ms] */`) と、porter の nonce 構築 (1 文だけに関わる説明を後置へ分離する、望ましい例と望ましくない例) を記載します。

### 形式

- 1 行に収まる前置コメントは `/* 文。 */` とします。
- 複数行のコメントは、`/*` だけの行で始め、各行を ` * ` で始め、`*/` だけの行で終えます。
- `see: <URL>` は、その根拠に依存する説明の最終行に配置します。
- コメント内に `/*` を記述しません。記号を説明する場合は `'*'` と `'/'` に分解して記述します。
- C のソースでは `//` を使用しません。Doxygen の `@code` 内のコード例は、既存の「Doxygen コード例内のコメント形式」に従って `//` を使用します。
- 段落コメントに番号を付けません。
- コンパイラや解析ツールが認識する注記 (`/* fall through */`、`/* coverity[...] */`、`// clang-format off` など) は、ツールが定める形のまま独立したコメントとして残し、ほかの説明と 1 つのコメントにまとめません。

### 単位の表記

- コメント中の単位は、後置コメントか文中かによらず、値の後ろへ半角空白を置いて角括弧で示します (`/* 1 [ms] */`、「1 [ms] 間隔で繰り返す」)。
- リテラルと異なる単位へ換算して示す場合は、換算後の値と単位を記述します (ナノ秒の値である `1000000L` を `1 [ms]` と記述するなど)。
- 角括弧を付けるのは、時間、データ量、割合などの単位 (`[ms]`、`[ns]`、`[s]`、`[byte]`、`[%]` など) とします。データ量は `[byte]` と記述します。
- 「1 文字」「10 倍」「3 件」などの助数詞は単位ではないため、角括弧を付けません。

### 文体と表記

- 実装コメントは常体 (「〜する」「〜である」) で記述します。
- 識別子は Markdown のバッククォートで囲まず、コード上の表記をそのまま使用します。関数は `name()` と記述し、1 文字の記号を地の文と区別する場合は `'<'` のようにシングル クォートで囲みます。
- モジュール内で確立した専門用語に統一します。
- 日本語の表記と表現は [日本語技術文書の文章規範](../../../../../framework/docsfw/docs/japanese-technical-writing-guideline.md) に従います。

> [!NOTE]
> 実装コメントを常体とするのは、敬体の Doxygen コメント (宣言側の契約) と見分けるためです。

### 保守

- コードを変更する際は、同じ変更の中で該当するコメントを更新します。コードと矛盾するコメントは不具合として扱います。
- 説明の対象がなくなったコメントは削除します。

### 検証

- コメント内の `/*` は、GCC の `-Wall` に含まれる `-Wcomment` が警告します。ビルド後の `.warn` が空であることで確認します。
- C のソースの行頭 `//` は `grep -rn -P '^\s*//'` で検出し、Doxygen の `@code` 内のコード例を目視で除外して 0 件であることを確認します。
- コメント アウトしたコードの候補は `grep -rn -P '^\s*/\*(?![*!]).*(;|\{|\})\s*\*/\s*$'` で検出し、0 件であることを確認します。この検出は補助であり、カンマで終わる要素などは検出できないため、レビューで確認します。

## 空行規則 (R-2)

`coding-guideline.md` に「処理を区切る空行」節を新設します。

### 空行を入れる箇所

次の箇所には空行を 1 行入れます。

| 箇所 | 例 |
| --- | --- |
| 連続するブロックの間 | `}` の直後に次の `if` |
| ブロックの後に通常の文が続く箇所 | `}` の直後に代入や `return` |
| 通常の文の後にブロックが続く箇所 | 代入の直後に `if` |
| 前置コメントの直前 | 処理の直後に、次の処理の前置コメント |
| 関数末尾の `return` の直前 | 関数の最後の文としての `return` |

Table: 空行を入れる箇所

ここでのブロックは、`if`、`for`、`while`、`switch`、`do` の文と、波括弧だけで始まるブロックを指します。`do` 文の末尾 `} while (...);` もブロックの終わりとして扱います。  
後置コメントはその行の一部であるため、前置コメントの規則の対象外とします。

> [!NOTE]
> 前置コメントが作用するのは下の処理です。上の処理と空行で切り離すと、どの処理にかかる説明かを見分けやすくなります。

### 空行を入れない場合

ブロックの前後では、次の場合は空行を入れません。

- `else`、`else if` が続く場合
- `do` 文の閉じ波括弧と `while` の間
- 外側のブロックの閉じ波括弧が続く場合
- 字下げの異なる行 (プリプロセッサ指令、`case` ラベルなど) が続く場合
- 直前の文で代入した値を、ブロックの条件 (`if`、`while`、`switch` の式、`for` の条件) で判定する場合 (通常の文の後にブロックが続く箇所に限ります。`do` 文は含めません)

前置コメントの直前では、次の場合は空行を入れません。

- ブロックの先頭 (`{` の直後)
- `case`、`default`、`goto` のラベルの直後
- プリプロセッサ指令の直後
- 別のコメントの直後

関数末尾の `return` の直前では、次の場合は空行を入れません。

- `{` の直後 (本体が `return` だけの関数)
- 前置コメントの直後
- 本体が `return` を含めて 2 文以下で、`return` の直前が通常の文の場合。文は本体の直下にある宣言と文を数え、ブロックは 1 文、複数行にわたる文も 1 文と数えます。`return` の直前がブロックの場合は、ブロックの後の空行を優先して空行を入れます。

正本には、連続する `if` の望ましい例と望ましくない例、前置コメントの直前の望ましい例と望ましくない例、直前の代入値を判定する例外の例、関数末尾の `return` の例を記載します。

### 整形ツールとの関係

`clang-format` には、これらの空行を挿入する設定がありません。既存の空行は `MaxEmptyLinesToKeep` (LLVM の既定値は 1) の範囲で保持されるため、手作業で入れた空行は整形後も維持されます。  
`source-style-guideline.md` の「整形結果の確定と手作業修正の禁止」節に、空行の挿入はこの規則に従うことを追記し、整形結果の手作業修正の禁止と混同しないようにします。

### 検証

`app/general/bin/check_c_blank_lines.py` で、空行がない箇所を検出します (T-1)。

## Doxygen コメントの単位表記 (R-3)

`doxygen-comment-guideline.md` の「本文の記述規則」に、単位は値の後ろへ半角空白を置いて角括弧で示す (`タイムアウト [ms]`) ことを追加し、詳細は `coding-guideline.md` の「実装コメント」節の単位の表記を参照させます。

対象は、Git 管理下の各 app の `prod/` 配下にある `.c`、`.h`、`.cc` から、`gen/` 配下と bison・flex の出力 (`*.tab.c`、`*.tab.h`、`lex.*.c`) を除いたものです。サブモジュール (`app/cplat`、`app/porter`) は各サブモジュールの Git 管理下のファイルを対象とします。

### 手順

1. 対象ファイル一覧と進捗 (`261107-source-comment-progress.md`) を作成します。
2. 主エージェント (Opus) が、書式の移行と空行の挿入をスクリプトで行います。書式の移行は、複数行コメントの形式、コメント内の `/*`、`//`、単位の角括弧 (Doxygen コメントを含む) を対象とします。文体 (敬体から常体) は文の書き換えを伴うため、内容の見直しで行います。
3. 内容の見直しを、ディレクトリ単位でサブエージェントへ委譲し、主エージェントが結果をレビューします。
4. Doxygen コメントを変更した app で `make doxy` を実行します。
5. 全 app の作業を終えてから、まとめて提示します (途中で区切りません)。

### 内容の見直し

サブエージェントは、担当ディレクトリの各ファイルを [実装コメント規範](#実装コメント規範-r-1) と照合し、次を行います。

- 書く場面に該当する箇所へ、コードと文書で確認できる事実だけをコメントとして追加します。
- 既存のコメントを、文体 (常体)、形式、単位の表記、書かない内容の規則に合わせて修正します。
- 理由の推測が必要な箇所にはコメントを書かず、箇所と推測が必要な理由を報告します。主エージェントは報告を残課題一覧 (`261107-source-comment-backlog.md`) へ記録します。
- コードの変更 (識別子の変更、処理の変更、関数の分割など) は行いません。規範上の問題をコードに見つけた場合は報告し、主エージェントが残課題一覧へ記録します。

主エージェントのレビューでは、差分がコメントと空白だけであること、追加した理由がコードや文書で確認できること、規範との整合を確認します。
