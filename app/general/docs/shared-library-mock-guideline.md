# 第三者共有ライブラリの mock

## 対象

この文書は、第三者共有ライブラリの公開 API を API 表から mock 化するときの一般則を示します。  
ライブラリ固有のプリプロセッサ定義、ライブラリ名、除外 API は、対象パスに適用される `AGENTS.md` と README.md を正本とします。

## ライブラリの命名

外部の配布アーカイブから取り込む第三者管理ライブラリには、接尾辞 `_app` を付けます。  
共有ライブラリ名、リンク指定、mock の実委譲先の名前を一致させ、OS やほかの製品の同名ライブラリと区別します。  
第一者管理ライブラリと mock ライブラリの名前は変更しません。  
共有ライブラリのファイル名に加え、公開シンボル名またはシンボル バージョンの名前空間を OS 側と分離します。  
固有の公開 API 名を採用するライブラリでは、関数・変数と公開 API を呼び出すマクロに同じ接頭辞を使い、旧名 alias を提供しません。

## 構成

公開関数の一覧は `mock_<lib>_api_table.h` に集約します。  
元の第三者 API 名と固有の公開 API 名、実 API の引数と呼び出し式、mock の引数と呼び出し式を区別して記録します。  
同じ表から、関数宣言、`MOCK_METHOD`、real delegate、C リンケージのラッパー、`ON_CALL` を生成します。

API 表には include guard を置かず、展開に必要なマクロが未定義なら `#error` で停止します。  
可変長引数関数は表から除外し、対応する `va_list` 版を利用する専用実装を用意します。

API 表から生成する `ON_CALL` は 1 つのコンストラクターに集まり、巨大な関数になります。  
ビルド設定は [How to mock](../../../framework/testfw/docs/how-to-mock.md) の「モック ライブラリのビルド設定」に従い、`makepart.mk` で変数追跡や `/bigobj` を個別に指定しません。

## 呼び出し元情報を API 表と差し替えヘッダーで渡します

差し替えヘッダーは、mock をリンクするテストが明示した有効化マクロを確認して注入を行います。  
依存 app の差し替え探索パスが存在するだけでは有効にせず、実ライブラリを使うテストの呼び出しを維持します。  
通常呼び出しは関数形式マクロで C 用 mock 関数へ置き換え、先頭 3 引数に `__FILE__`、`__LINE__`、`__func__` を渡します。  
Google Mock のクラス定義は C++ 部分へ分離し、テスト対象の C ソースには C 用宣言と差し替えマクロだけを提供します。  
関連する公開ヘッダーの宣言がマクロで書き換えられないよう、宣言の取り込み後に差し替えを有効にします。  
固有の公開 API と同名の関数ラッパーも設け、関数アドレスの取得や関数ポインター経由の呼び出しを同じ mock 処理へ渡します。  
この経路は呼び出し元を取得できないため、ファイル名と関数名は `"<unknown>"`、行番号は `0` としてトレースにも取得不能であることを示します。  
旧 API 名の互換ラッパーは追加しません。

## 既定動作

mock が未注入の場合と、mock 注入後に個別動作を設定していない場合は、実ライブラリへ委譲します。  
実シンボルは固有の名前を `resolveSharedSymbolOrExit()` で解決し、OS 側の旧名へ戻す探索は行いません。  
ライブラリの接続またはシンボル解決に失敗した場合は、理由を標準エラーへ出力して終了します。  
実シンボルは `resolveSharedSymbolOrExit()` で解決し、ライブラリの接続またはシンボル解決に失敗した場合は、理由を標準エラーへ出力して終了します。  
ライブラリが見つからない場合は、探索に使う環境変数 (Linux は `LD_LIBRARY_PATH`、Windows は `PATH`) の値を併せて出力します。  
終了には後処理を行わない `_Exit()` を使うため、生存中の mock が gmock のリークとして報告されることはありません。

完全に隔離するテストでは、テスト対象が呼ぶ関数を `EXPECT_CALL` または `ON_CALL` で明示します。  
偽のハンドルを、既定動作によって実ライブラリへ渡さないようにしてください。

## リンク規則

利用側は実ライブラリではなく mock ライブラリだけをリンクします。  
両方をリンクすると、Linux では実共有ライブラリの強シンボルが mock の弱定義を上書きする場合があります。

Linux のラッパーには `MOCK_WEAK_IMPL` を使用します。  
Windows では、対象ヘッダーの `dllimport` を解除するライブラリ固有の定義を使用し、C API を `extern "C"` の強シンボルとして実装します。

## 関数 mock の限界

次の要素は、関数ラッパーだけでは差し替えられません。

- 公開構造体のフィールドを直接読む処理
- フィールドへ展開されるマクロ
- 公開変数
- 拡張 API 用の関数ポインター表

これらを使うテストでは、実レイアウトのオブジェクトを用意するか、対象処理を別の境界で隔離します。

## 確認

- API 表から生成するすべての要素が同じ関数一覧を使っていることを確認します。
- 利用側が実ライブラリを同時リンクしていないことを確認します。
- ライブラリ固有の Windows 定義が、mock 本体、利用例、README.md で一致していることを確認します。
- 公開 API の追加または削除を検出する対象 app のテストを実行します。
