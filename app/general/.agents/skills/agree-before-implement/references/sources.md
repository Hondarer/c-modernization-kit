# 出典と独自ルールの区別

このスキルは AWS の AI-DLC を参考に、AI とユーザーの対話を通じて作業前に合意を行うための運用を汎用化した独自スキルです。AWS 公式の配布物ではありません。v1 の特定タグやコミットとの対応は未確認であり、v1 への準拠は保証しません。次の表に示す main ブランチや公開記事は、今後更新される可能性があります。

## 本スキルの独自設計

次の各項目は、本スキルの独自設計に基づきます。この設計に対応する公開 URL はないため、架空の外部出典を関連付けないでください。

- このスキルは特定のプロジェクトやドメインに依存しない汎用スキルとし、コーディング規範、テスト構成、文章規範、ディレクトリ構成、Git 運用などのリポジトリ固有の情報や制約は、作業対象パスの `AGENTS.md` や各リポジトリの個別規範 (正本文書) を参照します。前提検討や質問の作成、回答検証、最終仕様の作成、成果物への反映に至るすべての段階において、該当する個別規範に準拠します。
- どの成果物にも適用し、前提の整合性・充足性と作業着手に合意するまで、指定した検討用 Markdown (`対象となる事柄-discussion.md` または `案件ディレクトリ/discussion.md`) 以外の成果物を作成・更新しません。AI は不足や矛盾を独断で解消せず、すべて Q として確認します。
- ユーザーから提示された案件の目標、目的、手法は、計画策定にあたっては確定した作業手順ではなく要求・要件として受け止めます。指示された手法を機械的に適用せず、その指示により得られる機能や効果が、リポジトリ固有の各種規範や既存実装と相反しないか、またリポジトリを横断して妥当かつ有益であるかを分析します。指示が個別規範と異なる場合や、単一箇所の局所修正にとどまる一方で依存元の共通処理を改修したほうが横断的な品質向上・不具合解消につながる場合などは、指示の文面だけをそのまま踏襲せず、本来の意図の確認や全体最適となる代替案の提案を Q&A に織り込んで合意を形成します。
- 検討用 Markdown の先頭に作業 WBS を設けます。WBS は情報収集と質問、残懸念の解消 (第 1 ゲート: 最終仕様作成への着手)、最終決定事項を記載した `対象となる事柄-design.md` (または `案件ディレクトリ/design.md`) の作成、最終仕様の承認の受付 (第 2 ゲート)、および承認された最終仕様に従って作業を完遂するまでの詳細手順を管理します。具体的な作業対象を明記し、Q&A のターンごとに必要に応じて見直し、各ゲートの通過・承認および作業の進行に従って状態を順次更新します。
- 作業 WBS の各項目は、チェック ボックスではなく行頭の絵文字で未着手 (⏸️)、実施中 (🔄)、ブロック中 (🚫)、要注意 (⚠️)、完了 (✅) の 5 状態を示します。ブロック中の項目には停止理由と関連 Q-ID、要注意の項目には未確認の事項と確認方法を併記し、要注意の項目を残したまま全完としません。現在取り組んでいる末端の項目 1 件に `← **CURRENT**` を付け、中断時は停止位置として残します。`← **CURRENT**` の項目は処理が中止された項目である場合があり、進んでいた範囲は文書だけでは分からないため、再開時は対象成果物の内容を確認して実施済みの範囲を特定してから作業を再開します。子項目を持つ項目の状態は、子項目から定めた順序で判定して導きます。質問の **Answer** の選択肢はユーザーがクリックして回答するため、チェック ボックスを維持します。
- 前提合意から成果物の受入承認までは 3 段階のゲートで進行します。第 1 ゲートはユーザーによる明示的な承認確認ではなく「残懸念なし (質問・未解決事項の解消)」とし、エージェントからの質問がなくなり懸念がないことをもってフェーズ 2 の最終仕様書 (`design.md`) の作成に着手します。第 2 ゲートで最終仕様書の承認を得てから具体的な対象成果物の作成・更新に着手します。そして作業完了後に第 3 ゲートで成果物の受入承認を得て一連の動作を完了します。検討文書の作成時点で対象成果物の変更を一括承認させたり、最終仕様の承認を得ずに対象成果物の変更に着手したりしてはなりません。
- 質問は明確化のための確認項目とし、1 件につき 1 つの判断のみを求めます (1 問 1 判断)。質問には質問に至った経緯を盛り込み、根拠となった実際の資料へのリンクや現状のコード引用、および推奨案だけでなく他の案についても採用した場合にどのようになるかを示すコード ブロックや具体例を盛り込み、各案の違いを理解できるようにします。ただし、質問意図が簡潔明瞭な際に全数で挿入する必要はなく、成果物の具体的な姿を提示したほうが良い場合や、意図不明とされた質問の詳細化において積極的に行います。**Answer** に選択方式 (単一選択または複数選択の別) を明記し、代表的な選択肢をチェック ボックスに A, B, C 形式で集約します。推奨する選択肢がある場合はテキスト先頭に `(推奨)` を付与してマークします。推奨案と理由、その他の回答余地を必須とします。
- 質問回答の記録において、Q の提示段階では **Answer** の回答者、回答日時、および **Assessment**、**History** は記載しません (ユーザーに質問内容の判断に集中させるため)。これらはユーザーの回答後に記録します。記録には JST ベースの日時と回答者 (通常の対話セッションでは Git ユーザー名、トランスクリプト反映時は発言者) を記載します。トランスクリプト (.vtt) の絶対日時特定のため必要に応じて会議開催日時を確認します。「その他の回答」と「補足」は「その他の回答 / 補足」として合成します。
- 検討用 Markdown 内の質問同士や参照先には、ファイル内リンク (`[Q-XXX](#q-xxx-...)`) を設けます。**Related** は該当がなければ項目自体を設けず、回答結果で過去の質問に **Related** の追加が必要になった際に追加します。
- 再質問や過去の質問への補足質問は、過去のやり取りを編集させず、新たな質問番号 (Q-ID) で継続します。
- **Answer** に選択肢 X として「意図不明 (詳細な質問内容に再生成すること)」を設けます。この選択がなされた場合は、そのターンの回答を踏まえて新たな質問番号 (Q-ID) で質問を再生成し、元の質問は回答済みとして以降のターンで回答させません。
- 最終決定事項 (最終仕様) は、途中で覆った経緯や議論の推移を含めず、最終的に確定した仕様を構造的に論ずる構成とします。重要な補足情報や意思決定の背景は、本文の構造を崩さず admonition (注記ブロック) で補います。また、検討用 Markdown を削除しても単体で意味が通る自己完結した文書とし、最終決定事項から検討用 Markdown への個別参照は原則行いません。上流文書への案内は本文に書かず、先頭のメタ情報に記載します。
- 検討用 Markdown、最終仕様、残課題一覧の先頭には、HTML コメントでメタ情報を置きます。メタ情報には、本スキルの生成物であること、文書種別、その対話を最終更新したエージェントの名称 (`agy`、`codex`、`claude code`、`grok`、`copilot` など) と含められる場合のセッション ID、上流文書または下流文書のパス、ファイルを開いたエージェント向けの再開手順を記載します。HTML コメントは GitHub、エディターのプレビュー、文書生成器のいずれでも表示されないため、YAML フロント マターではなく HTML コメントを使います。最終仕様と検討用 Markdown は削除される場合があるため、関連する生成物が存在しないことを異常として扱いません。また、各種エージェントを混在して利用し、別エージェントの過去セッションを引き取って継続する場合や担当変更によりセッションが見つからない場合があるため、セッションが見つからないことを致命的条件とせず、セッション情報があれば再開時のコンテキストに利用できる補足として扱います。
- 作成する文書 (検討用 Markdown および設計書) は、原則として「です・ます調」の文体とします。ただし、各質問の **Status** や検討文書メタデータの `状態:` などの状態表示は、丁寧語にせず単語の言い切り (「未回答」「未解決」「解決済み」「検討中」「合意済み」など) とします。Q&A の各ターンで都度機械的なフォーマット チェックを行う必要はなく、初期作成時や最終承認時などの節目に実施します。
- 推奨案が明確な質問に対して「おまかせ」やこれに準じる回答がなされた場合は、再確認の質問を行わず方針を確定します。対話の応答で回答を自動選定した旨を報告します。推奨案が不明確な場合のみ追加 Q で確認します。
- 対話でユーザーから「回答済み」と伝えられた場合でも、検討用 Markdown ファイルが更新されていない (未保存など) ときは、推測で進行せず、対話にてファイルの保存を促して保存を確認できるまで待機します。
- 検討用 Markdown (discussion ファイル) は初期作成時を版 1 とし、Q&A のターンを重ねるごとに版番号 (`版:`) をインクリメントして検討の版を管理します。
- 第 2 ゲートで最終仕様 (design.md) が否決された場合は、検討用 Markdown (discussion.md) の改版につながり、対話セッションでユーザーに理由を確認してフェーズ 1 に戻り、条件の再明確化と改版 (版番号インクリメント) を行って残懸念を解消してから design.md を再作成します。
- design に基づく作業が全完した際、見送る決定がなされた問題点や、作業中に潜在または別問題として判明したが今回は対策しなかった最終的な残渣 (残課題) を、`backlog.md` にチケット起票可能な詳細度・具体性で記録します。作業中に解消した問題や、仕様・制約として容認した問題点は含めません。
- フェーズ 3 の完了時、成果物、検証結果、未対応残渣がある場合の `backlog.md` を提示して成果物の承認 (第 3 ゲート) を求めます。「承認」または「完了」が宣言された場合にスキルによる一連の動作を完了し、以後は通常の対話となります。追加の課題や指摘を受けた場合は、フェーズ 1 の追加検討から再度やり直すか、一旦案件を完了して通常の対話として作業を行うかをユーザーに問い合わせます。

## 出典を扱う際の規則

AWS の原則、公開実装に見られる方式、本スキルの独自ルールを混同しないでください。  
将来 v1 への準拠を求められた場合は、対象のタグまたはコミットを特定して差分を確認します。  
確認できない事項を公式仕様として説明しないでください。
