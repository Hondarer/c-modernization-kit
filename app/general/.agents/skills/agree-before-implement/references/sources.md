## 本スキルの独自設計

次の各項目は、本スキルの独自設計に基づきます。この設計に対応する公開 URL はないため、架空の外部出典を関連付けないでください。

- このスキルは特定のプロジェクトやドメインに依存しない汎用スキルとし、コーディング規範、テスト構成、文章規範、ディレクトリ構成、Git 運用などのリポジトリ固有の情報や制約は、作業対象パスの `AGENTS.md` や各リポジトリの個別規範 (正本文書) を参照します。前提検討や質問の作成、回答検証、最終仕様の作成、成果物への反映に至るすべての段階において、該当する個別規範に準拠します。
- どの成果物にも適用し、前提の整合性・充足性と作業着手に合意するまで、指定した検討用 Markdown (`yymmdd-対象となる事柄-discussion.md` または `案件ディレクトリ/yymmdd-案件概要-discussion.md`)、全体管理文書 (`overview.md`)、簡易 ADR (`lightadr.md`)、残課題一覧 (`backlog.md`) 以外の成果物を作成・更新しません。生成物のファイル名 (案件ディレクトリ形式ではディレクトリ内のファイル名) には、全体管理文書と検討用 Markdown を新規作成した日 (JST) を `yymmdd-` 形式で前置し、同じ案件の生成物で共通にします。配置するディレクトリはスキルでは定めません。AI は不足や矛盾を独断で解消せず、すべて Q として確認します。
- ユーザーから提示された案件の目標、目的、手法は、計画策定にあたっては確定した作業手順ではなく要求・要件として受け止めます。指示された手法を機械的に適用せず、その指示により得られる機能や効果が、リポジトリ固有の各種規範や既存実装と相反しないか、またリポジトリを横断して妥当かつ有益であるかを分析します。指示が個別規範と異なる場合や、単一箇所の局所修正にとどまり、依存元の共通処理を改修したほうが横断的な品質向上や不具合解消につながる場合などは、指示の文面だけをそのまま踏襲せず、本来の意図の確認や全体最適となる代替案の提案を Q&A に織り込んで合意を形成します。
- 検討用 Markdown には Q&A の本文だけを置き、新しい Q を末尾へ追記します。案件の識別、作業 WBS、対象と参照資料、観点別の確認、質問一覧、合意版、経緯、反映と検証の記録は、全体管理文書 (`yymmdd-対象となる事柄-overview.md` または `案件ディレクトリ/yymmdd-案件概要-overview.md`) に置きます。Q&A のたびに更新する情報を検討用 Markdown の先頭に置くと行数が増減し、ユーザーがエディターで回答している Q の表示位置がずれるためです。経緯には、案件の進行上の出来事を発生順に追記します。
- Q&A で得られた事実、ユーザーの選択とコメント、およびそれらに基づく決定事項は、簡易 ADR (`yymmdd-対象となる事柄-lightadr.md` または `案件ディレクトリ/yymmdd-案件概要-lightadr.md`) に記録します。1 つのファイルに案件の決定事項をまとめ、決定 1 件ごとに「背景と課題」「得られた事実」「決定」「経緯」を記載します。「決定」は方針変更のたびに書き換えて案件終了時点の決定だけを示し、過去の Q&A は改変しないため、1 件の決定が複数の Q を源泉に持ち、その源泉を「経緯」に時系列で記録します。簡易 ADR は正式な ADR ではなく、正式な ADR への転記はユーザーが必要時に行います。本スキルは正式な ADR の運用を扱いません。
- 全体管理文書に作業 WBS を設けます。WBS は情報収集と質問、残懸念の解消 (第 1 ゲート: 最終仕様作成への着手)、最終決定事項を記載した `yymmdd-対象となる事柄-design.md` (または `案件ディレクトリ/yymmdd-案件概要-design.md`) の作成、最終仕様の承認の受付 (第 2 ゲート)、および承認された最終仕様に従って作業を完遂するまでの詳細手順を管理します。具体的な作業対象を明記し、Q&A のターンごとに必要に応じて見直し、各ゲートの通過・承認および作業の進行に従って状態を順次更新します。
- 作業 WBS の各項目は、チェック ボックスではなく行頭の絵文字で未着手 (⏸️)、実施中 (🔄)、ブロック中 (🚫)、要注意 (⚠️)、完了 (✅) の 5 状態を示します。ブロック中の項目には停止理由と関連 Q-ID、要注意の項目には未確認の事項と確認方法を併記し、要注意の項目を残したまま作業完了としません。現在取り組んでいる末端の項目 1 件に `← **CURRENT**` を付け、中断時は停止位置として残します。`← **CURRENT**` の項目は処理が中止された項目である場合があり、進んでいた範囲は文書だけでは分からないため、再開時は対象成果物の内容を確認して実施済みの範囲を特定してから作業を再開します。子項目を持つ項目の状態は、子項目から定めた順序で判定して導きます。質問の **Answer** の選択肢はユーザーがクリックして回答するため、チェック ボックスを維持します。
- 前提合意から成果物の受入承認までは 3 段階のゲートで進行します。第 1 ゲートはユーザーによる明示的な承認確認ではなく「残懸念なし (質問・未解決事項の解消)」とし、エージェントからの質問がなくなり懸念がないことをもってフェーズ 2 の最終仕様書 (`design.md`) の作成に着手します。第 2 ゲートで最終仕様書の承認を得てから具体的な対象成果物の作成・更新に着手します。そして作業完了後に第 3 ゲートで成果物の受入承認を得て一連の動作を完了します。検討文書の作成時点で対象成果物の変更を一括承認させたり、最終仕様の承認を得ずに対象成果物の変更に着手したりしてはなりません。
- 質問は明確化のための確認項目とし、1 件につき 1 つの判断のみを求めます (1 問 1 判断)。質問には質問に至った経緯を盛り込み、根拠となった実際の資料へのリンクや現状のコード引用、および推奨案だけでなく他の案についても採用した場合にどのようになるかを示すコード ブロックや具体例を盛り込み、各案の違いを理解できるようにします。ただし、質問意図が簡潔で明瞭な場合はすべての質問に挿入する必要はなく、成果物の具体的な姿を提示したほうがよい場合や、意図不明とされた質問の詳細化において積極的に行います。**Answer** に選択方式 (単一選択または複数選択の別) を明記し、代表的な選択肢をチェック ボックスに A, B, C 形式で集約します。推奨する選択肢がある場合はテキスト先頭に `(推奨)` を付与してマークします。推奨案とともに選定時に重視した優先順位・判断基準、理由、その他の回答余地を必須とし、ユーザーが自身の優先順位と乖離がないかを確認できるようにします。
- 質問回答の記録において、Q の提示段階では **Answer** の回答者、回答日時、および **Assessment**、**History** は記載しません (ユーザーに質問内容の判断に集中させるため)。これらはユーザーの回答後に記録します。記録には JST ベースの日時と回答者 (通常の対話セッションでは Git ユーザー名、トランスクリプト反映時は発言者) を記載します。トランスクリプト (.vtt) の絶対日時特定のため必要に応じて会議開催日時を確認します。「その他の回答」と「補足」は「その他の回答 / 補足」として合成します。
- 検討用 Markdown 内の質問同士や参照先には、ファイル内リンク (`[Q-XXX](#q-xxx-...)`) を設けます。全体管理文書と簡易 ADR から Q を参照する場合は、検討用 Markdown の該当見出しへの相対リンクを設けます。**Related** は該当がなければ項目自体を設けず、回答結果で過去の質問に **Related** の追加が必要になった際に追加します。
- 再質問や過去の質問への補足質問は、過去のやり取りを編集させず、新たな質問番号 (Q-ID) で継続します。
- **Answer** に選択肢 X として「意図不明 (詳細な質問内容に再生成すること)」を設けます。この選択がなされた場合は、そのターンの回答を踏まえて新たな質問番号 (Q-ID) で質問を再生成し、元の質問は回答済みとして以降のターンで回答させません。
- 最終決定事項 (最終仕様) は、途中で覆った経緯や議論の推移を含めず、最終的に確定した仕様を構造的に記述します。重要な補足情報や意思決定の背景は、本文の構造を崩さず admonition (注記ブロック) で補います。また、検討用 Markdown を削除しても単体で意味が通る自己完結した文書とし、最終決定事項から検討用 Markdown への個別参照は原則行いません。上流文書への案内は本文に書かず、先頭のメタ情報に記載します。
- 全体管理文書、検討用 Markdown、簡易 ADR、最終仕様、残課題一覧の先頭には、HTML コメントでメタ情報を置きます。メタ情報には、本スキルの生成物であること、文書種別、最終更新日時 (`YYYY-MM-DD HH:MM:SS JST`)、その文書を最終更新したエージェントの名称 (`agy`、`codex`、`claude code`、`grok`、`copilot` など) と含められる場合のセッション ID、稼働 OS (`Windows`、`Linux`、`Linux (WSL)` など。WSL 上の Linux 環境はネイティブの `Linux` と区別する。ホスト名などの端末固有の識別情報はリポジトリで公開すべき情報ではないため含めない)、上流文書または下流文書のパス、ファイルを開いたエージェント向けの再開手順を記載します。HTML コメントは GitHub、エディターのプレビュー、文書生成器のいずれでも表示されないため、YAML フロント マターではなく HTML コメントを使います。最終仕様と検討用 Markdown は削除される場合があるため、関連する生成物が存在しないことを異常として扱いません。また、各種エージェントや複数の環境、稼働 OS (`Windows` と `Linux (WSL)` の切り替えなど) を混在して利用し、別エージェントや別環境の過去セッションを引き取って継続する場合や担当変更によりセッションが見つからない場合があるため、セッションが見つからないことを致命的な異常とせず、セッション情報や稼働 OS・日時情報があれば再開時のコンテキストや環境差分の把握に利用できる補足として扱います。
- 作成する文書 (全体管理文書、検討用 Markdown、簡易 ADR、最終仕様、残課題一覧) では、レベル 1 見出し (`#`) を文書タイトルとして各ファイルにつき先頭の 1 か所のみに使用し、本文の見出しはレベル 2 (`##`) から始めて階層を飛ばさずに構成します (検討用 Markdown の各質問は `## 明確化のための確認項目` 配下のレベル 3 見出し `### Q-XXX ...`、簡易 ADR の各決定と残課題一覧の各課題はレベル 2 見出し `## LADR-XXX ...` / `## BL-XXX ...` とその配下のレベル 3 見出し)。文体は原則として「です・ます調」とし、各質問の **Status** や全体管理文書の `状態:` などの状態表示は単語の言い切り (「未回答」「未解決」「解決済み」「検討中」「合意済み」など) とします。Q&A の各ターンで都度機械的なフォーマット チェックを行う必要はなく、初期作成時や最終承認時などの節目に実施します。
- ユーザーに検討用 Markdown の審査・回答を促す際、「全件おすすめ」「おまかせ」といった一括承認や判断の全面的な委任を提案・誘導しません。また、各判断の全面的な委任は許容せず、推奨案の採用であっても、検討用 Markdown 上でユーザー自身が各 `(推奨)` をチェックして回答するか、対話で対象の Q-ID を明示的に指定したうえで推奨案で良い旨を受理した場合にのみ確定します。対象指定のない「おまかせ」「全件推奨で」などの包括的な回答は受理せず、各質問へのチェックまたは対象 Q-ID を明示した指示を求めます。推奨案が不明確な場合や採用対象が一意でない場合は追加 Q で確認します。
- 対話でユーザーから「回答済み」と伝えられた場合でも、検討用 Markdown ファイルが更新されていない (未保存など) ときは、推測で進行せず、対話にてファイルの保存を促して保存を確認できるまで待機します。
- モバイル セッションなどへの対応として、ユーザーが個別の Q&A を対話セッションで要求した場合は、ユーザーが検討用 Markdown を直接編集できる環境で対話による回答をキャンセルする可能性に備え、先に未回答状態の質問を記載した検討用 Markdown と全体管理文書を作成・更新してからユーザーへ問い合わせます。回答後の検討用 Markdown への記入 (選択肢のチェック、コメントの転記、回答者・回答日時の記録) はエージェントが実施します。対話セッションでも Markdown ベースの手続きと品質を変えず、選択肢の決定とコメントの記入を併用するべきであるため、択一式では選択とコメントを同時に示せない制約を避け、複数選択式の選択肢の提示と任意コメントを 1 回で入力できる問い合わせ方法を推奨します。本来択一式の質問で複数チェックされた場合は、推測で 1 つに絞らず再度ユーザーに真意を確認します。
- 検討用 Markdown (discussion ファイル) は初期作成時を版 1 とし、Q&A のターンを重ねるごとに、全体管理文書の「案件の識別」に記録する版番号 (`検討用 Markdown の版:`) をインクリメントして検討の版を管理します。
- 第 2 ゲートで最終仕様 (design.md) が否決された場合は、対話セッションでユーザーに理由を確認してフェーズ 1 に戻り、条件の再明確化と検討用 Markdown (discussion.md) の改版 (版番号インクリメント) を行って残懸念を解消してから design.md を再作成します。
- 見送る決定がなされた問題点や、作業中に潜在的な問題や別問題として判明した問題点は、気付いた時点で当該作業の `backlog.md` に随時追記します。作業の中断や障害で終盤の手順が実行されなくても、気付いた事項を失わないためです。design に基づく作業がすべて完了した後、第 3 ゲートの前に文書を再構築して整理し、当該作業中に解消した問題や、仕様・制約として容認した問題点を除外して、今回は対策しなかった最終的な残渣 (残課題) だけをチケット起票可能な詳細度・具体性で残します。過去の `backlog.md` を使って新たな案件 (継続作業) を開始・進行する際は、過去の `backlog.md` ファイルや記載を削除することなく、作業完了時だけでなく案件開始時 (検討用 Markdown の作成時) から検討・設計・各課題の実装完了・最終整理に至る各段階において、過去の `backlog.md` 側の継続作業の状況 (メタ情報、各項目の状態、経緯と対処) も随時更新することを原則とします。また、フェーズ分けした `backlog.md` の対策で対処できていない項目は、当該作業の `backlog.md` にも必ず転記し、最新作業の `backlog.md` を見れば残件が把握できるようにします。
- フェーズ 3 の完了時、成果物、検証結果、未対応残渣がある場合の `backlog.md` を提示して成果物の承認 (第 3 ゲート) を求めます。「承認」または「完了」が宣言された場合にスキルによる一連の動作を完了し、以後は通常の対話となります。追加の課題や指摘を受けた場合は、フェーズ 1 の追加検討から再度やり直すか、一旦案件を完了して通常の対話として作業を行うかをユーザーに問い合わせます。

## 出典を扱う際の規則
