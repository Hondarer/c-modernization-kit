# 出典と独自ルールの区別

このスキルは AWS の AI-DLC を参考に、AI とユーザーの対話を通じて作業前に合意を行うための運用を汎用化した独自スキルです。AWS 公式の配布物ではありません。v1 の特定タグやコミットとの対応は未確認であり、v1 への準拠は保証しません。次の表に示す main ブランチや公開記事は、今後更新される可能性があります。

## 本スキルの独自設計

次の各項目は、本スキルの独自設計に基づきます。この設計に対応する公開 URL はないため、架空の外部出典を関連付けないでください。

- このスキルは特定のプロジェクトやドメインに依存しない汎用スキルとし、コーディング規範、テスト構成、文章規範、ディレクトリ構成、Git 運用などのリポジトリ固有の情報や制約は、作業対象パスの `AGENTS.md` や各リポジトリの個別規範 (正本文書) を参照します。前提検討や質問の作成、回答検証、最終仕様の作成、成果物への反映に至るすべての段階において、該当する個別規範に準拠します。
- どの成果物にも適用し、前提の整合性・充足性と生成開始に合意するまで、指定した検討用 Markdown (`対象となる事柄-discussion.md` または `案件ディレクトリ/discussion.md`) 以外の成果物を生成・更新しません。AI は不足や矛盾を独断で解消せず、すべて Q として確認します。
- 検討用 Markdown の先頭に作業 WBS チェックリストを設けます。WBS は情報収集と質問、検討用 Markdown の承認の受付 (第 1 ゲート)、最終決定事項を記載した `対象となる事柄-design.md` (または `案件ディレクトリ/design.md`) の作成、最終仕様の承認の受付 (第 2 ゲート)、および承認された最終仕様に従って作業を完遂するまでの詳細手順を管理します。具体的な作業対象を明記し、Q&A のターンごとに必要に応じて見直し、各ゲートの承認および作業の進行に従ってチェックリストを順次更新します。
- 前提合意から作業着手までは 2 段階の承認ゲートで進行します。第 1 ゲートで検討用 Markdown (方針・前提条件) の承認を得てから最終仕様書 (`design.md`) を作成し、第 2 ゲートで最終仕様書の承認を得てから初めて具体的な対象成果物の生成・更新に着手します。検討文書の承認時点で対象成果物の変更を一括承認させたり、最終仕様の作成と対象成果物の変更を同時に着手したりしてはなりません。
- 質問は明確化のための確認項目とし、1 件につき 1 つの判断のみを求めます (1 問 1 判断)。**Answer** に選択方式 (単一選択または複数選択の別) を明記し、代表的な選択肢をチェック ボックスに A, B, C 形式で集約します。推奨する選択肢がある場合はテキスト先頭に `(推奨)` を付与してマークします。推奨案と理由、その他の回答余地を必須とします。
- 質問回答の記録において、Q の提示段階では **Answer** の回答者、回答日時、および **Assessment**、**History** は記載しません (ユーザーに質問内容の判断に集中させるため)。これらはユーザーの回答後に記録します。記録には JST ベースの日時と回答者 (通常の対話セッションでは Git ユーザー名、トランスクリプト反映時は発言者) を記載します。トランスクリプト (.vtt) の絶対日時特定のため必要に応じて会議開催日時を確認します。「その他の回答」と「補足」は「その他の回答 / 補足」として合成します。
- 検討用 Markdown 内の質問同士や参照先には、ファイル内リンク (`[Q-XXX](#q-xxx-...)`) を設けます。**Related** は該当がなければ項目自体を設けず、回答結果で過去の質問に **Related** の追加が必要になった際に追加します。
- 再質問や過去の質問への補足質問は、過去のやり取りを編集させず、新たな質問番号 (Q-ID) で継続します。
- **Answer** に選択肢 X として「意図不明 (詳細な質問内容に再生成すること)」を設けます。この選択がなされた場合は、そのターンの回答を踏まえて新たな質問番号 (Q-ID) で質問を再生成し、元の質問は回答済みとして以降のターンで回答させません。
- 最終決定事項 (最終仕様) は、途中で覆った経緯や議論の推移を含めず、最終的に確定した仕様を構造的に論ずる構成とします。重要な補足情報や意思決定の背景は、本文の構造を崩さず admonition (注記ブロック) で補います。また、検討用 Markdown を削除しても単体で意味が通る自己完結した文書とし、最終決定事項から検討用 Markdown への個別参照は原則行いません (上流ドキュメントとして 1 行言及する程度は問題ありません)。
- 作成する文書 (検討用 Markdown および設計書) は、原則として「です・ます調」の文体とします。ただし、各質問の **Status** や検討文書メタデータの `状態:` などの状態表示は、丁寧語にせず単語の言い切り (「未回答」「未解決」「解決済み」「検討中」「合意済み」など) とします。Q&A の各ターンで都度機械的なフォーマット チェックを行う必要はなく、初期作成時や最終承認時などの節目に実施します。
- 推奨案が明確な質問に対して「おまかせ」やこれに準じる回答がなされた場合は、再確認の質問を行わず方針を確定します。対話の応答で回答を自動選定した旨を報告します。推奨案が不明確な場合のみ追加 Q で確認します。
- 対話でユーザーから「回答済み」と伝えられた場合でも、検討用 Markdown ファイルが更新されていない (未保存など) ときは、推測で進行せず、対話にてファイルの保存を促して保存を確認できるまで待機します。
- 検討用 Markdown (discussion ファイル) は初期作成時を版 1 とし、Q&A のターンを重ねるごとに版番号 (`版:`) をインクリメントして検討の版を管理します。
- 第 2 ゲートで最終仕様 (design.md) が否決された場合は、検討用 Markdown (discussion.md) の改版につながり、対話セッションでユーザーに理由を確認してフェーズ 1 に戻り、条件の再明確化と改版 (版番号インクリメント) を行って前提合意を取り直してから design.md を再作成します。
- design に基づく作業が全完した際、見送る決定がなされた問題点や、作業中に潜在または別問題として判明したが今回は対策しなかった最終的な残渣 (残課題) を、`backlog.md` にチケット起票可能な詳細度・具体性で記録します。作業中に解消した問題は含めません。

## 出典を扱う際の規則

AWS の原則、公開実装に見られる方式、本スキルの独自ルールを混同しないでください。  
将来 v1 への準拠を求められた場合は、対象のタグまたはコミットを特定して差分を確認します。  
確認できない事項を公式仕様として説明しないでください。
