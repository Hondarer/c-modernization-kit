# 成果物生成前の前提合意

## 基本原則

成果物に必要な前提を多角的に検討し、ユーザーとの合意を検討用 Markdown に記録してから生成・更新してください。AI-DLC の質問による明確化を参考とする独自の汎用手順として扱い、AWS 公式スキルや v1 へ厳密に準拠していると表明しないでください。

AI は資料の読解、事実確認、不足や矛盾の検出、選択肢と推奨理由の提示を行います。ただし、ユーザーが示していない条件、判断、決定を補わないでください。これらは推奨案や源泉を明確にした意見の提示としてのみ許されます。慣行、既定値、推奨案、実装の容易さを採用の根拠にしてはなりません。不足、曖昧さ、矛盾はすべて Q としてユーザーに確認してください。事実の引用と、採用すべき方針の決定を明確に区別してください。

## 書き込みの境界

合意前は、この検討のために指定した Markdown のみを作成・更新してください。既存資料やソース コードの読み取りや、書き込みを伴わない調査は行って構いません。対象成果物、参照資料、コード、設定、関連文書の新規作成・変更・削除を行わないでください。下書きや試作という名目であっても、セッション用の一時ファイル以外の検討用 Markdown の外へ出力してはなりません。必要な比較案や短い試案は検討用 Markdown 内に配置してください。資料を変更するコマンド、生成器、整形器、ビルドなども合意前に実行しないでください。セッション用の一時フォルダーに複製してのコマンド、生成器、整形器、ビルドは事前検証として許容します。

検討文書には判断過程を、成果物には確定した内容を記載します。成果物に必要な判断理由は残して構いませんが、質問の往復や旧回答を混入させないでください。成果物と検討文書は、検討 ID、合意版、パスで対応付けます。

## 検討の開始と再開

まず依頼内容、既存の検討文書、参照資料を確認してください。対象成果物、参照資料の版、今回の範囲、書き込み可能な検討用 Markdown を記録します。ユーザーがすでに明示した内容は根拠とともに転記し、再回答を強制しないでください。ただし、新たな意味を含む解釈は Q として確認します。

新規の検討には `assets/discussion-template.md`、各質問には `assets/question-template.md` を参照して使用してください。検討用 Markdown の先頭には、この検討が完了した際に行う作業項目の WBS と、その進行を管理するチェック付きリストを設けてください。作業 WBS には抽象的な工程だけでなく、具体的な作業対象 (対象ファイルや成果物) を明記します。質問は 1 件 1 葉、すなわち独立した見出しと安定した Q-ID を持つ単位とし、1 件で 1 つの判断のみを求めます。1 つの検討用 Markdown 内に複数の質問葉を配置して構いません。確認対象をまとめた複合質問にしないでください。

再開時はユーザーが編集した最新版を読み直してください。前回参照した内容やチャット上の記憶で上書きしてはなりません。更新直前にも変更を確認し、競合を検出したら最新版に基づいて処理します。取得できない過去の内容や時刻を推測で補わないでください。

## 多角的な確認

次の各観点について、確認結果と根拠となる資料または Q-ID を記録してください。

| 観点 | 確認事項 |
| --- | --- |
| 目的・利用者 | 誰が何のために使い、何を実現すればよいか |
| 範囲・境界 | 対象、対象外、変更可能範囲が明確か |
| 入力・根拠 | 必要な資料がそろい、版と適用範囲が明確か |
| 整合性・依存関係 | 回答同士、用語、上位資料、制約が整合するか |
| 実現性・例外 | 実現可能性、異常時、境界条件が明確か |
| 受入条件・検証 | 完成と正しさを確認する基準と方法があるか |

観点ごとに「確認済み」「未解決」「対象外」を示してください。対象外としての扱い、後回し、仮定の採用についても、ユーザーによる根拠の提示または回答を必須とします。質問がすべて回答済みであっても、観点の未確認や未解決があれば生成へ進まないでください。

## 質問と回答の形式

`[Question]` には判断対象を 1 つのみ記述してください。単一選択または複数選択の別を明記します。`[Context]` には質問が必要な理由と影響を示します。専門用語を説明し、回答に必要な背景を省かないでください。

代表的な選択肢は `[Answer]` に記述します。各選択肢に安定した ID と `- [ ]` を付与します。必ず「その他」と自由記入欄を設け、さらに `- [ ] 意図不明 (詳細な質問内容に再生成すること)` を設けてください。自由回答も正式な回答として受け付けます。

`[Recommendation]` には推奨する選択肢 ID と理由、重要な制約を示します。根拠が不足して推奨できない場合は、その不足を明記し、根拠のない推奨案を創作しないでください。推奨案であっても初期状態ではチェックを付けないでください。

`[Answer]` はユーザーの意思表示、`[Assessment]` は AI の検証結果として分離してください。ユーザーが明示的に選んだ内容のみを `- [x]` にします。チャットから回答を転記する場合は発言の出典を残し、推測を回答へ混入させないでください。回答を誘導する事前チェックを行わないでください。

## 回答の検証と追加質問

回答後は、単一の Q だけでなく、過去の回答、現行の合意要約、参照資料を横断して再検証してください。回答済みと解決済みを区別します。

未回答、単一選択の複数チェック、自由記述との不一致、「その他」の具体内容不足、曖昧な条件、資料との矛盾は未解決とします。AI が優先順位を決定したり、不足した値を補ったりしないでください。それぞれ 1 つの判断を問う追加 Q を作成します。例えば再試行の実施が決まっても、回数と間隔は別々の Q としてください。

「お任せ」「適切に」「推奨で」などの回答で採用対象が一意でない場合は、具体的な提案を Q にして確認してください。明確に特定された推奨案の採用回答は、その範囲に限って転記して構いません。沈黙、経過時間、単なる「続けて」といった指示を、未解決事項の承認とみなさないでください。

## 複数ターンと過去の Q&A の整備

後続の回答によって過去の決定が明確に変更された場合は、過去の該当 Q&A にも遡って現行の回答、状態、評価、関連質問を更新してください。本文を先頭から順に読むだけで現行の決定を把握できるように保ちます。単に追記するだけで旧回答を有効なまま放置しないでください。

Q&A のターンごとに、ユーザーの回答や方針決定を踏まえて作業 WBS の見直し要否を判断してください。作業対象の追加・変更や工程の詳細化が必要であれば、適宜作業 WBS を見直して更新します。

更新前の回答、変更理由、変更根拠の Q-ID またはユーザー発言、版を `[History]` に保存してください。旧版を現行の回答と明確に区別し、履歴のチェック ボックスを現行回答として解釈してはなりません。必要に応じて履歴内をコード ブロックで保存します。

明示的な変更回答の転記は行って構いませんが、後続の回答によって以前の回答が自動的に上書きされたとは扱わないでください。置換の意思や影響が不明なら追加 Q で確認し、現行本文に矛盾が未解決である旨を明記してください。影響を受ける合意も再確認対象に戻します。

質問文と選択肢の意図は原則として固定し、回答後に定義を変更しないでください。新たな判断には新しい Q-ID を用います。

## 「意図不明」による質問再生成の例外

ユーザーが `[Answer]` の「意図不明」を選択した場合は、当該質問の改訂指示として受け付けてください。通常の質問固定原則の例外として、追加の改訂許可を求めず、質問、背景、用語説明、選択肢、推奨理由を具体的に改訂します。

判断対象と Q-ID は維持してください。別の論点への変更、複数の判断の混入、回答の代行、成果物の更新を行わないでください。再生成前の質問一式と回答状態を `[History]` に保存し、理由を「ユーザーによる意図不明の指定」と記録します。

再生成後は当該 Q を未回答に戻し、すべての現行チェックを外して再回答を待ってください。以前の回答を新しい文面への回答として引き継いではなりません。「意図不明」と実質的な回答が同時にチェックされている場合も、実質回答を決定として採用せず再生成し、その同時選択を履歴に残します。影響する合意を再確認対象に戻してください。

## 合意と生成のゲート

すべての確認観点に根拠があり、必要な決定に未解決事項がないことを検証してください。未確定事項を対象外、後続判断、仮定として扱う場合も、その扱いに対するユーザーの承認を必須とします。必須の前提が不足したまま作業を進めないでください。

検討用 Markdown に確定内容、更新対象、受入条件、根拠となる Q-ID をまとめ、文書の版を特定してください。最後に、その版の確定内容を対象成果物へ反映してよいかのみを対話セッションで行い、その結果を検討用 Markdown に反映します。複数の未決事項を一括承認で解消してはなりません。

ユーザーが承認した版と範囲のみを生成・更新してください。すでに当該版・範囲への明確な承認がある場合は、それを記録し、重複して承認を求めないでください。承認後に回答や参照資料が変更された場合は影響を再検証し、関係する合意を再確認対象に戻します。

生成中に新たな判断が必要になった場合は、対象成果物への書き込みを中断し、検討用 Markdown の Q に戻ってください。変更済みの範囲と停止位置を記録し、独断で修正や巻き戻しを行わないでください。生成後は合意内容および受入条件と照合します。前提合意と成果物の受入を区別し、生成しただけで受入済みとしないでください。

## 承認後の作業進行と進捗管理

合意ゲートを通過してユーザーの承認を得た後は、対象成果物の生成・更新に着手し、作業の進行に従って検討用 Markdown 先頭の作業 WBS チェックリストを順次更新 (`- [x]`) してください。

各作業項目の着手前と完了後に該当するチェック ボックスを更新し、進捗状況を可視化します。生成や検証の過程で新たな判断が必要になった場合や問題が発生した場合は、対象成果物への書き込みを中断し、該当する WBS 項目や検討用 Markdown の Q の状態を更新してユーザーに確認してください。

## 出力品質

ユーザーの使用言語で、具体的かつ回答可能な問いを記述してください。質問待ちの応答では検討文書と未解決 Q-ID を案内します。内部の逐語的思考ではなく、検証可能な根拠、選択理由、決定、変更履歴を記録してください。Markdown ファイルは UTF-8 とし、末尾を空行で終えてください。
